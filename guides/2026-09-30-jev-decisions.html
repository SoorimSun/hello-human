에이전트가 일을 진행하는 동안, 작은 판단은 계속 쌓입니다.

요청에 맞는 도구를 고르고, 검색 결과에서 필요한 자료를 추리고, 작업 기록 중 다음 단계에 남길 정보를 정합니다. 여러 단계를 계획하는 능력과 함께, 각 단계의 선택을 빠르고 일관되게 처리하는 설계가 중요해집니다. 현재 에이전트 문서도 모델, 도구, 실행 환경과 작업 상태를 함께 다룹니다. OpenAI · 에이전트 구성 ↗

이 가운데 문장의 의미를 읽어야 하지만, 결과는 선택지 하나나 점수면 충분한 일이 있습니다. Jev는 이런 판단을 프로그램에 연결하는 모델입니다. 이번 가이드에서는 에이전트와 기존 업무 코드 사이에 작은 판단을 넣는 방법을 살펴봅니다.

첫 번째 가이드에서 모델·도구·검증의 조합을 골랐다면, 이번에는 그 조합 안에서 반복되는 판단 하나를 분리해 보겠습니다.

10월 2일 업데이트 Clef, Perplexity Decider, Mercury Decide와 추가 후보를 비교하고, 두 공개 리더보드의 평가 조건을 확인했습니다. 모델 비교부터 읽거나, Jev 실습을 따라간 뒤 같은 한국어 데이터로 후보를 비교해 보세요.

1. 에이전트 안에서 Jev가 맡을 일

고객이 이렇게 요청했다고 가정해 보겠습니다.

주문한 물건이 아직 안 왔어요. 취소는 하지 말고 배송 상태만 확인해 주세요.

시스템은 배송 조회로 보내야 합니다. ‘취소’라는 단어가 등장했다고 취소 흐름을 선택하면 고객의 의도를 거꾸로 이해한 셈입니다. 키워드만으로 처리하기 어렵지만, 여기서 필요한 결과는 긴 분석문보다 delivery라는 분류값입니다.

TypeSafe는 Jev를 System One 모델이라고 부릅니다. 평가할 정보인 state와 형식을 정한 questions를 보내면, 코드가 사용할 수 있는 선택·점수·확률을 반환합니다. 한 질문에 하나의 좁은 판단을 맡기고, 여러 결과를 코드에서 조합하는 접근입니다. TypeSafe · 소개 ↗

상태는 한 번 읽고, 질문은 나누어 판단합니다

입력은 두 부분으로 나뉩니다. state에는 고객 문의와 관련 정보를, questions에는 질문별 지시문과 선택지·평가 기준을 담습니다. 공식 문서에 따르면 Jev는 state를 한 번 읽고, 같은 상태를 바탕으로 여러 질문을 병렬 평가합니다. 각 질문은 독립적이어서 다른 질문의 답을 기다리거나 이어받지 않습니다. TypeSafe · 상태 처리 방식 ↗ · 질문의 독립성 ↗

학습 목표도 이 구조에 맞춥니다. TypeSafe는 사전학습 언어 모델을 RLCD라는 방식으로 후속 학습해, 판단 결과와 보정된 확률을 반환하도록 한다고 설명합니다. RLCD는 Reinforcement Learning for Calibrated Decisions의 약자입니다. 확률 보정은 많은 예측에서 부여한 확률과 실제 발생 비율이 맞아가도록 하는 목표이며, 개별 답의 정답을 보장하는 것은 아닙니다. TypeSafe · RLCD와 확률 보정 ↗

에이전트에서는 생성·추론 모델이 전체 작업을 계획하고 응답문을 작성할 수 있습니다. Jev는 그 사이에 필요한 선택과 평가를 맡고, 프로그램은 반환된 값을 조합해 도구와 업무 API를 실행합니다. 이 분류 기능은 기존 업무 프로그램에도 바로 연결할 수 있습니다.

예를 들어 ‘쿠폰 관련 요청인가?’는 의미 판단입니다. 반면 쿠폰 적용 조건, 재고 수량, 최종 결제 금액은 업무 로직이 확인해야 합니다. 공식 한계 문서도 산술과 정밀한 수치 처리, 날짜 비교를 코드에 맡기도록 안내합니다. TypeSafe · 알려진 한계 ↗

Jev는 스스로 주문 상태를 조회하거나 도구를 실행하지 않습니다. 판단 결과를 받아 어떤 동작으로 연결할지 결정하는 주체는 프로그램입니다.

2. Choice, Score, Noul로 질문하기

세 가지 질문 방식을 익히면 대부분의 첫 실험을 구성할 수 있습니다.

방식질문 예시반환값
Choice배송, 취소·반품, 상품 문의 중 어디에 해당하는가?choice, 선택지별 probabilities, confidence
Score표현된 긴급성은 어느 수준인가?score, 단계별 probabilities, confidence, legend
Noul기존 주문을 바꾸는 작업을 실제로 요청했는가?‘예’에 해당하는 확률 noul, 0~1

Choice의 선택지는 직접 정의합니다. Noul은 예·아니요 질문이며 null과 관계가 없습니다. Noul에는 별도 confidence 필드가 없습니다. Choice ↗ · Noul ↗

Score의 숫자는 내가 정의한 단계입니다

긴급성을 ‘급한 처리 요구 없음’, ‘빠른 처리 요구’, ‘오늘·즉시 등 구체적인 마감’으로 정의하면 세 단계의 위치는 0, 1, 2입니다. 결과는 단계별 확률을 가중 평균하므로 1.6처럼 중간값도 나옵니다. 범위는 0~2이며, ‘정확도 160%’로 해석할 수 없습니다. TypeSafe · Score의 단계와 점수 ↗

질문을 묶되, 결과는 코드에서 조합합니다

업무 유형, 긴급성, 변경 요청 여부를 한 요청에 담을 수 있습니다. 다만 각 질문은 같은 state를 보고 독립적으로 평가됩니다. ‘첫 번째 답이 취소일 때만 두 번째를 판단하라’는 연결을 가정하지 말고, 응답을 받은 코드가 필요한 결과를 선택해야 합니다. TypeSafe · 여러 질문의 평가 방식 ↗

3. Jev 이후의 디시전 모델, 무엇이 다른가

Jev는 TypeSafe의 제품명입니다. Cloudflare의 Clef, Perplexity의 Decider, Inception의 Mercury Decide는 각각 다른 모델입니다. 이들이 공유하는 방향은 상황과 선택 기준을 받아, 프로그램이 바로 쓸 수 있는 제한된 답과 확률을 돌려주는 것입니다.

선택할 때는 정답률뿐 아니라 어떤 입력을 읽는지, 직접 운영할 수 있는지, 기존 API와 어디까지 호환되는지를 함께 봐야 합니다. 아래는 2026년 10월 2일 확인한 공개 사양입니다.

커머스에서는 문의 문장에 첨부된 파손 사진이나 상품 이미지까지 검토 대상으로 넓힐 수 있습니다. 다만 이미지 입력 지원과 파손 판정의 정확도는 별개이므로, 실제 촬영 조건과 한국어 문의를 함께 평가해야 합니다. Flash도 모든 과제에서 Clef와 같은 품질을 내는 것은 아닙니다.

공개 모델 카드의 영상 지원과 호스팅 API의 입력 필드는 구분해야 합니다. 현재 Workers AI 규격은 첨부 이미지 확장을 명시하므로, 영상 처리에는 실제 사용할 실행 경로의 지원 범위를 먼저 확인하세요. Workers AI · 입력 규격 ↗

Perplexity는 확률 출력과 API 계약을 함께 봐야 합니다

모델 카드의 11개 벤치마크 자체 평가에는 RAGTruth처럼 Jev보다 높은 항목과 BBH처럼 낮은 항목이 함께 있습니다. 이 결과를 모든 업무의 우열로 일반화할 수는 없습니다. 직접 운영할 때는 공식 예제가 가중치만 약 49GiB에 추가 작업 메모리를 요구한다는 점도 고려해야 합니다. Perplexity · 평가와 로컬 실행 조건 ↗

Mercury Decide는 API로 빠르게 비교할 후보입니다

OpenRouter는 9월 30일 공개된 Mercury Decide를 System One 엔드포인트로 소개하며, 32,768토큰 문맥과 보정된 확률 출력을 명시합니다. ‘초당 최대 14개 판단’은 제공 측 설명이며, 한국어 요청의 길이·질문 수·동시 처리 조건이 같은 측정은 아닙니다. 무료 경로는 초기 비교에 유용하지만 운영 용량을 보장하는 가격표로 읽어서는 안 됩니다. OpenRouter · Mercury Decide 사양과 제공 조건 ↗

선택지가 많아졌다는 사실이 곧 모든 모델의 품질이 같다는 뜻은 아닙니다. 빠른 API 비교, 시각 입력, 로컬 운영, 자체 학습 중 지금 필요한 조건으로 두세 후보를 좁힌 뒤 평가하는 편이 좋습니다.

4. 리더보드는 순위보다 평가 조건부터

사용할 자료는 두 곳입니다. 커뮤니티 Jev Decision Index는 공개 재현 모델과 Jev를 비교합니다. Cloudflare Decision Model Leaderboard는 그 결과에 Clef 계열의 자체 측정치를 더한 보드입니다. 두 곳 모두 모든 신제품을 평가한 목록은 아닙니다.

Decision Index 점수는 정답률 퍼센트가 아닙니다. 0.2.1 지수는 38개 벤치마크를 지식·언어·검색/분류·도구·취향의 다섯 영역으로 묶고, 무작위 선택의 기대 성적을 보정해 가중 평균합니다. 0은 무작위 수준, 100은 완벽한 결과에 해당합니다. Decision Index · 계산법과 재현 조건 ↗

route 같은 질문 키는 응답을 찾기 위한 이름입니다. 키 자체는 판단 지시를 대신하지 않으므로 무엇을 평가할지는 instructions에 적습니다. 요청·응답의 필드와 Bearer 인증은 공식 HTTP API 규격을 따릅니다.

다음은 WSL·Linux·macOS의 Bash에서 실행하는 예시입니다. API 키를 발급받은 뒤 request.json이 있는 폴더에서 호출합니다.

# 키를 화면에 표시하지 않고 입력합니다.
read -rsp "TypeSafe API key: " TYPESAFE_API_KEY
printf '\n'
export TYPESAFE_API_KEY

curl --fail-with-body --silent --show-error \
  --connect-timeout 3 --max-time 10 \
  "https://api.typesafe.ai/v1/systemone" \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \

이 예시는 공개 규격에 맞춰 작성했으며 실제 API 호출로 결과를 측정하지 않았습니다. 버전은 비교 실험을 위해 jev-1.13.0으로 고정했습니다. jev-latest는 새 안정 버전이 나오면 대상이 바뀝니다. TypeSafe · 버전과 별칭 ↗

응답에서 읽을 값

  • 업무 유형은 answers.route.choice, 분류의 확신 지표는 answers.route.confidence입니다.
  • 긴급성은 answers.urgency.score이며, 이 실습의 범위는 0~2입니다.
  • 변경 요청 여부는 answers.change_requested.noul의 0~1 값으로 읽습니다.

이 문장의 기대 분류는 delivery입니다. 실제 응답이 다른지 확인하고, 틀린 문장과 질문 버전을 함께 기록하는 것이 실습의 핵심입니다.

  • Clef·Clef-Flash Workers AI의 계정별 호출 경로와 인증을 사용하고, 모델 선택값을 맞춥니다. 요청당 질문은 최대 64개입니다. 공식 호출 예제 ↗
  • Perplexity Decider https://api.perplexity.ai/v1/decisions와 Perplexity 키, 해당 모델 ID를 사용합니다. 공식 API는 세 질문 유형을 지원하며 최대 128개 질문을 받습니다. 공식 시작 예제 ↗

7. 판단 이후의 처리를 설계하기

confidence는 분포에서 계산한 지표입니다

Jev의 Choice와 Score에서 confidence는 답의 확률 분포가 얼마나 집중되어 있는지 계산한 0~1 값입니다. 선택된 항목의 확률과도 같은 값은 아닙니다. TypeSafe · confidence ↗

confidence = 0.9를 ‘우리 업무에서 정답률 90%’로 읽어서는 안 됩니다. 모델은 높은 확신으로도 틀릴 수 있습니다. 실제 정답률은 우리가 모은 평가 데이터로 확인해야 합니다.

모델을 바꿀 때도 같은 숫자의 임계값을 그대로 옮기지 않습니다. 반환된 confidence의 계산법과 확률 보정 상태를 확인하고, 같은 오분류 허용 수준에서 자동 처리할 수 있는 비율로 비교합니다. 형식 호환과 판단 품질의 호환은 각각 검증할 항목입니다.

예를 들어 ‘분류가 delivery이고, confidence가 0.9 이상이며, 변경 요청의 noul이 0.2 이하일 때 조회 후보로 표시’라는 정책을 실험할 수 있습니다. 0.9와 0.2는 실습용 가설 값입니다. 공식 권장 운영 기준이 아니며, 실제 데이터와 오분류의 영향을 보고 조정해야 합니다. TypeSafe · 확신에 따른 분기 ↗

배송 조회를 실제 API에 연결할 때는 로그인, 주문 소유권, 주문번호, 읽기 전용 API 여부를 코드에서 별도로 확인합니다. 의도 분류가 권한 검증을 대신할 수는 없습니다.

응답 누락을 임의로 noul = 0으로 바꾸면 실패가 ‘변경 요청 없음’으로 둔갑합니다. 판단 실패와 ‘아니요’는 서로 다른 상태로 유지하세요. 재시도에도 횟수와 전체 시간의 한도를 두어야 합니다.

8. 커머스 업무에 적용할 세 가지 흐름

문의의 처리 경로 선택

단순 배송 조회는 업무 API로, 설명이 필요한 상품 문의는 전문 문맥을 가진 생성 모델로, 복합 요청이나 판단이 어려운 문의는 사람에게 전달하는 흐름입니다. 공식 Intent routing 예제도 분류 이후 코드·전문 모델·사람으로 처리 경로를 나눕니다. TypeSafe · Intent routing ↗

상품기술서의 검토 우선순위

상품 설명과 옵션 정보가 서로 모순되는지, 추가 확인이 필요한 모호한 표현이 있는지 각각 묻습니다. 필수 필드 누락, 허용 코드, 구성 수량은 기존 검증이 처리합니다. Jev는 담당자가 먼저 볼 문서를 선별하는 역할로 시작할 수 있습니다.

‘상품기술서를 승인해도 되는가?’처럼 넓게 묻기보다, 문제가 되는 의미 조건을 분리하고 검토 대상을 모아 보세요. 모델 판단을 최종 승인 조건으로 사용할지는 별도의 평가가 필요합니다.

검색 후보의 재정렬

‘책상 위에 놓을 작고 조용한 USB 선풍기’를 찾는다면 기존 검색이 후보를 모으고, Jev가 요청과 후보 설명의 적합도를 평가하도록 제안합니다. 가격·재고·전원 규격처럼 구조화된 조건은 코드와 업무 API에서 확인합니다.

공식 재정렬 예제는 법률 문서를 먼저 검색으로 좁히고, 각 후보를 평가해 다시 정렬합니다. 그 결과를 한국어 상품 검색의 성능으로 옮겨 해석할 수는 없으므로, 우리 후보·질의로 비교 실험해야 합니다. TypeSafe · 재정렬 예제 ↗

Codex나 Claude Code에는 프로그램 구현을 맡기고, 완성된 프로그램이 실행 중 Jev를 호출하도록 구성합니다. TypeSafe도 Jev를 코딩 에이전트의 기반 모델로 교체하는 방식과, 에이전트로 Jev 연동 코드를 작성하는 방식을 구분합니다. TypeSafe · 코딩 에이전트와 사용하기 ↗

Java·Spring이라면 HTTP 호출을 감싼 작은 서비스로 시작하거나, 앞서 소개한 커뮤니티 클라이언트를 검토할 수 있습니다. 처음부터 에이전트 전체 구조를 바꿀 필요는 없습니다.

현재 Java·Spring 프로젝트에 고객 문의 분류 실험을 추가해 주세요.

가상 문의로 업무 유형, 긴급성, 주문 변경 요청 여부를 판단합니다.
TypeSafe 공식 HTTP API 규격을 확인하고 jev-1.13.0을 사용하세요.
질문 정의와 임계값은 별도 설정으로 관리해 주세요.

첫 버전은 결과 조회 화면만 제공합니다.
주문 변경과 고객 발송 API는 연결하지 않습니다.
오류·타임아웃·응답 누락은 판단 실패 상태로 구분하고
사람 검토 또는 기존 처리로 전환해 주세요.

공급자별 호출을 분리해 같은 질문으로 대체 모델을 비교할 수 있게 하세요.
모델 ID와 버전, 질문 버전, 판단 결과, 처리시간을 기록하세요.
API 키는 서버에서 관리하고 키와 개인정보는 로그에 남기지 마세요.
외부 호출 없는 테스트와 실제 API 평가를 분리해 주세요.

결과 화면에는 선택값만 표시하기보다 질문 기준, 확률 분포, 검토 상태를 함께 보여 주세요. 담당자가 오분류 이유를 찾고 기준을 수정할 수 있어야 실험이 이어집니다.

실제 문의를 외부 API로 보내기 전에는 조직의 데이터 전송 정책을 확인하고 필요한 정보만 전달합니다. 가상 문의로 동작을 먼저 확인하면 데이터 준비와 연동 구현을 나누어 진행할 수 있습니다.

10. 한국어로 틀리기 쉬운 문장을 모으기

첫 평가에서는 부정, 정정, 생략, 복합 요청을 따로 모아 보겠습니다. 아래 기대값은 모델의 측정 결과가 아니라 우리가 먼저 정해 둘 실습용 정답 기준입니다.

처음 50~100건은 분류 기준과 실패 유형을 발견하는 데 사용할 수 있습니다. 이 작은 표본으로 운영 안전성을 입증했다고 보기는 어렵습니다. 질문을 수정할 때 사용한 문장과 최종 평가 문장도 나누어야 합니다.

같은 입력으로 세 가지 방식을 비교합니다

기존 키워드·정규식 규칙, 생성형 모델의 구조화된 분류, 디시전 모델과 검토 전환을 결합한 방식을 비교해 보세요. 세 번째 방식 안에서 Jev와 후보 모델 두세 개를 같은 문의·질문·정답 기준으로 평가합니다. 전체 정답률에 더해 다음을 함께 기록합니다.

  • 자동 분기된 건의 정확도 자동으로 보낸 것 중 실제로 맞은 비율
  • 중요 요청의 누락률 변경 요청이나 복합 요청을 놓친 비율
  • 자동 분기와 검토 비율 처리 부담을 얼마나 줄이고, 얼마나 다시 확인했는지
  • 처리시간과 재작업 입력 길이·질문 수·동시 요청 수를 맞춘 중앙값과 p95, API 호출부터 사람의 수정까지 걸린 시간
  • 확률의 신뢰도 예측 확률 구간별 실제 정답률과 높은 확신으로 틀린 사례

항상 사람에게 보내는 방식은 분류기의 효용을 보여 주기 어렵습니다. 자동 분기 비율만 높이는 방식도 오분류를 가릴 수 있습니다. 정확도와 처리 범위를 함께 비교해야 합니다.

질문 문구, 선택지, 모델 버전이 바뀌면 같은 평가를 다시 실행합니다. 특히 ‘Jev 호환’ API로 옮길 때는 반환 형식뿐 아니라 확률·confidence의 의미와 우리 데이터의 성능도 확인해야 합니다.

11. 한 건을 정확히 끝내는 비용

2026년 10월 2일 공식 문서에서 확인한 입력 요금입니다. 같은 수의 토큰을 가정한 비교이며, 실제 요청에서는 모델별 토크나이저와 이미지 처리에 따라 과금 입력량이 달라질 수 있습니다.

가격과 제공 조건은 도입 시 다시 확인하세요. 공개 가중치를 직접 운영한다면 GPU·메모리·서빙과 운영 비용을 따로 계산해야 합니다.

Jev에서 호출당 과금 입력이 2,000토큰이고 1만 번 호출한다고 가정하면 다음과 같습니다.

2,000토큰 × 10,000회 = 20,000,000토큰
20,000,000 ÷ 1,000,000 × $0.042 = $0.84

가정에 따른 입력 요금 계산입니다. 실제 한국어 요청의 토큰 수를 측정한 값이나 서비스 전체 비용은 아닙니다.

검토 전환이나 후속 모델 호출이 자주 발생하면 전체 비용은 달라집니다. 속도도 네트워크, 업무 API, 재처리 시간을 포함해 봐야 합니다. 작은 판단을 분리한 뒤 사람의 재작업까지 줄었는지가 도입의 기준입니다.

작은 판단 하나를 우리 업무로 확인하기

헬로우 휴먼의 첫 실험은 고객 문의 분류기 정도면 충분합니다. 가상 한국어 문의를 모으고, 기대 정답과 검토 기준을 합의한 뒤, 세 가지 처리 방식을 같은 입력으로 비교합니다. Jev를 기준으로 호스팅 API 후보를 하나 더 붙이거나, 로컬 운영이 필요하다면 Strands Decider 같은 작은 공개 모델을 추가해 보세요.

결과물이 쓸 만하면 검색 후보 재정렬이나 상품기술서 검토 순서로 범위를 넓힐 수 있습니다. 그때도 의미 판단, 사실 확인, 실제 실행의 담당을 명확히 나눕니다.

반복되는 선택은 모델이 돕고,
실행 조건과 완료 기준은 우리가 정합니다.

에이전트가 오래 일할수록 단계마다 무엇을 선택했고 왜 멈췄는지 확인할 수 있어야 합니다. Jev와 새로운 디시전 모델들의 활용 가치는 이 작은 판단들을 코드가 다룰 수 있는 형태로 연결하는 데 있습니다. 선택 기준은 우리 데이터에서의 오분류, 검토 부담, 전체 처리시간과 비용입니다.
