쇼핑몰 고객 채널에
WebMCP 적용하기

“3만 원 이하 텀블러를 찾아줘.” 고객이 검색 버튼을 눌렀을 때와 에이전트가 이 부탁을 받았을 때, 같은 상품이 나와야 합니다. 상품 세 개로 이 흐름을 만든 뒤 옵션 재고와 내 주문 배송 조회에 적용해 봅니다.

2026년 11월 21일상품 탐색 · 마이페이지
가이드 목차 첫 도구 고르기 텀블러 검색 실습 쇼핑몰 검색에 연결 재고와 내 주문 조회 장바구니와 결제 확인 파일럿 통과 기준

첫 도구는 상품 목록에 둡니다

텀블러를 찾는 고객은 상품명과 예산을 알고 있습니다. 쇼핑몰은 어떤 상품을 판매 중인지, 현재 표시 가격이 얼마인지 알고 있습니다. WebMCP를 쓰면 열린 상품 목록 페이지가 shop_search_products라는 도구를 등록해 둘을 연결할 수 있습니다. 에이전트가 검색어와 최대 가격을 건네면 페이지가 기존 검색 함수를 실행하고 결과를 돌려줍니다.

검색은 비회원도 할 수 있고 정답을 화면에서 바로 확인할 수 있습니다. 첫 실습은 상품명에 ‘텀블러’가 들어가고 원화 표시 가격이 30,000원 이하인 상품을 찾는 일로 정합니다. 실제 서비스에서는 회원가·옵션 추가금·배송비 중 무엇이 이 가격에 포함되는지 기존 가격 필터의 기준을 따릅니다.

2026년 11월 21일 기준 WebMCP는 커뮤니티 그룹 초안 단계이며 Chrome은 로컬 실험 플래그와 오리진 트라이얼을 안내합니다. 도구를 등록한 탭을 열고, 그 도구를 발견하고 호출할 수 있는 브라우저나 확장 프로그램을 연결해야 자연어 요청이 실행됩니다. 탭을 닫은 뒤에도 이어지는 입고 알림은 서버가 담당합니다. WebMCP 명세 초안 ↗ · Chrome 실험 환경 ↗ · 페이지 도구와 서버 MCP의 실행 범위 ↗

검색창과 도구에서 같은 텀블러 찾기

상품 검색 실습 열기 →   실습 HTML 내려받기

실습 파일에는 머그컵 15,000원, 텀블러 500ml 29,000원, 텀블러 900ml 42,000원이 들어 있습니다. 검색창에 텀블러와 30000을 넣고 검색하세요. 상품 번호 P200 한 건이 기준 답입니다. 최대 가격을 29,000원으로 낮춰도 그 상품이 남고, 28,999원으로 바꾸면 결과가 비어야 합니다.

같은 검색을 WebMCP로 실행하기

  1. 개발용 Chrome 프로필에서 chrome://flags/#enable-webmcp-testing을 Enabled로 바꾸고 브라우저를 다시 시작합니다.
  2. HTTPS로 제공되는 실습 페이지를 엽니다. 내려받았다면 파일을 놓은 폴더에서 python -m http.server 8000 --bind 127.0.0.1을 실행하고 http://127.0.0.1:8000/product-search.html을 엽니다. 페이지에 ‘도구 shop_search_products를 등록했습니다’가 표시되는지 확인합니다.
  3. 그 탭의 개발자 도구에서 Application → WebMCP를 열고 shop_search_products를 선택합니다. query에 텀블러, maxPrice에 숫자 30000을 넣고 Run tool을 누릅니다. 이 수동 호출에는 모델이나 API 키가 필요 없습니다. Chrome DevTools 수동 실행 안내 ↗

실습 탭의 Console에서도 같은 호출을 실행할 수 있습니다. 아래 코드는 등록 목록에서 도구를 찾아 입력 객체를 전달하고, 반환된 JSON 문자열을 읽습니다.

const mc = document.modelContext;
const tools = await mc.getTools();
const search = tools.find(tool => tool.name === "shop_search_products");
const raw = await mc.executeTool(search, { query: "텀블러", maxPrice: 30000 });
console.log(JSON.parse(raw));
{
  "ok": true,
  "currency": "KRW",
  "items": [{ "id": "P200", "name": "텀블러 500ml", "price": 29000 }]
}

도구가 보이지 않으면 실습 탭에서 window.isSecureContext가 true인지, typeof document.modelContext?.registerTool이 "function"인지 확인하세요. 직접 호출하려면 getTools와 executeTool도 함수여야 합니다. 지원하지 않는 브라우저에서는 일반 검색창으로 같은 과제를 마칠 수 있습니다. WebMCP 초안의 ModelContext 인터페이스 ↗

자연어 요청도 같은 조건을 전달하는지 보기

실습 탭에서 Chrome이 소개하는 Model Context Tool Inspector 확장을 열고 도구 목록을 확인합니다. 확장의 Gemini 연결 설정에 테스트용 API 키와 모델을 지정한 뒤 “3만 원 이하 텀블러를 찾아줘”라고 요청하세요. 호출 기록에서 도구 이름과 maxPrice: 30000을 먼저 보고, 답변과 화면이 모두 P200을 가리키는지 대조합니다. 수동 호출이 통과했는데 이 단계에서만 42,000원 상품이 나오면, 기록을 열어 모델이 가격 상한을 빠뜨렸는지부터 볼 수 있습니다. Model Context Tool Inspector 확장 ↗

기존 검색 버튼이 쓰는 함수에 연결하기

실습 파일에서 검색 버튼과 도구의 execute는 모두 searchAndDisplay를 호출합니다. 이 함수는 입력을 검증하고 상품을 고른 뒤 검색 조건과 결과를 화면에 표시하고, 같은 상품 목록을 호출자에게 돌려줍니다. 아래는 도구를 등록하는 부분입니다.

await document.modelContext.registerTool({
  name: "shop_search_products",
  description: "상품명과 최대 가격(원, 상한 포함)으로 상품을 조회합니다.",
  inputSchema: {
    type: "object",
    properties: {
      query: { type: "string", minLength: 1, maxLength: 80 },
      maxPrice: { type: "integer", minimum: 0 }
    },
    required: ["query"],
    additionalProperties: false
  },
  annotations: { readOnlyHint: true },
  execute: searchAndDisplay
});

실제 상품 목록에 붙일 때는 실습 배열을 기존 검색 서비스로 교체합니다. 버튼과 도구가 같은 인증 클라이언트, 가격 필터, 정렬, 페이지 크기를 쓰게 하세요. 입력 스키마는 에이전트가 인자를 고르는 데 쓰입니다. 실행 함수와 서버에서도 공백 검색어, 음수 가격, 허용되지 않은 필드를 검사합니다. 결과에는 고객에게 보이는 상품 ID·이름·표시 가격·통화·상세 링크를 담습니다. 정상 조회에서 결과가 없으면 빈 배열, 조회 자체가 실패하면 오류를 반환해야 에이전트가 둘을 구별할 수 있습니다. 도구 입력과 화면 갱신 권장사항 ↗

React·Vue처럼 같은 탭에서 화면이 바뀌는 쇼핑몰은 상품 목록이 마운트될 때만 도구를 등록합니다. registerTool(tool, { signal: registration.signal })에 AbortController의 신호를 넘기고 화면을 떠날 때 registration.abort()로 해제하세요. 진행 중인 검색에는 별도 처리가 필요합니다. execute(input, { signal })의 취소 신호와 화면 수명 신호를 네트워크 요청까지 전달하고, 화면·계정·검색 조건이 여전히 일치할 때만 응답을 표시합니다. Chrome의 등록·실행 수명 주기 ↗

이미 GET 검색 폼이 있다면

고객이 검색어를 제출하면 결과 페이지로 이동하는 쇼핑몰은 Chrome의 선언형 방식도 시험할 수 있습니다. 기존 form에 toolname과 tooldescription을 붙이고, 검색 입력의 name은 서버가 받던 이름을 유지합니다. 아래의 /products는 쇼핑몰의 검색 결과 경로로 바꾸세요. 이 예제는 에이전트가 검색어를 채우고 고객이 검색 버튼을 누르면 제출됩니다. Chrome의 폼 등록과 제출 동작 ↗

<form action="/products" method="get" toolname="shop_find_by_name"
      tooldescription="상품명으로 검색 결과 페이지를 엽니다.">
  <label>상품명 <input name="query" required maxlength="80"></label>
  <button type="submit">검색</button>
</form>

옵션 재고와 내 주문 배송 상태 읽기

“500ml 텀블러 파란색도 살 수 있어?”라는 질문에 답하려면 상품 전체의 재고로는 부족합니다. “내 텀블러는 언제 와?”라는 질문에는 현재 로그인한 고객의 주문과 배송 정보를 연결해야 합니다. 두 조회 모두 기존 화면에 표시하는 값으로 정답을 만들 수 있습니다.

화면과 도구 예시받을 값돌려줄 값
상품 상세
shop_get_availability		상품과 선택한 옵션의 식별자. 색상이나 용량이 모호하면 고객에게 선택을 요청합니다.그 옵션의 판매 가능 여부와 확인 시각. 품절과 재고 조회 실패를 구분합니다.
마이페이지
shop_get_my_order_status		고객이 자기 주문 목록에서 선택한 주문 번호. 서버가 현재 세션에서 고객을 식별합니다.주문 상태, 배송 단계, 마지막 갱신 시각. 도착 예정일은 배송 데이터에 있을 때만 제공합니다.

주문 API는 요청마다 로그인 상태와 해당 주문의 소유자를 확인합니다. 도구 입력에서 고객 ID를 받으면 에이전트가 다른 사람의 ID도 넣을 수 있습니다. 세션 만료 시에는 LOGIN_REQUIRED를 돌려주고 기존 로그인 화면으로 안내합니다. 다른 고객의 주문 번호와 존재하지 않는 번호에는 똑같이 “주문을 찾을 수 없습니다”라고 응답해 주문의 존재 여부도 드러내지 않습니다.

배송 단계에 답하려면 ‘배송 중’과 갱신 시각이면 충분합니다. 수령인 이름·전체 주소·전화번호·배송 메모는 도구 결과와 모델 호출 로그에서 제외합니다. 로그아웃하거나 계정을 전환하면 이전 주문 결과를 화면에서 지우고, 이전 세션의 응답이 뒤늦게 와도 표시하지 않습니다. 외부 모델을 연결한 첫 검증에는 가상 주문을 사용하세요. WebMCP 도구 보안 지침 ↗

“하나 담아줘”에서 고객이 확인할 값

재고 조회가 맞으면 다음 후보는 장바구니입니다. “파란색 하나 담아줘”라는 요청에는 상품과 옵션, 수량이 필요합니다. 기존 장바구니에 같은 옵션이 한 개 있다면 ‘한 개 추가, 변경 후 두 개’라고 보여줘야 고객이 결과를 예상할 수 있습니다.

  1. 변경안 만들기. 선택한 옵션, 현재 수량과 변경 후 수량, 적용 단가와 예상 금액을 보여줍니다. 이 단계에서는 장바구니 수량을 바꾸지 않습니다.
  2. 장바구니 반영. 고객이 화면에서 변경안을 확인하면 서버가 세션·가격·재고를 다시 확인하고 반영합니다. 확인한 뒤 가격이 바뀌었다면 새 금액을 보여주고 다시 선택하게 합니다.
  3. 응답을 놓쳤을 때. 같은 변경안의 재시도에는 같은 멱등 키를 씁니다. 서버가 처리 결과를 보관하면 응답이 끊겨도 같은 요청으로 수량이 또 늘지 않습니다. 화면에서는 처리 상태나 최신 장바구니를 조회합니다.

결제는 고객이 기존 주문서에서 배송비·할인·최종 결제액을 보고 결제 수단을 확인한 뒤 확정하는 별도 단계로 둡니다. 도구가 보내는 confirmed: true는 에이전트도 만들 수 있습니다. 서버에서 고객이 실제 확인한 장바구니와 그때의 금액을 대조하세요. 브라우저에서 호출을 중단한 경우에도 서버가 이미 반영한 수량이나 결제는 처리 결과를 조회해야 알 수 있습니다.

같은 고객 과제로 파일럿 판정하기

테스트 상품과 계정 두 개를 준비합니다. 같은 계정·옵션·가격 시점에서 먼저 고객이 화면으로 얻은 답을 적고, 그다음 같은 요청을 에이전트에 건넵니다. 아래는 고객 채널에서 바로 써볼 수 있는 통과 기준입니다.

시험할 일통과 기준
3만 원 이하 텀블러 검색검색창·직접 호출·자연어 호출 모두 P200 한 건. 29,000원 상한에도 포함되고 28,999원 상한에는 0건입니다.
빈 검색어·음수 가격입력 오류를 안내합니다. 상품이 없는 정상 조회는 성공과 빈 목록을 반환합니다.
품절 옵션 확인같은 상품의 다른 색상이 판매 중이어도 선택한 품절 옵션은 구매 불가로 표시합니다.
본인 주문·다른 고객 주문·로그아웃본인 주문은 마이페이지와 배송 단계가 같습니다. 다른 계정에서는 주문 정보가 보이지 않고 세션 만료 시 재로그인을 안내합니다.
화면 이동·미지원 브라우저이전 화면의 도구가 사라지고 늦은 응답이 새 화면을 덮지 않습니다. 도구를 끈 상태에서도 검색과 주문 조회를 마칠 수 있습니다.
장바구니 변경 재시도같은 확인 건의 응답을 놓쳐 재시도해도 최종 수량은 한 번만 증가합니다.

기록에는 브라우저·에이전트·모델 버전, 선택한 도구와 인자, 기대한 상품 번호나 배송 단계, 소요 시간과 재호출 수를 남깁니다. 성공률은 ‘정답과 일치한 과제 수 ÷ 실행한 과제 수’로 계산하세요. 다른 계정의 주문이 보인 경우는 평균 수치와 관계없이 주문 도구 확대를 멈추고 서버의 소유권 검사를 먼저 고칩니다.

이 실습에서 확인한 범위는 데스크톱 Chrome 158의 검색창과 WebMCP 직접 호출입니다. 가격 상한 포함·빈 결과·입력 오류를 확인했고, 기능을 꺼도 검색창이 동작했습니다. 자연어 도구 선택과 주문 소유권 검사는 각 쇼핑몰의 테스트 모델과 계정으로 확인할 항목입니다.
