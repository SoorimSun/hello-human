Java4Shell(Java2Shell)
긴급 대응 가이드

서비스가 쓰는 Java부터 확인하세요. 패치가 늦어지면 JVM을 재시작할 수 있는지에 따라 지금 할 일이 달라집니다.

어떤 Java 서비스가 영향을 받을까?

Java가 Base64 문자열을 원래 바이트로 되돌릴 때, 일부 CPU에서 쓰는 고속 처리 코드가 메모리의 허용 범위를 벗어나 쓸 수 있습니다. 서비스가 비정상 종료되거나, 조건이 맞으면 로그인하지 않은 사람이 서비스 계정 권한으로 코드를 실행할 수 있습니다. 발견팀 Calif는 이 취약점을 Java4Shell이라고 이름 붙였습니다. Java2Shell이라는 이름으로 접한 경우에도 공급사 공지에서는 CVE-2026-114938을 찾으면 됩니다. JFrog의 명칭 설명 ↗ · Oracle의 영향 평가 ↗

운영 담당자는 아래 세 가지를 함께 확인합니다. 하나라도 확인할 수 없으면 그 항목을 ‘미확인’으로 남기고, 외부 입력을 받는 서비스부터 패치를 준비합니다.

  • 실행 빌드. OpenJDK 17 계열은 17.0.6부터 해당 코드가 들어갔고 후속 계열에도 포함됐습니다. 같은 ‘Java 17’이라도 공급사와 업데이트 이력에 따라 수정 여부가 다릅니다. Red Hat 보안 공지 ↗
  • CPU와 JVM 설정. 알려진 문제는 x86-64에서 AVX-512 VBMI 명령을 지원하고 JVM이 해당 Base64 최적화를 사용할 때 발생합니다. ARM64에서는 이 경로를 사용하지 않습니다. VM이나 컨테이너가 옮겨지면 실제 노드의 조건을 다시 확인합니다. 캐나다 사이버보안센터 경보 ↗
  • 입력 경로. 외부 요청, 제휴사 파일, 큐 메시지 등이 앱이나 라이브러리를 거쳐 해당 디코더에 도달하는지 살펴봅니다. 메모리 손상은 Java 예외 처리보다 먼저 일어날 수 있습니다. 앱에서 잘못된 입력을 예외로 처리하거나 소스에서 직접 호출을 찾지 못해도 점검을 이어갑니다.

Oracle의 평가는 CVSS 3.1 기준 8.1점(높음), Calif의 평가는 CVSS 4.0 기준 9.2점(치명적)입니다. 두 수치는 평가 주체와 척도가 다릅니다. 개별 서비스의 우선순위에는 실제 빌드와 외부 노출 여부를 반영합니다. Oracle 위험도 표 ↗ · 발견팀의 공지와 권고 ↗

요청을 처리하는 JVM에서 버전과 설정 읽기

서버 한 대에 Java가 여럿일 수 있습니다. 예를 들어 주문 API는 컨테이너에 있는 JDK 17로, 야간 배치는 호스트의 JDK 21로 실행될 수 있습니다. 터미널에서 실행한 java -version은 그 셸에서 선택한 Java의 버전입니다. 서비스별 프로세스 ID(PID)를 찾아 실행 중인 JVM의 공급사와 전체 빌드를 기록하세요.

Linux와 컨테이너

대상 JVM과 같은 실행 환경에서 서비스 계정으로 조회합니다. 아래의 경로와 PID는 예시입니다. 컨테이너에서는 해당 컨테이너 안의 PID를 사용합니다. 호스트의 jcmd -l에 다른 컨테이너의 JVM이 빠질 수 있습니다. Oracle jcmd 사용법 ↗

jdk=/opt/service-jdk
"$jdk/bin/jcmd" -l
jvm_pid=12345
readlink -f "/proc/$jvm_pid/exe"
"$jdk/bin/jcmd" "$jvm_pid" VM.version
"$jdk/bin/jcmd" "$jvm_pid" VM.system_properties |
  grep -E '^(java\.vendor|java\.home|java\.runtime\.version|os\.arch)='
"$jdk/bin/jcmd" "$jvm_pid" VM.flags -all |
  grep -wE 'UseBASE64Intrinsics|UseAVX'

같은 노드에서 uname -m으로 아키텍처를 확인합니다. x86-64 Linux에서는 아래 명령으로 CPU 기능을 조회합니다. 발견팀이 제시한 네 항목이 모두 보여도 패치 여부와 JVM 옵션은 별도로 확인합니다.

grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' |
  grep -xE 'avx512f|avx512bw|avx512vbmi|bmi2'
Windows 서비스와 Tomcat에서 확인하기

서비스 이름을 알면 해당 서비스의 PID부터 찾습니다. 기본 예시의 Tomcat10과 JDK 경로를 실제 값으로 바꾸세요. Windows Tomcat이 서비스 프로세스 안에 jvm.dll을 로드한 구성이라면 프로세스 이름이 java.exe가 아닐 수 있습니다. 별도 Java 자식 프로세스를 띄우는 구성에서는 그 자식 PID를 사용합니다. Tomcat Windows 서비스 문서 ↗

$svc = Get-CimInstance Win32_Service -Filter "Name='Tomcat10'"
$svc | Select-Object Name, State, ProcessId
# 실행 중인 서비스에서 JVM을 담고 있는 프로세스의 PID를 입력합니다.
$javaPid = 12345
$jcmd = 'C:\Java\service-jdk\bin\jcmd.exe'
& $jcmd $javaPid VM.version
& $jcmd $javaPid VM.system_properties |
  Select-String '^(java\.vendor|java\.home|java\.runtime\.version|os\.arch)='
& $jcmd $javaPid VM.flags -all | Select-String '\b(UseBASE64Intrinsics|UseAVX)\b'

제품 내장 JVM, CI 서버와 빌드 에이전트, 다음에 시작할 배치와 대기 서버도 목록에 넣습니다. 진단 도구가 없거나 접근이 제한되면 서비스 기동 로그, 패키지 번호, 이미지 식별값을 수집합니다. 실행 중인 빌드와 연결할 증거가 부족하면 ‘미확인’으로 둡니다.

대표 인스턴스 한 대부터 교체하기

  1. 현재 빌드와 경로, JVM 옵션, 이미지 식별값, 복구할 배포본을 기록합니다. 공급사의 공식 패키지와 체크섬 또는 서명을 확인합니다. JDK가 내장된 상용 제품은 공급사가 지원하는 업데이트를 선택합니다.
  2. 대표 인스턴스를 트래픽에서 빼고 처리 중인 작업을 마칩니다. 서비스가 참조하는 Java 경로나 jvm.dll을 수정 빌드로 바꿉니다. 컨테이너는 최종 실행 이미지를 다시 빌드하고 새 이미지 식별값으로 교체합니다.
  3. 재시작 후 새 프로세스의 빌드를 확인하고 로그인·토큰 발급, 파일 처리와 주문 연계를 정상 데이터로 점검합니다. 오류율·응답시간·CPU 사용률을 변경 전과 비교한 뒤 다음 인스턴스로 넘어갑니다.

복구 때문에 이전 빌드로 돌아간다면 미리 확인한 완화 옵션을 함께 적용합니다. 새 JVM에서 그 값을 확인한 뒤 트래픽을 복귀시키고 상태를 ‘긴급 완화’로 되돌려 기록합니다.

패치가 늦어지면 Base64 최적화 끄기

-XX:-UseBASE64Intrinsics는 Base64 기능을 유지하면서 하드웨어 가속 구현을 끕니다. 다른 AVX-512 최적화를 유지할 수 있어 Red Hat이 먼저 권하는 방법입니다. JDK 파일 교체 없이 적용할 수 있지만 JVM 재시작이 필요합니다. Red Hat 임시 완화 권고 ↗

  1. 같은 바이너리로 시작 옵션을 시험합니다. 아래 명령은 짧게 실행되고 종료되는 별도 JVM을 띄웁니다. 서비스와 같은 배포판·경로에서 정상 종료하는지 확인합니다.
/opt/service-jdk/bin/java -XX:-UseBASE64Intrinsics -version

빌드가 진단 옵션 잠금 해제를 요구하면 -XX:+UnlockDiagnosticVMOptions를 앞에 둔 조합으로 다시 확인합니다. 옵션을 인식하지 못하면 오류를 무시하도록 설정하지 말고 해당 공급사의 대안을 확인합니다. Oracle의 JVM 옵션 설명 ↗

  1. 확인한 옵션을 서비스의 시작 설정에 추가합니다. 기존 메모리·GC·에이전트 옵션을 보존합니다. 실행형 JAR에서는 JVM 옵션을 -jar 앞에 둡니다. 이중화돼 있다면 인스턴스 한 대씩 트래픽에서 빼고 재시작합니다.
  2. 새 JVM에서 최종 값을 읽습니다. 재시작 후 다시 찾은 PID로 아래 명령을 실행합니다. UseBASE64Intrinsics 값이 false일 때 이 완화가 적용된 것으로 기록합니다. 주요 기능과 CPU·응답시간을 확인하고 패치 일정을 남깁니다.
# 재시작 후 확인한 PID로 바꿉니다.
jvm_pid=23456
/opt/service-jdk/bin/jcmd "$jvm_pid" VM.flags -all |
  grep -w UseBASE64Intrinsics

x86-64 전용 대안. 공급사가 지원하는 HotSpot JVM이라면 -XX:UseAVX=2로 AVX-512 사용을 제한할 수도 있습니다. 이 경우 재시작 후 UseAVX의 최종 값이 2 이하인지 확인합니다. Base64 외의 연산 성능도 달라질 수 있습니다. ARM에서 인식하지 못하면 JVM 기동이 실패하므로 혼합 클러스터의 공통 설정에는 넣지 않습니다. 두 옵션 중 하나를 선택합니다. Red Hat의 두 가지 옵션 ↗

서비스를 시작하는 곳에 옵션 넣기

아래에서 실제 시작 방식에 맞는 항목을 펼치세요. app과 myapp은 예시 이름입니다. 작업용 셸에서 환경변수를 바꿔도 이미 실행 중인 서비스에는 전달되지 않습니다.

Linux 시작 스크립트와 systemd 서비스

직접 Java를 실행한다면 서비스 시작 스크립트의 기존 JVM 옵션에 추가합니다. systemd라면 systemctl cat myapp.service에서 ExecStart, EnvironmentFile, 기존 drop-in을 확인합니다. 환경 파일이 JAVA_TOOL_OPTIONS를 관리하면 그 파일의 기존 값에 옵션을 덧붙입니다.

기존 값도 없고 환경 파일이 같은 변수를 지정하지 않을 때는 systemctl edit myapp.service에서 다음 설정을 사용할 수 있습니다. Environment= 안의 변수 참조는 셸처럼 확장되지 않습니다. systemd 환경변수 규칙 ↗

[Service]
Environment="JAVA_TOOL_OPTIONS=-XX:-UseBASE64Intrinsics"

유닛 구성을 다시 읽힌 후 systemctl restart myapp.service로 서비스를 재시작하고 새 JVM을 확인합니다. daemon-reload만 실행하면 기존 프로세스는 계속 동작합니다.

Linux Tomcat과 Windows Tomcat 서비스

Linux. 표준 catalina.sh를 사용한다면 해당 인스턴스의 $CATALINA_BASE/bin/setenv.sh에서 CATALINA_OPTS에 아래 한 줄을 추가합니다. systemd가 Java를 직접 실행하는 구성은 그 유닛의 설정을 사용합니다. Tomcat 시작 환경 문서 ↗

export CATALINA_OPTS="$CATALINA_OPTS -XX:-UseBASE64Intrinsics"

Windows. 예를 들어 Tomcat 10 서비스 이름이 MyTomcat이면 tomcat10w.exe //ES//MyTomcat에서 Java 탭을 엽니다. JVM 모드에서는 ‘Java Options’에 옵션을 한 줄 추가하고 ‘Java Virtual Machine’의 DLL 경로도 기록합니다. 해당 서비스를 재시작한 뒤 새 PID에서 확인합니다. Tomcat 서비스 설정 ↗

Docker Compose

해당 서비스의 environment 또는 실제로 읽는 env_file에 옵션을 반영합니다. 아래 예시는 이미지와 Compose 설정 어디에도 기존 JAVA_TOOL_OPTIONS 값이 없는 경우입니다. 기존 값이 있다면 전체 값을 보존해 추가합니다.

services:
  app:
    environment:
      JAVA_TOOL_OPTIONS: "-XX:-UseBASE64Intrinsics"

이미지 식별값을 확인하고 docker compose up -d --no-deps --force-recreate app으로 컨테이너를 다시 만듭니다. docker compose restart는 변경한 환경변수를 반영하지 않습니다. 새 컨테이너 안에서 실행 중인 JVM을 조회합니다. Docker Compose 재시작 동작 ↗

Kubernetes·OpenShift와 예약 배치

Deployment라면 원본 매니페스트나 Helm 값에서 대상 컨테이너의 spec.template.spec.containers[].env에 옵션을 반영합니다. GitOps로 운영하면 동기화가 참조하는 원본을 수정합니다. ConfigMap을 환경변수로 읽는 기존 Pod는 맵이 바뀌어도 예전 값을 사용하므로 새 Pod로 교체합니다. 디플로이먼트 갱신 ↗ · 컨피그맵 동작 ↗

kubectl -n myapp rollout status deployment/app
kubectl -n myapp get pods -l app=myapp -o wide

네임스페이스·이름·라벨은 실제 값으로 바꿉니다. OpenShift에서는 oc로 같은 Deployment를 조회할 수 있습니다. 이전 복제본 종료, 새 Pod별 JVM 옵션, 다음에 실행될 CronJob의 작업 템플릿까지 확인합니다.

Jenkins·Bamboo와 빌드 에이전트

재시작 전까지 외부 입력 줄이기

재시작 시간을 확보하기 전에는 어떤 데이터를 어디에서 차단했는지 기록합니다. 아래 조치는 노출을 줄입니다. 메모리 손상 코드가 포함된 JVM은 계속 실행되므로 패치나 JVM 완화 일정을 별도로 정합니다.

  • 접근 범위를 좁힙니다. 관리·협력사·CI 서비스는 허용된 접속 원천으로 제한합니다. 정상 업무는 계속 허용되는지, 제한한 원천에서는 백엔드까지 직접 접근할 수 없는지 확인합니다.
  • 디코딩 전에 처리를 멈춥니다. 업무 담당자와 협의해 외부 파일 업로드, 연계 응답 처리, 큐 소비를 일시 중지할 수 있습니다. 신규 접속을 막아도 이미 쌓인 메시지와 파일은 남습니다. 재개 전에 처리할 데이터와 소비하는 JVM을 함께 확인합니다.
  • 통제하기 어려우면 격리합니다. WAF 규칙이나 요청 크기 제한만 적용했다면 그 범위만 기록합니다. 입력을 통제할 수 없는 인스턴스는 트래픽에서 제외하거나 서비스를 일시 중지하고 패치 시간을 확보합니다.

JVM이 반복 종료되거나 설명하기 어려운 자식 프로세스·외부 연결이 보이면, 영향 시간대와 서비스·프록시 로그, JVM 오류 기록을 보존하고 사고 대응 담당자에게 전달합니다. 오류 한 건으로 침해를 확정할 수 없고, 패치 결과만으로 과거 침해 여부를 판단할 수도 없습니다.

어떤 증거가 있어야 패치 완료일까?

재시작 뒤 서비스의 새 PID나 Pod를 찾아 VM.version과 VM.flags -all을 다시 읽습니다. 공급사가 OS 패키지에 수정을 반영한 경우에는 실행 파일을 제공한 패키지의 릴리스 번호까지 대조합니다. 아래 기준으로 JVM 하나당 한 줄을 남기면 교대 근무자도 남은 일을 알 수 있습니다.

기록할 상태필요한 증거와 다음 조치
패치 완료새 JVM의 공급사·전체 빌드 또는 대응 패키지가 이 CVE를 수정한 릴리스와 일치하고 주요 기능이 정상입니다. 수정된 JVM에서는 UseBASE64Intrinsics=true여도 정상일 수 있습니다.
긴급 완화 적용미패치 JVM의 실제 옵션이 UseBASE64Intrinsics=false 또는 x86-64에서 UseAVX 2 이하입니다. 패치 담당자와 목표 일시를 남깁니다.
현재 배치에서 해당 경로 비활성실제 노드의 아키텍처·CPU 기능으로 해당 경로를 사용할 수 없음을 확인했습니다. 자동 확장이나 노드 변경 시 다시 확인합니다.
노출 축소허용·차단 경로와 중단한 작업을 확인했습니다. 미패치 JVM과 남은 입력 경로, 재시작 예정 시각을 기록합니다.
미확인버전 조회 실패, 불명확한 패키지 매핑 등 빠진 증거와 이를 확인할 담당자를 기록합니다.

전체 서비스 종료 기준. 모든 복제본·에이전트의 증거를 모으고 자동 확장 이미지, 배치·재해 복구 템플릿, 롤백 구성을 확인합니다. 이전 런타임을 다시 띄울 경로가 남으면 후속 작업으로 기록합니다. 임시 옵션을 해제할 때도 수정 빌드에서 기능과 성능을 비교한 뒤 순차 재시작합니다.

가상 기록 예시 · 주문 API 복제본 3개 중 2개는 Oracle JDK 17.0.21.1+4로 실행 중이며 주문 조회를 확인했다. 나머지 1개는 이전 빌드에서 Base64 최적화만 껐다. 현재 상태는 ‘패치 2개, 긴급 완화 1개’다.
