맡길 일, 바꿔도 되는 범위, 완료를 판단할 근거입니다.

이 세 가지가 분명해야 설명을 거듭 보충하거나 결과물을 다시 고치는 일을 줄일 수 있습니다. 에이전트가 코드를 작성하는 동안 사람은 결과가 업무 목적에 맞는지, 변경이 다른 기능에 어떤 영향을 줄지 살핍니다.

쿠폰 표시 개선을 예로 들어 작업 지시, 구현과 검증, 병렬 작업, 지식 재사용을 차례로 살펴봅니다. 특정 도구나 기술 스택을 전제로 하지 않으며, 작업 양식은 팀에서 사용하는 정책과 개발 환경에 맞춰 바꿔 쓸 수 있습니다.

바로 적용하려면 작업 지시문과 완료 보고 양식부터 보세요. 구체적인 실패 상황은 쿠폰 표시 예시, 팀의 검토 절차는 코드리뷰에서 배포까지 가이드로 이어집니다.

01. 작업을 맡기기 전에
팀의 기준을 정합니다

에이전트와 일할 때도 팀원끼리 무엇을 맡기고 어떻게 확인할지 맞춰야 합니다. 작업마다 설명을 처음부터 반복하지 않도록, 아래 다섯 가지를 팀의 공통 기준으로 정해 보세요.

작은 화면에서는 표를 좌우로 밀어 나머지 열을 확인할 수 있습니다.

처음에는 작은 작업 한 건에 이 기준을 적용합니다. 설명이 부족했던 곳과 검증에서 빠진 조건을 보완한 뒤 다음 작업에도 사용하세요. 동시 실행 수와 병합 권한은 팀의 검토 역량과 변경 영향에 맞춰 조정합니다.

02. 탐색과 구현을
다르게 맡깁니다

아직 무엇을 만들지 모를 때와 만들 것이 정해졌을 때는 협업 방식이 달라야 합니다. “상품 검색을 개선해 줘”에는 검색 결과의 정확도, 응답 속도, 검색어 입력의 불편처럼 서로 다른 문제가 섞일 수 있습니다.

작업 상태에이전트에 맡길 일사람이 판단할 일
문제와 해법이 모호함관련 코드 조사, 빠진 조건 찾기, 대안과 작은 시제품실제 문제, 사용자 가치, 선택할 방향
범위와 기준이 정해짐구현, 테스트 실행, 문서 수정, 결과 정리기준 충족 여부와 남은 위험
운영 영향이 큼로그 분석, 재현, 변경안과 복구 절차 준비권한·데이터·배포에 영향을 주는 결정

문제가 모호하면 조사를 먼저 요청하세요

방향을 고른 뒤에는 그 결정을 작업 지시문에 남깁니다. 작은 문구 수정까지 긴 설계 과정을 거칠 필요는 없습니다. 아직 확인하지 않은 업무상의 전제가 많을수록 탐색에 시간을 더 씁니다.

04. 작은 기능 하나를
끝까지 진행합니다

예제로 장바구니에서 쿠폰 사용 불가 이유를 표시하는 작업을 맡겨 보겠습니다. 설명을 위한 가상 상황이며, 실제 서비스에 적용할 때는 해당 서비스의 정책과 API 계약을 확인해야 합니다.

쿠폰 사용 가능 여부는 기존 서버 API가 판정하고, 화면은 그 결과를 표시한다고 가정합니다. 쿠폰 적용 API와 최종 할인 계산은 이번에 바꾸지 않습니다. 서버가 현재 장바구니에 대해 사용 가능으로 응답했을 때만 ‘사용 가능’으로 표시합니다. 조회 중이거나 실패했다면 아직 사용 가능 여부를 알 수 없습니다.

[목표]
장바구니에서 쿠폰을 사용할 수 없는 이유를 알 수 있게 한다.

[범위]
쿠폰 상태 표시, 장바구니 변경 뒤 상태 갱신, 관련 테스트.

[완료 조건]
사용 가능, 사용 불가, 조회 중, 조회 실패를 구분한다.
사용 불가이면 서버가 반환한 사유를 표시한다.
장바구니가 바뀌면 현재 장바구니에 맞는 결과를 표시한다.
이전 요청의 늦은 응답이 최신 결과를 덮어쓰지 않는다.

[기존 계약]
쿠폰 사용 가능 여부는 기존 서버 판정을 따른다.
적용 버튼의 활성 조건·적용 요청·할인 계산을 유지한다.

[중단 조건]
기존 API에 필요한 사유가 없거나 정책이 충돌하면,
확인한 응답과 필요한 변경안을 정리해 질문한다.

구현 전에 기대 결과를 정합니다

이 예시에서는 서버의 사용 불가 응답을 받으면 적용 버튼이 비활성화되는 기존 동작을 유지합니다.

상황 또는 준비한 API 응답확인할 결과
사용 가능 응답사용 가능 상태를 표시하고 기존 적용 동작을 유지합니다.
최소 구매금액 미달 응답해당 사유를 표시하고, 적용 버튼은 비활성 상태로 유지합니다.
만료된 쿠폰 응답만료 사유를 보여 줍니다. 화면에서 만료 여부를 다시 판정하지 않습니다.
수량 변경 뒤 사용 불가 응답이전의 사용 가능 표시를 현재 장바구니의 새 결과로 바꿉니다.
조회 실패 또는 시간 초과조회 실패를 알리고 재시도 방법을 안내합니다. 사용 가능이나 사용 불가로 확정하지 않습니다.
이전 요청의 응답이 나중에 도착현재 장바구니의 조회 결과를 유지합니다.
현재 요청 실패 뒤 과거의 사용 가능 응답 도착조회 실패 상태를 유지합니다. 과거 응답으로 사용 가능 표시를 복원하지 않습니다.

화면 테스트에는 상황별로 만든 모의 응답을 사용합니다. 각 조건을 모의 응답으로만 시험했는지, 실제 테스트 환경의 API에도 연결해 확인했는지 구분해 기록합니다. 한 번의 연동 성공이 모든 실패 상황의 검증을 대신하지는 않습니다.

사유 표시를 위해 추가한 화면 상태가 기존 쿠폰 적용 조건을 바꾸지 않게 합니다. 알 수 없는 사유 코드는 합의된 기본 안내로 표시하되 서버의 판정은 유지합니다. 조회 실패 때 쿠폰 적용을 허용할지는 기존 정책을 따르고, 정책이 불분명하면 구현 전에 확인합니다.

응답은 요청을 보낸 장바구니 상태와 연결해서 처리합니다. 다른 기기나 경로에서 바뀐 서버 상태까지 다루려면 API의 버전·동기화 규칙을 별도로 확인해야 합니다.

테스트의 기대값은 확정된 정책과 위 표에서 가져옵니다. 구현 함수로 기대값까지 계산하면 같은 오류가 테스트에도 반영돼 잘못된 결과를 통과시킬 수 있습니다.

05. 완료 여부는
실행 결과로 판단합니다

“수정했습니다”라는 보고만으로는 요청한 동작이 구현됐는지 알 수 없습니다. 다음 세 가지로 나눠 검증하고, 확인한 결과와 남은 항목을 함께 보고합니다.

검증확인할 것쿠폰 표시 예시
요구사항요청한 동작이 구현됐는가?조회 실패와 사용 불가를 구분하는가?
회귀기존 기능이 유지되는가?기존 버튼 활성 조건·클릭·적용 요청·할인 결과가 유지되는가?
통합다른 변경과 합친 최종 상태에서도 동작하는가?다른 장바구니 변경과 합친 뒤 상태 갱신이 유지되는가?

버그 수정이면 변경 전에 문제를 재현하고, 수정 뒤 같은 절차로 다시 확인합니다. 화면을 바꿨다면 실제 화면과 사용자 흐름을 확인합니다. API나 데이터 처리라면 요청·응답·최종 데이터 상태가 증거가 됩니다.

스크린샷은 화면 확인에 유용하지만 서버 처리나 중복 요청의 안전성까지 증명하지는 않습니다. 검증 수단은 변경의 성격에 맞춰 고릅니다.

완료 보고 양식

[검증]

- 통과·실패 결과와 로그 또는 화면 근거

[미검증]

[판단 요청]

다른 에이전트의 리뷰에도 근거를 요구하세요

새 세션이나 별도 에이전트에 요구사항, 변경 전후 코드, 테스트 결과를 주고 검토를 맡길 수 있습니다. 검토 대상과 판단 기준을 명확히 전달하고, 어떤 버전의 코드를 검토했는지 남깁니다. 이후 코드가 수정되면 영향을 받는 부분을 다시 검증하고 리뷰합니다.

이 변경을 읽기 전용으로 검토해 줘.

요구사항, 변경 전후 코드, 테스트 결과를 비교해 줘.
발견 사항마다 위치, 발생 조건, 사용자 영향,
재현 방법 또는 코드 근거를 적어 줘.

확인된 결함과 추가 확인이 필요한 항목을 구분해 줘.
중요한 문제가 없으면 없다고 말해 줘.

GitHub는 Copilot 코드 검토가 문제를 놓치거나 존재하지 않는 문제를 지적할 수 있다고 명시합니다. 두 에이전트의 의견이 같아도, 그 판단이 타당한지는 요구사항·코드·실행 결과와 대조해야 합니다. GitHub의 제한 사항 안내 ↗

06. 병렬 실행은
독립된 작업부터 늘립니다

처음에는 구현 한 건을 맡기고, 결과가 나온 뒤 별도 에이전트나 동료에게 검토를 맡겨 보세요. 조사 단계라면 코드 구조 파악과 테스트 사례 수집을 동시에 진행할 수 있습니다. 여러 구현 작업을 병렬로 맡길 때는 작업 사이의 의존성을 먼저 살핍니다.

조합진행 방법
서로 다른 모듈의 독립적인 수정작업 폴더와 브랜치를 나눠 병렬 진행합니다.
같은 API 계약을 바꾸는 서버와 화면계약을 먼저 정한 뒤 역할을 나눕니다.
같은 공통 파일을 여러 에이전트가 수정편집 담당을 정하거나 순서대로 처리합니다.
구현과 해당 구현의 최종 리뷰검토할 변경 상태를 확정한 뒤 리뷰를 시작합니다.

코드 작업 공간과 실행 자원을 함께 살핍니다

Git의 worktree를 쓰면 같은 저장소의 여러 브랜치를 별도 작업 디렉터리에서 다룰 수 있습니다. 아래는 같은 기준 커밋에서 두 작업 공간을 만드는 예입니다. 아직 커밋하지 않은 변경사항은 새 작업 공간에 반영되지 않습니다. 예시의 브랜치·폴더 이름은 사용하지 않는 이름으로 바꾸세요. Git 공식 문서 ↗

git status --short
git rev-parse HEAD
git worktree add -b agent/coupon-ui ../work-coupon HEAD
git worktree add -b agent/search-empty ../work-search HEAD
git worktree list

두 명령은 같은 HEAD를 기준으로 실행하는 예입니다. 실행 중 기준 커밋이 바뀔 수 있다면 HEAD 대신 같은 커밋 ID를 명시합니다.

worktree는 실행 환경 전체를 격리하지 않습니다

같은 데이터베이스, 캐시, 큐, 포트, 외부 계정을 사용하면 작업끼리 영향을 줄 수 있습니다. 테스트 데이터와 연결 설정도 분리할지 정하고, 변경을 합친 뒤에는 기능 충돌이 없는지 다시 검증합니다.

동시 구현은 독립된 두 작업 정도로 시작해 보세요. 검토 대기가 쌓이거나 변경을 합친 뒤 수정할 일이 늘면, 동시에 맡기는 작업 수를 줄입니다.

작업이 늘면 진행 상황을 한곳에 모읍니다

조정 역할을 맡은 에이전트가 작업별 담당자·기준 커밋·브랜치, 진행 상태·막힌 이유, 검증 결과와 필요한 결정을 모으게 합니다. 이 정보를 이슈나 작업 문서에 남겨 진행 상황의 기준으로 삼습니다. 채팅의 “완료” 한 줄만으로 작업을 종료하지 않습니다.

후속 작업을 맡길 때는 이전 변경과 검증 기록도 함께 전달합니다. 담당자가 바뀌어도 현재 상태와 다음 할 일을 알 수 있어야 합니다. 관련 없는 오래된 대화는 덜어 냅니다.

07. 병합 권한은
변경의 영향으로 정합니다

“유지보수”나 “성능 개선”이라는 이름만으로 위험을 판단하기 어렵습니다. 재시도 로직을 바꿀 때는 중복 처리 가능성을, 캐시를 바꿀 때는 오래된 결과가 노출될 가능성을 살펴야 합니다. 쿼리 변경도 조회 결과와 실행 비용을 함께 점검해야 합니다.

PR(풀 리퀘스트)은 코드 변경의 검토를 요청하는 절차이고, 병합은 그 변경을 기준 브랜치에 합치는 작업입니다. 아래 표를 바탕으로 팀의 승인 기준을 정해 보세요.

변경 유형에이전트가 진행할 범위사람이 확인할 지점
문서 오탈자·제한된 형식 수정수정과 정해진 검사팀이 정한 간소화된 병합 절차
범위가 정해진 기능·버그 수정재현, 구현, 검증, PR 준비요구사항 충족과 변경 영향
결제·재고·인증·권한·스키마 변경조사, 변경안, 시험 환경 검증설계 결정, 데이터 영향, 병합·배포
운영 데이터 변경·외부 발송실행 계획과 사전 확인 자료권한 있는 담당자의 실행 승인

승인된 범위의 수정과 테스트는 에이전트가 이어서 진행하게 합니다. 업무 정책을 새로 정하거나 변경 범위를 넓혀야 할 때는 담당자에게 결정을 요청하도록 합니다.

반드시 지켜야 할 접근 권한과 병합 조건은 도구 설정과 CI에도 반영합니다. CI는 코드 변경에 맞춰 테스트·빌드 등을 자동 실행하는 체계입니다. Anthropic 공식 문서도 자연어 지침과 테스트·권한 제한·샌드박스·브랜치 보호 같은 통제 장치를 구분합니다. 지침과 강제 장치의 차이 ↗

운영 알림을 받으면 변경안을 준비합니다

  1. 같은 오류를 묶어 중복 작업을 줄입니다.
  2. 허용된 로그와 재현 자료로 원인을 조사합니다.
  3. 격리된 환경에서 수정과 검증을 진행합니다.
  4. 근거가 포함된 PR을 만들고 기존 검토 절차로 넘깁니다.

PR 작성, 병합, 배포는 각각 다른 권한입니다. 자동 병합은 범위, 필수 검사, 복구 방법이 정해진 변경부터 검토합니다.

백그라운드 작업에는 시간·비용·재시도 횟수의 상한을 둡니다. 새로운 단서 없이 같은 실패만 반복되면 현재 상태와 막힌 이유를 남기고 중단하게 합니다. 야간 작업의 결과는 정해진 업무 시간에 검토하면 됩니다.

08. 사용자 여정을 시험하고
검증한 지식을 남깁니다

여러 기능을 이어서 사용해 보세요

기능을 하나씩 시험하면 화면 전환과 상태 변경이 겹칠 때 생기는 문제를 놓칠 수 있습니다. 사용자의 목적과 기기, 네트워크 환경을 정해 실제 사용 순서대로 점검해 보세요. 쿠폰 표시 작업에는 다음 시나리오를 추가할 수 있습니다.

네트워크가 느린 휴대전화에서 쿠폰 목록을 엽니다. 응답을 기다리는 동안 상품 수량을 바꿉니다. 뒤로 갔다가 장바구니로 돌아옵니다. 최종 화면이 현재 장바구니와 맞는지 확인합니다.

각 단계에 기대 상태와 실제 결과를 적습니다. 코드만 읽고 예상했다면 ‘코드 검토’, 브라우저에서 실행했다면 ‘실행 확인’으로 구분합니다. 문제를 찾아낸 시나리오는 회귀 테스트로 남깁니다. 에이전트가 가정한 사용자 행동은 실제 문의나 관찰 내용과 맞는지도 살펴봅니다.

같은 실수가 반복되면
그날 규칙으로 바꿉니다

성공한 절차뿐 아니라 반복한 실수도 다음 작업의 자산이 됩니다. 커머스 개발팀이라면 “같은 원인의 실수가 두 번 나오면 그날 회고에서 규칙이나 스킬로 옮긴다”는 운영 기준을 정해 볼 수 있습니다. 두 번은 도입을 위한 제안입니다. 결제 금액이나 재고처럼 영향이 큰 오류는 첫 발견 때부터 원인을 고치고 재현 사례를 남깁니다.

“다음에는 주의하자”로 끝내지 않고, 언제 적용할 규칙인지, 어떤 동작을 지킬지, 무엇으로 확인할지를 적습니다. 아래는 커머스 개발에서 사용할 수 있는 가상 사례입니다.

반복한 실수남길 규칙스킬에 넣을 검증
쿠폰의 오래된 응답이 현재 상태를 덮어씀응답이 현재 장바구니의 요청에 해당하는지 확인한 뒤 화면에 반영합니다.수량 변경, 응답 순서 역전, 현재 요청 실패를 조합해 확인합니다.
결제 시간 초과를 실패로 단정하고 새 결제를 요청함연결된 결제 API의 상태 조회·재시도 계약을 먼저 확인하고, 기존 중복 결제 방지 규칙을 유지합니다.응답 유실 뒤 재시도하는 상황에서 결제와 주문의 최종 상태를 확인합니다.
부분 취소 때 할인·배송비의 배분 조건을 빠뜨림현재 환불 정책의 계산 순서와 반올림 기준을 확인한 뒤 변경합니다.확정된 정책에서 가져온 기준 금액으로 부분 취소 사례를 검증합니다.

반복되는 설명은 적절한 위치에 둡니다

정보두기 좋은 위치다음 작업에 연결하는 방법
이번 작업의 범위·상태·남은 문제이슈 또는 작업 문서후속 작업 지시문에서 해당 문서를 지정합니다.
매번 필요한 검증 명령·팀 공통 규칙도구가 자동으로 읽는 프로젝트 지침 파일세션 시작 시 적용되는 위치에 두고 실제 로드 여부를 확인합니다.
특정 작업의 절차와 확인 방법재사용 가능한 스킬 또는 실행 가이드시작 지침에 적용 조건과 경로를 적고, 해당 작업 전에 읽도록 합니다.
반드시 강제할 권한과 병합 조건도구 설정과 CI·저장소 정책문서 확인에만 맡기지 않고 실행·병합 단계에서 검사합니다.

AGENTS.md, CLAUDE.md 등의 지원 여부와 적용 범위는 사용하는 도구에서 확인합니다. Anthropic은 상시 지침에 반복 설명할 정보를 담고, 특정 업무에만 필요한 다단계 절차는 스킬이나 범위별 규칙으로 분리하도록 안내합니다. 프로젝트 지침 관리 ↗

저장한 규칙이 다음 세션에서
실제로 읽히게 합니다

회고 문서에 기록만 해 두면 다음 세션에서 빠질 수 있습니다. 핵심 규칙과 필요한 절차를 찾는 방법은 세션 시작 때 자동으로 읽히는 지침에 둡니다. 긴 스킬을 모두 넣기보다 어떤 작업에서 어느 문서를 먼저 읽을지 짧게 연결합니다.

자동 로드 범위는 도구와 시작 디렉터리, 설정에 따라 다릅니다. Claude Code도 상위 지침, 하위 디렉터리 지침, 작업별 스킬을 읽는 시점이 다릅니다. 스킬 파일을 저장하거나 경로를 적었다고 내용 전체가 시작부터 읽히는 것은 아닙니다. 사용하는 도구의 로드 규칙을 확인하고, 필요한 작업에서는 스킬을 명시적으로 호출하거나 문서를 읽도록 지정합니다. 지침이 로드되는 방식 ↗

다음은 프로젝트 시작 지침에 넣을 문장 예시입니다. 문서 경로와 검증 명령은 실제 저장소에 맞게 바꿉니다.

[쿠폰·장바구니 작업을 시작할 때]
먼저 docs/playbooks/coupon-state.md를 읽는다.
현재 API 계약과 적용할 규칙, 실행할 검증을 짧게 정리한 뒤 수정한다.
오래된 응답이 현재 상태를 덮지 않는지 확인한다.
조회 실패를 사용 불가로 바꾸지 않는다.

[작업을 마칠 때]
실제 실행한 검증과 남은 문제를 기록한다.
같은 원인의 실수가 반복됐다면 재현 조건과 수정 근거를 정리하고,
팀이 검토한 규칙·절차와 회귀 테스트에 반영한다.

새 세션에 이전 대화를 넘기지 않은 상태로 같은 종류의 작업을 맡겨 봅니다. 에이전트가 필요한 문서를 읽었는지, 그 규칙을 변경 계획과 검증에 반영했는지 확인합니다. “읽었습니다”라는 답만으로 끝내지 않고 실행 결과까지 봅니다. 빠진다면 파일 위치·적용 조건·호출 방법을 고칩니다.

검증한 절차를 스킬로 다듬습니다

스킬은 에이전트가 다음 작업에서 참고할 절차와 자료를 담은 문서입니다. 이를 저장한다고 모델 자체가 학습되는 것은 아닙니다. 쿠폰 화면 검증 절차는 다음처럼 정리할 수 있습니다.

[적용 대상]
장바구니 쿠폰 상태 표시 변경.

[참조]
현재 API 계약, 승인된 상태별 문구, 테스트 데이터 위치.

[다시 막아야 할 실수]
과거의 사용 가능 응답으로 현재 요청의 실패 상태를 덮지 않는다.

[절차]
사용 가능·사용 불가·조회 중·조회 실패 상태를 확인한다.
장바구니가 바뀌거나 응답이 요청 순서와 다르게 도착할 때를 시험한다.
기존 적용 동작을 회귀 검증한다.

[통과 근거]
실제 실행 결과와 변경 상태를 함께 기록한다.

[재검토 조건]
API 계약이나 화면 상태 정의가 바뀌면 절차를 갱신한다.

[관리]
담당자와 마지막 확인 날짜.

절차에는 실제 파일 위치와 실행 명령을 넣고, 각 단계가 필요한 이유도 남깁니다. 정책이 바뀌면 관련 규칙·스킬·테스트를 함께 갱신합니다. 자연어 규칙을 읽는 것만으로 오류가 막히지는 않으므로, 재현 가능한 결함은 회귀 테스트로도 확인합니다.

당일 회고에서 반복한 실수를 반영하고, 주간 회고에서는 명령 실행·변경 내역·테스트·재시도 기록을 모아 지침의 효과를 살펴봅니다. 사람이 같은 지적을 다시 한 횟수와 같은 원인으로 재작업한 횟수가 줄었는지 확인하세요. 겹치거나 오래된 규칙은 정리하고, 기록에는 필요한 정보만 남기며 비밀값과 고객 정보는 제외합니다.

09. 일주일 동안
작게 시험해 봅니다

처음부터 팀 전체의 개발 방식을 바꾸기보다 되돌리기 쉬운 작업 몇 건으로 운영 방식을 확인해 보세요. 아래 일정은 도입 예시입니다. 앞 단계의 검토가 끝나지 않았다면 날짜에 맞추려고 병렬 작업을 늘리지 않습니다.

시점해 볼 일남길 결과
첫날작은 작업의 완료 조건과 기존 검증 방법 정리작업 지시문
둘째 날에이전트 한 개로 구현과 자체 검증변경 내용과 실행 증거
셋째 날별도 검토 후 부족했던 지시와 검증 보완수정한 지시문과 검토 기록
넷째 날독립된 두 작업을 병렬로 진행대기·충돌·통합 문제 기록
다섯째 날반복한 실수를 규칙·스킬로 옮기고 새 세션에서 적용 확인재사용 절차와 다음 운영 기준

개선 목표에도 측정 조건을 붙이세요

성능이나 품질 개선을 맡길 때는 목표 수치와 함께 측정 환경, 지켜야 할 동작, 중단 조건을 적습니다. 검색 응답 속도를 개선한다면 다음처럼 시작할 수 있습니다.

같은 데이터와 부하 조건에서 현재 응답시간을 먼저 측정해 줘.
병목 근거를 찾고 변경 후보를 비교해 줘.

개선안은 검색 결과의 정확성과 기존 접근 권한을 유지해야 한다.
응답시간뿐 아니라 오류율과 자원 사용량도 함께 확인해 줘.
이번에는 측정과 후보 비교까지 진행해 줘.
개선 목표와 비용 상한은 측정 결과를 보고 정한다.

개선 과정에서 사용하지 않은 입력으로도 성능과 정확성을 시험합니다. 익숙한 입력에서만 효과가 나는 변경을 걸러내기 위해서입니다.

사람의 시간까지 포함해 효과를 봅니다

  • 요청부터 완료까지 걸린 시간 완료 조건을 충족할 때까지의 구현, 검토 대기, 재수정 시간을 모두 포함합니다.
  • 사람이 쓴 시간 지시, 검토, 설명 보충에 쓴 시간을 합칩니다.
  • 재작업과 결함 검토 후 다시 고친 횟수와 뒤늦게 발견한 문제를 기록합니다.
  • 작업당 비용 에이전트 실행 비용과 검증 환경 비용을 함께 봅니다.

성격이 비슷한 작업끼리 비교합니다. 한 번의 빠른 구현만으로 전체 생산성이 높아졌다고 결론 내리지 않습니다.

오늘의 작은 실험

작은 작업 하나에 완료 조건 세 가지를 적어 보세요. 구현과 검증이 끝나면 결과를 확인하고, 다음 작업에도 필요한 규칙 한 가지를 남깁니다.
