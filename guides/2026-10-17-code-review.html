HELLO, HUMAN! / GUIDE 09

코드리뷰에서 배포까지,
팀이 함께 확인하는 7단계

코드를 바꾼 뒤 무엇을 확인하고, 누가 검토하며, 문제가 생기면 어떻게 복구할까요?
Anthropic의 운영 사례를 살펴보고, 우리 팀의 다음 리뷰에 쓸 질문과 양식을 준비합니다.

“테스트는 통과했고, 자동 리뷰도 끝났습니다.”
그다음, 동료는 무엇을 확인하면 될까요?

코드리뷰는 변경을 이해하고, 실패할 조건을 찾고, 운영에 넘길 준비가 됐는지 판단하는 과정입니다. 작성 도구가 달라져도 업무 규칙과 기대 결과, 문제가 생겼을 때의 책임은 팀이 설명할 수 있어야 합니다.

먼저 Anthropic이 공개한 변경 처리 흐름을 살펴보고, 우리 팀에 적용할 조건을 정리합니다. 우리 팀 적용안은 작성자의 검증 + 동료 1명의 리뷰 + 위험한 변경의 추가 검토에서 시작합니다. AI는 허용된 환경에서 코드 탐색과 오류 후보 확인을 돕습니다. 승인 인원과 반복 횟수는 팀에 맞게 조정할 제안이며 Anthropic의 정책과 다릅니다.

PR(Pull Request)은 코드 변경을 합치기 전에 검토를 요청하는 단위입니다. GitLab의 Merge Request도 같은 뜻으로 읽으면 됩니다. 사례·거래·코드 상황은 설명을 위해 구성한 가상 예시입니다.

01 / THE LIFE OF A CHANGE

코드를 합친 뒤에도
확인은 계속됩니다

PR(풀 리퀘스트)은 내가 바꾼 코드를 팀의 기준 코드에 합치기 전에 검토를 요청하는 단위입니다. 코드를 합치는 작업을 병합이라고 합니다. 리뷰를 통과했더라도 다른 변경과 합쳐지거나 실제 사용자가 쓰기 시작하면 예상하지 못한 문제가 드러날 수 있습니다.

그래서 이 글은 PR 준비부터 병합, 배포, 배포 후 확인과 복구까지를 함께 다룹니다. 아래 흐름은 Anthropic이 공개한 THE LIFE OF A CHANGE 도식과 단계별 설명을 바탕으로 구성했습니다. ‘Anthropic 실제 운영’은 공개된 사례이고, ‘우리 팀 적용안’은 커머스·업무 시스템을 개발하는 팀에 제안하는 방법입니다. 원문 도식과 설명 ↗

처음 읽는다면 이렇게 따라가세요

먼저 아래 7단계로 전체 흐름을 훑어보세요. 작성자는 PR 준비 방법, 리뷰어는 검토 순서를 읽은 뒤 템플릿을 하나 골라 다음 PR에 써보면 됩니다. 결제 예시는 실패했을 때 무엇을 확인해야 하는지 보여줍니다.

리뷰 도구를 켜는 것만으로 병합이 막히지는 않습니다

Claude가 제공하는 관리형 Code Review 서비스는 직접 PR을 승인하거나 병합을 막지 않습니다. 위 사례에서 병합을 막는 것은 Anthropic의 내부 운영 정책입니다. 우리 팀도 필수 검사·지적 처리·사람 승인 조건을 저장소에 설정하고, 조건을 충족하지 못한 PR이 실제로 병합되지 않는지 확인해야 합니다. 제품의 동작 범위 ↗

병합 직전과 배포 직후에 필요한 확인

다른 PR과 합쳐진 결과도 검사하세요

GitHub 병합 큐는 최신 기준 브랜치와 대기열 앞쪽의 변경까지 합쳐 검사합니다. GitHub Actions를 쓴다면 큐 검사를 요청하는 merge_group 이벤트에서도 필수 검사가 실행되도록 설정해야 합니다. 병합 큐 공식 안내 ↗

실제 업무 결과를 보고 넓히세요

내부에서 문제가 없었더라도 주문·결제가 제대로 처리되는지 확인한 뒤 사용 대상을 넓힙니다. 뒤늦게 나오는 정산 결과와 고객 문의도 살펴보세요. 기능을 꺼도 이미 잘못 처리된 거래는 따로 바로잡아야 합니다.

사례의 수치는 조건과 함께 읽습니다

Claude Code 팀은 2026년 6~9월 병합 PR 수가 두 배 이상 늘고, 되돌린 PR의 비율은 40% 넘게 줄었다고 보고했습니다. 자동 리뷰와 함께 CI, 위험별 승인, 단계적 출시와 복구를 운영한 결과입니다. 회사 내부에서 관찰한 수치이므로, 자동 리뷰 하나의 효과로 보거나 우리 팀도 같은 만큼 개선될 것이라고 기대할 수는 없습니다. Anthropic 운영 사례 ↗

이 사례를 참고할 때는 승인 인원이나 개선 수치보다 어떤 검사를 하고, 남은 위험은 무엇이며, 문제가 나면 누가 대응하는지부터 정해보세요. 다음 절부터는 이 질문을 실제 PR에 옮기는 방법을 살펴봅니다.

02 / REVIEW BY RISK

한 줄 수정도
깊은 검토가 필요할 수 있습니다

얼마나 자세히 검토할지는 잘못됐을 때 어떤 일이 생기는지를 보고 정합니다. 결제 재시도 횟수, 접근 권한 조건, 정산 기준 시각은 한 줄만 바뀌어도 영향이 클 수 있습니다.

‘1명 승인’에 누가 포함되는지 먼저 보세요

위험Anthropic 실제 운영우리 팀 적용안
낮음조건 충족 시 추가 사람 승인 생략 가능작성자 외 동료 1명
보통사람 1명작성자 외 영역 담당 1명
높음사람 2명작성자 외 역할을 나눈 2명
인원 계산에이전트를 지시한 사람도 포함 가능작성자·에이전트를 지시한 사람은 제외

원문에서는 위험 등급과 추가 사람 검토 여부를 따로 판단합니다. 보안상 민감한 경로와 CI 파일에는 사람 검토가 필요합니다. 봇 승인은 사람 수에 포함되지 않으며, 승인은 검토한 커밋에 적용됩니다. 실제 정책과 예외 ↗

같은 ‘1명’이어도 원문과 아래 제안은 세는 방식이 다릅니다. 이 글에서는 작성자와 별개로 동료가 한 번 더 확인하는 방식부터 시작하길 제안합니다. 위험 등급도 그대로 복사하지 않고, 커머스 업무에서 문제가 생겼을 때의 피해를 기준으로 나눴습니다.

두 명이 검토한다면 맡을 부분을 나눠보세요. 부분취소 기능에서는 한 명이 할인 배분과 반올림 규칙을, 다른 한 명이 DB 상태와 재시도 시 중복 처리 여부를 확인할 수 있습니다. 각자 무엇을 봤는지도 PR에 남깁니다.

해당 영역을 검토할 사람이 없다면 변경 범위나 일정을 조정합니다. 긴급하게 처리해야 한다면 팀의 예외 절차에 따라 승인자, 아직 확인하지 못한 위험, 최소한의 검사 결과, 복구 담당자를 기록합니다.

03 / BEFORE THE REQUEST

무엇이 맞는 결과인지
먼저 적어주세요

“부분취소를 지원한다”는 설명만으로는 코드가 맞는지 판단하기 어렵습니다. 어떤 상품을 취소했을 때 할인·쿠폰·배송비가 어떻게 바뀌어야 하는지, 예시와 기대 결과를 함께 적어주세요. 아직 정하지 못한 규칙은 표시하고 담당자에게 확인합니다. 업무 규칙이 틀리면 코드와 테스트가 함께 틀릴 수도 있습니다.

구현 전에 함께 정하세요

무엇을 바꿀지, 반드시 지켜야 할 규칙은 무엇인지, 실패하면 어떤 상태가 되어야 하는지 적습니다. 설계 방향이 달라질 만한 변경은 담당자와 먼저 이야기합니다.

리뷰를 요청할 때 붙여주세요

확인한 코드 버전, 실행한 명령이나 수동 확인 순서, 기대 결과와 실제 결과를 남깁니다. 아직 확인하지 못한 부분도 함께 적습니다.

PR 하나에는 설명 가능한 목적 하나

Google은 작은 변경을 ‘관련 테스트와 함께 그 자체로 이해할 수 있는 단위’로 설명합니다. 몇 줄 이하로 자르는 것보다, 한 가지 목적을 설명할 수 있게 묶는 것이 중요합니다. 파일 구조를 크게 정리하는 작업은 기능 변경과 나누면 읽기 쉽습니다. 작은 변경 가이드 ↗

쿠폰 개선을 나누는 예함께 검토할 범위
최소 주문금액 검증업무 로직과 경계 금액 테스트
사용 불가 사유 표시API 응답과 화면의 오류·안내 상태
계산 클래스 구조 정리파일 이동·이름 변경과 기존 동작 유지

파일 종류별로만 나누면 오히려 흐름을 이해하기 어려워집니다. 한 기능을 설명하는 서비스·API·테스트는 함께 읽을 수 있게 묶으세요. 다른 PR이 먼저 반영되어야 한다면 순서를 적고, 중간 단계에서도 기존 기능이 동작하는지 확인합니다.

“테스트 완료”를 검증 가능한 문장으로 바꾸세요

“승인 후 응답이 유실되는 테스트에서 외부 승인 1건과 내부 확인 대기 상태를 확인했다. 검증 커밋과 결과 링크를 첨부했다.”처럼 어떤 버전에서 무엇을 확인했는지가 있어야 합니다. 실행하지 않은 검증도 그대로 적습니다.

오래된 코드에 자동 테스트를 바로 추가하기 어렵다면, 동료도 같은 결과를 확인할 수 있도록 입력 예시와 수동 확인 순서, 기대 결과부터 남기세요. 여러 번 확인하게 되는 항목부터 차례로 자동화하면 됩니다.

04 / PEOPLE AND CHECKS

무엇을 도구에 맡기고
무엇을 사람이 볼까요?

형식 검사나 테스트처럼 같은 기준으로 반복할 수 있는 일은 CI에 맡깁니다. 사람은 그 기준이 업무에 맞는지, 테스트의 기대 결과부터 잘못 정한 것은 아닌지 확인합니다. 아래처럼 역할을 나누면 어디를 더 살펴봐야 할지 분명해집니다.

리뷰 요청을 받았다면 이 순서로 읽어보세요

  1. 왜 필요한 변경인가

    해결하려는 문제와 이번에 바꿀 범위를 읽습니다. 기존 기능이나 설정으로 해결할 수 있는지도 살펴봅니다.

  2. 입력부터 결과까지 어떻게 흐르는가

    화면·API에서 서비스, DB, 외부 호출, 후속 배치까지 따라갑니다.

  3. 실패하면 어떤 상태가 남는가

    요청이 중복되거나 동시에 실행될 때, 응답이 늦거나 일부만 성공할 때 결과를 확인합니다.

  4. 테스트가 그 상황을 확인하는가

    정상 상황뿐 아니라 실패 상황도 검사했는지, 기대 결과가 합의한 업무 규칙과 맞는지 봅니다.

  5. 배포하고 운영할 준비가 됐는가

    구버전과의 호환성, 필요한 로그, 배포 순서, 복구 방법과 담당자를 확인합니다.

테스트 자체도 리뷰 대상입니다. 구현이 잘못됐다면 이 테스트가 실제로 실패하는가를 물어야 합니다. AI 요약으로 코드 위치를 찾을 수는 있어도, 승인자는 자신이 맡은 중요한 분기와 데이터 변경을 실제 코드에서 확인합니다. Google 검토 기준 ↗

05 / FAILURE AND RECOVERY

응답을 못 받았다면
결제 결과는 아직 모릅니다

“결제대행사(PG)에서 정해진 시간 안에 응답이 오지 않으면 한 번 더 요청한다”는 변경을 가정해 봅시다. 이렇게 응답을 기다리다 시간이 지난 상황을 타임아웃이라고 합니다. 그런데 PG는 이미 결제를 승인했고 응답만 사라졌다면 어떨까요? 새 결제로 다시 요청하면 돈이 두 번 빠져나갈 수 있습니다.

여기서 필요한 개념이 멱등성입니다. 같은 결제를 다시 요청해도 실제 결제는 한 번만 일어나도록 하는 성질입니다. 이를 위해 같은 작업임을 식별하는 값인 멱등 키를 쓸 수 있습니다. 다만 안전하게 재시도하려면 PG가 그 키를 어떤 범위와 기간 동안 인정하는지 확인해야 합니다. AWS 멱등 재시도(영문) ↗

이 PR에서 확인할 다섯 가지

  1. 같은 결제를 다시 요청할 때 같은 키를 쓰는가? 같은 키로 금액이나 주문을 바꿔 보내면 어떻게 처리하는가?
  2. ‘결과를 아직 모름’과 ‘명확한 결제 거절’을 구분하는가? 모르는 결과는 어떻게 확인하는가?
  3. PG 승인 뒤 DB 저장에 실패해도 새 결제 없이 복구할 수 있는가?
  4. 결과 통지가 두 번 오거나 늦게 와도 이미 확정한 상태가 잘못 바뀌지 않는가?
  5. 응답 유실·DB 실패·동시 요청을 테스트하고, PG 승인 건수와 최종 DB 상태까지 확인했는가?

가짜 응답을 돌려주는 테스트용 대역(Mock)을 썼다면 실제 PG와 같은 조건으로 동작하는지도 확인합니다. PG가 같은 키의 중복 처리를 막아주지 않는다면, 거래 조회와 중복 방지 방법부터 검토해야 합니다. 우리 DB에 키를 저장했다는 사실만으로 PG의 중복 결제까지 막을 수 있는 것은 아닙니다.

코드를 되돌려도 이미 승인된 거래는 남습니다

# 팀 리뷰 기준 예시

## 우선 확인
- 동일 결제·환불 작업의 재처리에서 금액 이동이 중복되지 않는다.
- 고객·협력사 데이터는 호출자의 허용 범위 안에서 조회한다.
- 주문·결제·재고 상태의 변경 조건이 확정한 업무 규칙과 일치한다.
- 배치 재시작에서 완료한 작업과 미완료 작업을 구분한다.
- DB 구조·주고받는 메시지를 바꿔도 정해진 배포 순서에서 구버전과 함께 동작한다.

## 지적 방법
- 필수 지적에는 발생 조건, 코드 위치, 영향을 적는다.
- 불확실한 업무 규칙은 추정하지 말고 질문한다.
- CI가 처리하는 형식 문제를 중복 지적하지 않는다.
- 기존 문제라도 이번 변경이 악화시키는지 확인한다.
- 테스트·빌드를 실행하지 않았다면 실행했다고 쓰지 않는다.

## 운영 시작안
- 작성자와 작성 에이전트를 지시한 사람을 제외하고, 낮음·보통 위험은 동료 1명, 높은 위험은 역할을 나눈 2명이 검토한다.
- 자동 수정·재검토는 최대 세 차례까지 시도하고, 해결되지 않으면 사람이 원인과 접근 방식을 다시 검토한다.
- 횟수를 채웠거나 AI가 문제가 없다고 답했다는 이유만으로 승인하지 않는다.
- 승인 후 코드가 바뀌면 다시 검토하고, 필수 검사도 최신 변경을 대상으로 했는지 확인한다.
- 다음 영업일까지 검토 결과·검토 예정 시점·대체 리뷰어 중 하나로 응답한다.

## 병합·배포·관찰
- 필수 CI와 필요한 코드·보안 검토를 완료하고 지적별 조치를 기록한다.
- 필수 지적은 고치거나 수정하지 않아도 되는 근거를 리뷰어와 확인한 뒤 병합한다.
- 병합 큐 또는 최신 기준 브랜치와 합친 상태에서 필수 검사를 다시 확인한다.
- 처음 적용할 대상, 지켜볼 기간, 확대·중단 기준과 담당자를 배포 전에 정한다.
- 문제가 생기면 대상 확대를 멈추고, 기능 끄기·수정 버전 배포·이전 버전 복귀·거래 복구 중 필요한 조치를 정한다.
- 한 번 놓친 실패 상황은 테스트와 리뷰 규칙에 추가한다.

다음 영업일까지 검토 결과, 검토 예정 시점, 대체 리뷰어 중 하나로 응답하는 규칙부터 시작할 수 있습니다. Google의 1영업일 권고도 첫 응답의 기준이지, 모든 PR을 하루 안에 병합하라는 뜻은 아닙니다. 리뷰 응답 기준 ↗

중요한 업무는 작성자 외에도 한 명 이상이 처리 흐름과 장애 확인 방법을 설명할 수 있게 해보세요. 위험한 변경은 짧게 시연하고, 해당 코드가 낯선 리뷰어는 익숙한 동료와 함께 읽으면 좋습니다. AI가 만든 설명을 팀 문서에 옮길 때도 실제 코드·SQL·로그와 맞는지 확인합니다.

함께 볼 지표해석할 때 확인할 것
첫 응답·병합 대기리뷰어 대기, 작성자 수정, CI 실행 시간을 구분
사람이 쓴 시간코드를 읽은 시간과 지적을 확인·설명·수정한 시간을 함께 기록
실제로 도움이 된 지적담당자가 실제 문제였는지 확인. 작성자가 고쳤다는 이유만으로 맞는 지적이라고 세지 않음
배포 후 업무 영향기존 기능의 오류, 긴급 수정, 데이터 정정, 중복 결제, 운영 문의를 함께 확인
자동화 비용모델·CI 비용, 재검토 횟수와 함께 비교

비교할 때는 위험 등급과 변경 범위가 비슷한 PR끼리 묶으세요. 얼마 동안 몇 건을 봤는지도 함께 적어야 숫자의 의미를 알 수 있습니다. PR이나 코멘트 수를 개인의 성과 점수로 쓰지는 않습니다. 과거 오류로 리뷰 규칙을 다듬었다면, 효과를 평가할 때는 그 과정에서 쓰지 않은 오류 사례도 확인해 보세요.

이번 리뷰에서 막혔던 부분 하나를 다음 PR에서 개선해 보세요. 업무 규칙이 모호했다면 예시를 더하고, 실패 상황을 놓쳤다면 테스트를 추가하고, 누가 처리할지 몰랐다면 담당자를 정하면 됩니다. 이렇게 남긴 기록이 다음 동료의 리뷰를 쉽게 만듭니다.
