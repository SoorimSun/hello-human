01 / 환경 목록

설치된 버전과
서비스가 쓰는 버전을 구분합니다

먼저 개발 PC, CI, 운영 서버, 컨테이너, 배치의 런타임을 나눠 적습니다. 아래 명령은 현재 셸이 선택한 실행 파일을 보여줍니다. 이 출력만으로 이미 실행 중인 서비스의 패치 완료를 판단하지 않습니다.

현재 셸에서 버전과 경로 확인

node --version
node -p "process.execPath"
java -version
java -XshowSettings:properties -version

Java 출력에서는 java.vendor, java.runtime.version, java.home을 확인합니다. ‘Java 17’만 적지 말고 공급자와 빌드 번호까지 남깁니다.

Windows와 Linux에서 실행 경로를 찾는 방법

Windows PowerShell 현재 셸의 경로와 실행 중인 프로세스를 각각 확인합니다.

Get-Command node, java | Select-Object Name, Source
Get-Process node, java -ErrorAction SilentlyContinue |
  Select-Object Id, Path, StartTime

Linux 셸의 경로와 실행 중인 프로세스를 확인합니다. 실행 인수에는 내부 경로나 비밀 값이 있을 수 있으므로 원문을 외부에 붙여 넣지 않습니다.

command -v node
command -v java
ps -eo pid,lstart,args | grep -E '[n]ode|[j]ava'

서비스 관리자·컨테이너의 실행 설정도 함께 보세요. 경로가 같아도 디스크의 파일만 교체되고 이전 프로세스가 남아 있을 수 있습니다. 접근 권한 때문에 경로를 읽지 못했다면 ‘미확인’으로 기록합니다.

작업 전에는 현재 배포본과 설정, 인증서 저장소의 복구 자료를 확보하고 테스트 환경에서 먼저 적용합니다. 운영 중단·오류 증가·외부 연동 실패가 나타나면 언제 배포를 멈출지도 정합니다.

nvm 공식 사용법 · Windows 네이티브의 nvm-windows와 WSL의 nvm은 별도입니다. 공식 설치 파일이나 OS 패키지로 운영한다면 해당 설치 경로의 업데이트 절차를 사용합니다.

프로젝트의 npm 의존성은 별도 확인

프로젝트 폴더에서 실행합니다. 조직이 허용한 레지스트리를 사용하세요. npm audit는 의존성 정보를 레지스트리에 보내 알려진 취약점을 조회합니다.

전체 의존성과 운영 의존성을 나눠 보고, 자동 수정 예정 내역을 검토합니다. --force는 메이저 변경까지 허용하므로 자동으로 붙이지 않습니다. 승인한 변경 후에는 lockfile과 빌드·테스트 결과를 함께 확인하세요. 이 점검이 Node.js 실행 파일을 패치하지는 않습니다. npm audit 공식 문서 ↗

03 / Java · JDK

JDK 공급자와 빌드,
인증서 저장소까지 확인합니다

10월 정기 패치 뒤 후속 수정이 나왔습니다

eMudhra 중간 인증기관(CA)의 키 침해에 대응해 Oracle은 10월 21일 CVE-2026-91403 공지를 냈고, 24일 CVE-2026-114820 공지에서 관련 루트 인증서를 제거하는 후속 업데이트를 제공했습니다. 외부 HTTPS 서버를 신뢰할 때 사용하는 인증서 검증과 관련된 문제입니다.

‘이번 달 JDK를 올렸다’는 기록만으로 끝내지 않습니다. 24일 공지에는 앞선 .0.2 빌드도 영향 대상으로 명시돼 있습니다. 21일 공지 · 24일 후속 공지

배포판·계열10월 24일 수정 빌드공식 자료
Oracle JDK 1717.0.21.0.3+1릴리스 노트
Oracle JDK 2121.0.13.0.3+1릴리스 노트

위 표는 Oracle의 두 계열 예시입니다. Temurin·Corretto·Zulu·OS 제공 OpenJDK에는 공급자별 빌드와 인증서 구성이 있습니다. Oracle의 .0.3을 다른 배포판의 합격 기준으로 쓰지 않습니다. 자신의 공급자 공지에서 수정 빌드와 해당 OS·아키텍처 패키지를 확인하세요.

같은 공급자·같은 메이저의 수정 빌드로 교체

  1. 실제 서비스의 JDK 공급자, 전체 버전, 실행 경로를 기록합니다.
  2. 공급자의 수정 JDK를 별도 경로에 준비하고 체크섬을 확인합니다. 설치 정책과 사용 조건도 확인합니다.
  3. 서비스의 JAVA_HOME 또는 직접 지정한 Java 경로를 바꿉니다. 컨테이너·내장 JRE·jlink 런타임도 각각 다시 만듭니다.
  4. 테스트 후 해당 JVM을 재시작하고, 실행 중인 프로세스에 연결해 버전을 확인합니다.

아래의 <PID>를 확인할 서비스의 프로세스 번호로 바꿉니다.

jcmd <PID> VM.version
jcmd <PID> VM.system_properties

VM.system_properties에서는 java.home·공급자·런타임 버전과 truststore 설정을 봅니다. 민감한 값이 포함될 수 있으니 외부에는 필요한 항목만 익명화해서 공유합니다. jcmd는 같은 머신에서 해당 JVM에 접근 가능한 계정으로 실행합니다. 컨테이너라면 그 실행 환경 안에서 PID와 접근 조건을 확인하세요. jcmd 공식 문서 ↗

이전 인증서 저장소를 통째로 복사하지 않습니다

javax.net.ssl.trustStore나 라이브러리 설정으로 별도 truststore를 사용하는지 봅니다. 기본 JDK의 cacerts를 갱신해도 앱이 다른 저장소를 읽으면 그 저장소를 따로 점검해야 합니다. 필요한 사내 CA만 검토해 이관하고, 이전 cacerts 전체를 새 JDK에 덮어써 제거된 인증서를 되살리지 않도록 합니다.

즉시 JDK를 교체하기 어렵다면

Oracle의 공식 임시 대응은 저장소 백업, 관련 루트 CA 제거, 실행 중인 런타임 재시작 등의 방법을 안내합니다. 별칭과 대상 파일은 배포판·실행 환경에 맞게 확인합니다. 이 조치는 인증서 문제를 위한 것이며 다른 정기 보안 수정까지 적용하지는 않습니다. 연결 오류를 없애기 위해 TLS 인증서 검증을 끄지 마세요.

적용 뒤에는 외부 결제·배송·파트너 API 같은 HTTPS 연동을 실제 앱 경로로 시험합니다. 일반 브라우저에서 접속된다는 사실은 해당 JVM의 신뢰 저장소가 정상이라는 증거가 아닙니다.

04 / Tomcat

독립 서버인지,
앱 안의 JAR인지부터 나눕니다

설정에 따라 영향이 달라집니다

CVE-2026-101356은 HTTP/2의 비동기 Servlet 처리 중 오류가 났을 때 사용자 간 요청·응답이 섞일 수 있는 문제입니다. CVE-2026-101296은 JNDIRealm에서 GSSAPI 이외의 SASL 인증을 설정한 경우 올바른 비밀번호 없이 인증될 수 있는 문제입니다. 둘 다 Apache 등급은 Important입니다.

일반적인 Spring Security 로그인 전체를 이 인증 우회와 동일하게 취급하지 않습니다. 또한 앞단 프록시가 HTTP/2를 지원한다는 사실만으로 Tomcat까지 HTTP/2가 연결되는 것은 아닙니다. 실제 Connector와 Realm 설정을 확인하세요.

9.0.x9.0.118~9.0.1229.0.0.M1~9.0.1229.0.123

수정 릴리스는 10월 12일자로 표시돼 있고 위 취약점의 공개일은 10월 20일입니다. 범위의 M은 정식 출시 전 milestone을 뜻합니다. 한 항목의 영향 범위 밖이라는 사실만으로 다른 취약점까지 안전하다고 판단하지 않습니다.

Tomcat 11에서 AJP를 사용한다면 추가 확인

CVE-2026-103119은 큰 비차단 쓰기 처리에서 응답 일부가 다음 요청에 섞일 수 있는 문제입니다. 11.0.0-M25~11.0.26에 영향을 주며 11.0.27에서 수정됐습니다. AJP Connector 사용 여부를 함께 확인합니다. Tomcat 11 공식 공지 ↗

A. 독립 Tomcat에 WAR를 배포한다면

  1. 서비스가 사용하는 CATALINA_HOME·CATALINA_BASE와 JDK를 확인합니다. 해당 설치본에서 Linux는 bin/version.sh, Windows는 bin\version.bat로 버전을 봅니다.
  2. 같은 계열의 수정 배포본을 별도 경로에 준비합니다. 설정·WAR·사용자 정의 라이브러리를 비교해 이관하고, 이전 lib 전체를 덮어쓰지 않습니다.
  3. 테스트 뒤 서비스 경로를 전환하고 재시작합니다. 시작 로그의 Tomcat 버전과 실제 설치 경로를 확인합니다.

Tomcat 9에서 10·11로 이동하면 javax.*에서 jakarta.*로의 전환 등 앱 호환성 검토가 필요합니다. 긴급 패치와 메이저 이전을 한 단계로 묶지 않습니다. Tomcat 마이그레이션 안내 ↗

B. Spring Boot의 내장 Tomcat이라면

JDK를 바꿔도 앱 안의 Tomcat JAR는 바뀌지 않습니다. 먼저 의존성에서 실제 선택된 버전을 보고, 수정된 Tomcat을 제공하는 지원 Boot 버전으로 갱신하는 경로를 검토합니다. 긴급하게 Tomcat만 재정의해야 한다면 호환성을 따로 시험합니다.

다음은 Maven에서 spring-boot-starter-parent를 상속하고 Tomcat 10.1.x를 쓰는 앱의 예시입니다. 기존 pom.xml의 properties 안에 추가하거나 기존 값을 바꿉니다. Tomcat 9·11 프로젝트에 그대로 넣지 않습니다.

<properties>
    <tomcat.version>10.1.61</tomcat.version>
</properties>

Boot BOM만 import하는 Maven 프로젝트는 이 속성만 추가해서는 적용되지 않을 수 있습니다. 해당 프로젝트의 dependencyManagement에서 관련 모듈을 일관되게 재정의해야 합니다. Gradle도 BOM·dependency-management 플러그인 구성에 맞는 별도 설정이 필요합니다. 어떤 방식이든 최종 의존성 결과를 확인합니다. Spring Boot의 의존성 재정의 방법 ↗

./mvnw dependency:tree "-Dincludes=org.apache.tomcat:*,org.apache.tomcat.embed:*"
./mvnw clean verify

Windows에서는 ./mvnw 대신 .\mvnw.cmd를 사용합니다. Gradle은 ./gradlew dependencyInsight --dependency tomcat-embed-core --configuration runtimeClasspath로 선택 버전을 보고 관련 Tomcat 모듈과 빌드·테스트 결과도 확인합니다. 멀티 모듈이면 실제 배포 모듈에서 확인하세요. Gradle 의존성 확인 방법 ↗

새 JAR·WAR·이미지를 배포하고 재시작한 뒤, 포함된 Tomcat JAR와 시작 로그가 목표 버전인지 확인합니다. 소스의 속성값만 바뀌고 이전 빌드가 배포된 경우를 잡아야 합니다.

Boot 버전만 보고 완료로 표시하지 않습니다

예를 들어 Spring Boot 3.5.16은 3.5 계열의 마지막 OSS 릴리스이며, 기본 Tomcat은 10.1.55입니다. 3.5.16으로 올렸다는 사실만으로 이번 수정 기준 10.1.61을 충족하지 않습니다. 긴급 조치 뒤에는 지원 계열 이전 또는 상용 지원 경로도 검토하세요. 릴리스 공지 · 기본 의존성 표

05 / 헬로우 휴먼의 적용 제안

‘설치 완료’를
‘적용 확인’으로 바꾸는 네 가지 증거

증거완료로 볼 조건부족한 기록
실행 버전실제 서비스 PID·시작 시각과 런타임 버전·경로가 목표와 일치관리자 터미널에서 버전 한 번 출력
배포본배포 ID·이미지 digest·의존성 결과를 운영 복제본과 대조다운로드 또는 CI 빌드만 완료
기능·보안 동작주요 정상 경로와 거부해야 할 요청이 기대대로 동작첫 화면이 열린다는 확인만 있음
전체 대상웹·워커·배치·컨테이너 복제본을 모두 확인하고 담당자 기록서버 한 대만 확인, 나머지는 추정

Node.js는 서비스 자체의 시작 로그나 내부 진단에서 process.version·process.execPath를 확인하는 방식이 좋습니다. 컨테이너에서 새로 실행한 node -v만으로 기존 앱 프로세스까지 확인했다고 쓰지 않습니다. Java는 해당 JVM의 jcmd 결과, Tomcat은 새 배포본의 의존성·시작 로그를 함께 남깁니다.

서비스에 맞게 고를 회귀 테스트

  • HTTPS 연동 결제·배송 등 실제 앱의 외부 API 연결이 정상이며, 테스트 환경의 신뢰하지 않는 인증서는 거부됩니다.
  • 로그인·권한·세션 올바른 사용자는 통과하고 틀린 비밀번호·권한 없는 요청은 차단됩니다. JNDIRealm을 쓴다면 그 인증 경로를 직접 시험합니다.
  • 압축·파일 처리 정상 Brotli 응답과 오류 입력이 예상대로 처리되고 프로세스가 비정상 종료되지 않습니다.
  • 동시 요청·비동기 처리 테스트 계정 둘을 구분해 응답이 섞이지 않는지, 오류 뒤에도 세션과 요청 처리가 유지되는지 봅니다.

위 항목은 서비스 회귀 확인을 위한 제안입니다. 모두 통과해도 모든 취약점의 부재를 증명하는 것은 아닙니다. 수정 버전·영향 조건 대조와 함께 판정하고, 공격성 입력은 승인된 테스트 환경에서만 다룹니다.

배포를 멈추거나 되돌릴 때

오류율·지연·외부 연동 실패를 적용 전과 비교합니다. 기준을 넘으면 배포를 중단하고 원인을 확인합니다. 이전 취약 버전으로 복구해야 한다면 ‘패치 완료’를 취소하고, 노출 제한과 재적용 담당자·기한을 남깁니다. 복구 성공과 보안 수정 완료는 별도 상태입니다.

패치 완료 확인표 내려받기 ↗환경 목록, 조치 계획, 배포 증거, 복구·미확인 항목을 한 파일에 기록합니다.

아래 가상 자료와 요청문을 허용된 AI 도구에 붙여 넣습니다. 실제 회사명·내부 주소·로그·인증 정보는 쓰지 않습니다. AI가 공식 원문을 열 수 없다면 관련 공지 내용을 직접 제공하고, 확인하지 못한 부분은 그대로 남깁니다.

규칙
1. 기준일, 공급자, 전체 버전, 실행 경로와 배포 방식을 구분하라.
2. 설치된 파일과 실행 중인 프로세스를 같은 것으로 취급하지 마라.
3. 영향 버전과 공격 조건을 각각 대조하라. 조건 자료가 없으면 ‘미확인’으로 남겨라.
4. 수정 버전은 같은 계열·같은 공급자를 기준으로 제시하고 공식 URL을 붙여라.
5. 원문을 열지 못했거나 자료가 충돌하면 그 한계와 추가 자료를 적어라.
6. 완료 증거가 없으면 ‘패치 완료’라고 쓰지 마라.

기대 결과와 비교하기
  • 서비스 A 실행 로그의 24.22.0과 Brotli 해제 조건을 근거로 조치 대상으로 분류합니다. 셸이 24.22.1이어도 워커 재시작·실행 버전 증거가 없으므로 완료 처리하지 않습니다.
  • 서비스 B의 JDK Oracle 17.0.21.0.2는 24일 후속 공지에 해당합니다. 17.0.21.0.3+1 또는 같은 계열의 후속 수정 빌드를 검토하고, 실제 truststore와 JVM 재시작을 확인하도록 요청합니다.
  • 서비스 B의 Tomcat 10.1.60과 HTTP/2·비동기 Servlet 사용이 확인됐으므로 해당 혼선 문제의 조치 대상입니다. JNDIRealm은 자료가 없어 ‘미확인’으로 남깁니다. 10.1.61 이상 같은 계열의 수정 버전으로 빌드·배포·검증하는 계획을 세웁니다.

이 답안은 공지와 가상 입력을 대조한 예시입니다. 실제 취약점 재현이나 패치 성공을 관측한 결과가 아닙니다.

실제 AI 실행 결과

위 가상 자료와 요청문을 GPT-6에 그대로 입력한 응답을 요약했습니다. 최종 판정은 ‘패치 완료 미확인 · 조치 및 운영 검증 필요’였습니다.

  • 서비스 A 시작 로그의 Node.js 24.22.0과 Brotli 처리 경로를 점검 대상으로 분류했습니다. 관리자 셸의 24.22.1은 워커의 패치 증거로 인정하지 않고, 실제 실행 버전·경로·재시작 기록을 요청했습니다.
  • 서비스 B의 JDK Oracle 17.0.21.0.2를 영향 버전으로 판단하고 17.0.21.0.3+1 적용을 검토하도록 했습니다. 실제 신뢰 저장소 구성과 HTTPS 연동 테스트는 추가 확인으로 남겼습니다.
  • 서비스 B의 Tomcat 10.1.60과 HTTP/2·비동기 Servlet 사용을 근거로 10.1.61 적용을 검토했습니다. 실제 로딩된 JAR 버전과 JNDIRealm 설정은 별도 확인이 필요하다고 했습니다.

기대 결과와의 비교 핵심 판정이 일치했고, 배포 식별자·실행 프로세스·테스트 결과를 완료 증거로 요구했습니다. 실제 서버에 패치를 적용한 기록이 아닌, 가상 자료로 작성한 AI 점검 초안입니다.

AI 결과를 통과시킬 기준

  1. 모든 판정에 실제 제공된 입력과 공식 근거가 연결돼 있는가?
  2. JDK 공급자와 Tomcat 배포 방식을 구분하고, 모르는 설정을 지어내지 않았는가?
  3. ‘수정 버전 선택’, ‘배포’, ‘실행 확인’을 별도 단계로 적었는가?
  4. 아직 실행하지 않은 테스트나 재시작을 완료했다고 쓰지 않았는가?

한 항목이라도 빠지면 근거를 보완해 다시 작성하게 합니다. 실제 운영에 옮길 때는 담당자가 버전·설정·호환성을 확정하고, 승인된 변경 절차에 따라 적용합니다.
