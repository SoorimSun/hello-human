쇼핑몰 앞단의 NGINX가 영향을 받으면

NGINX2Root는 Xint 연구팀이 NGINX의 취약점 다섯 개와 Linux 커널의 취약점 한 개를 묶어 붙인 이름입니다. NGINX 쪽 다섯 개는 각각 다른 조건에서 발생합니다. 대표 사례는 HTTP/2 연결을 처리하다가 메모리가 손상되는 문제입니다. 실제 접속과 요청을 처리하는 워커가 종료될 수 있고, 조건에 따라 외부에서 워커 계정 권한으로 코드를 실행할 수 있습니다. 이때 영향 범위에는 그 계정이 읽을 수 있는 파일과 자격증명, 연결할 수 있는 내부 서비스가 포함됩니다. NGINX 보안 공지 ↗

호스트의 관리자(root) 권한은 별도 문제입니다. Xint는 Docker 안에서 워커 권한을 얻은 뒤, 호스트 커널의 SCTP 취약점을 통해 호스트 root에 도달한 사례를 시연했습니다. 이 단계가 성립하면 같은 호스트의 다른 컨테이너까지 조사 범위에 들어갑니다. 실제 영향은 노드의 커널 구성, SCTP 사용 가능 여부와 컨테이너의 보안 설정에 따라 달라집니다. Xint 연구팀의 한국어 발표 ↗

외부 접속을 처음 받는 쇼핑몰 앞단부터 목록을 만드세요. 관리자·파트너 사이트, 앱 API 프록시, 내부 게이트웨이, 컨테이너 이미지와 Ingress Controller에도 NGINX가 따로 들어 있을 수 있습니다. 각각 어떤 팀이 어떤 패키지나 이미지로 배포하는지 표시합니다.

어떤 NGINX가 실제 접속을 받는지 찾기

서비스 정의와 디스크 설정

Linux에서 systemd로 운영하는 예입니다. 먼저 서비스 정의의 ExecStart에서 실행 파일 경로와 -c(설정 파일), -p(기준 경로), -g(전역 설정) 인수를 확인합니다. 아래는 실행 파일이 /usr/sbin/nginx이고 기본 설정을 쓰는 경우입니다. 별도 경로·인수가 있으면 이후의 설정 검사에도 동일하게 적용합니다.

systemctl cat nginx
systemctl show nginx -p MainPID -p ExecStart

/usr/sbin/nginx -v
/usr/sbin/nginx -V
sudo /usr/sbin/nginx -t
sudo /usr/sbin/nginx -T

-v는 호출한 파일의 버전, -V는 버전과 빌드 옵션을 출력합니다. -t는 설정 문법과 참조 파일을 검사하고, -T는 검사한 설정 전체도 출력합니다. 디스크에서 읽은 설정이 현재 워커에 적용됐는지는 마지막 재시작·재적용 기록과 실제 접속 결과를 함께 봅니다. 전체 출력에는 인증정보나 내부 주소가 있을 수 있으므로 원본은 운영 환경 안에서 확인하세요. NGINX 명령 옵션 ↗

설정에서는 listen … http2, http2 on, listen … quic, http3를 찾습니다. 동적 DNS는 resolver와 변수 기반 proxy_pass, mirror, ssi를 함께 봅니다. 메일은 mail { … } 안의 리스너와 auth_http, proxy 설정을 확인합니다. 지시어가 속한 블록과 상속, 실제로 열린 포트까지 대조해야 어느 서비스의 설정인지 알 수 있습니다.

실행 파일을 제공한 패키지

아래에서 실행 파일 경로는 ExecStart에서 확인한 값으로 바꿉니다. 어느 패키지가 그 파일을 설치했는지, 패키지 전체 버전과 저장소 후보 버전이 무엇인지 기록합니다. 직접 빌드한 파일이라면 배포에 사용한 빌드 기록을 찾습니다.

# Debian · Ubuntu
dpkg-query -S /usr/sbin/nginx
dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\n' 'nginx*' 'libnginx-mod-*'
apt-cache policy nginx

# RHEL · AlmaLinux · Rocky Linux
rpm -qf /usr/sbin/nginx
rpm -qa 'nginx*'
dnf --refresh list --upgrades 'nginx*'

Debian·Ubuntu 목록의 첫 열은 설치 상태입니다. installed인 행에서 실제 실행 패키지와 모듈의 전체 버전을 읽습니다. config-files는 제거 후 설정 파일만 남은 상태입니다. RPM 계열은 설치된 RPM과 업데이트 후보의 버전·저장소를 구분하고, 모듈 스트림을 쓰는 AlmaLinux 8·9에서는 dnf module list nginx로 스트림도 확인합니다. 업데이트 후보가 비어 있으면 설치된 버전 자체를 공지와 대조합니다. Debian 패키지 조회 문서 ↗

HTTPS가 끝나는 지점

관리하는 도메인에서 TLS 연결을 맺고, ALPN(접속할 때 사용할 프로토콜을 협상하는 기능)으로 HTTP/2를 제안합니다. 아래 도메인은 예시입니다.

openssl s_client -connect shop.example.com:443 \
  -servername shop.example.com -alpn h2 </dev/null

ALPN protocol: h2는 그 접속 지점이 HTTP/2를 받는다는 뜻입니다. 패치된 서버도 같은 결과를 냅니다. 연결 오류는 ‘미확인’으로 기록합니다. CDN이나 로드밸런서가 TLS를 끝내면 외부 도메인에서는 그 장비의 응답만 보입니다. 운영망에서 원본 NGINX의 주소와 서비스 이름으로 다시 확인하고, TLS 없이 HTTP/2를 쓰는 내부 연결(h2c)은 해당 리스너 설정과 정상 클라이언트 연결로 따로 점검합니다. NGINX HTTP/2 모듈 문서 ↗

배포판 공지에서 확인한 차이

배포판은 오래 지원하는 버전에 보안 수정만 옮겨 넣기도 합니다(백포트). 이때 nginx -v는 그대로여도 패키지의 릴리스 번호는 달라집니다. 아래는 2026년 11월 19일 한국 시각 기준이므로 설치 직전에 해당 릴리스의 공지를 다시 확인하세요.

  • AlmaLinux. 8·9·10의 지원 스트림에 수정 패키지를 배포했습니다. 예를 들어 AlmaLinux 9의 기본 1.20 계열에 공지된 수정 RPM은 nginx-1.20.1-32.el9_9.1.alma.4입니다. AlmaLinux 8 기본값인 1.14처럼 지원이 끝난 스트림은 이번 배포에서 제외됐습니다. 현재 스트림과 설정 호환성을 확인하고 지원 스트림으로 전환합니다. AlmaLinux 스트림별 수정 RPM 목록 ↗
  • Ubuntu. 공식 nginx 패키지 기준으로 22.04·24.04 LTS는 대표 HTTP/2 취약점(CVE-2026-123007)이 Vulnerable이고, HTTP/3 취약점(CVE-2026-121810)은 해당 코드가 없어 Not affected입니다. 특히 22.04는 위 표의 1.19.7보다 오래된 버전이어도 두 번째 HTTP/2 취약점(CVE-2026-123633)이 평문 HTTP/2(h2c) 리스너에 해당한다고 Ubuntu가 명시합니다. 외부 HTTPS만 확인하면 이 내부 포트를 놓칠 수 있습니다. 대표 HTTP/2 상태 ↗ · Ubuntu의 h2c 예외 설명 ↗ · HTTP/3 상태 ↗
  • Debian. 대표 CVE-2026-123007의 추적기에는 12(bookworm)·13(trixie) 보안 저장소가 vulnerable, 불안정판(sid) 1.30.6-4가 fixed로 표시됐습니다. sid의 같은 소스 패키지 변경 기록에는 다섯 패치가 모두 기재됐지만, 확인 당시 HTTP/3 추적기에는 같은 버전이 여전히 vulnerable로 표시됐습니다. 기록이 엇갈리면 해당 CVE를 ‘미확인’으로 남기고, 사용 중인 릴리스의 보안 공지와 설치 버전을 다시 대조하세요. 대표 HTTP/2 판정 ↗ · sid 패키지 변경 기록 ↗ · HTTP/3 판정 ↗

한 대씩 패치하고 새 워커까지 확인하기

  1. 현재 설정과 실행 인수, 설치 패키지·동적 모듈 목록, 마스터·워커의 PID와 시작 시각을 기록합니다. 설정과 배포본을 보관하고 현재 바이너리로 설정 검사(-t)를 먼저 통과시킵니다. 검사에 실패하면 패키지 설치 중 자동 재시작될 수 있으므로 오류부터 해결합니다.
  2. 저장소 후보가 공급사의 수정 패키지인지 확인합니다. 이중화 환경에서는 설치 전에 한 대를 로드밸런서에서 빼고 기존 연결을 정리합니다. 설치 도중 서비스가 자동 재시작될 수 있습니다. 단일 서버는 재시작에 필요한 중단 시간을 먼저 확보합니다.
  3. 실행 파일을 제공하는 패키지와 호환되는 동적 모듈을 갱신합니다. 같은 실행 경로와 인수로 설정 검사를 통과한 뒤 서비스를 재시작합니다.
  4. 새 마스터·워커를 확인하고 정상 요청을 보내 봅니다. 변경 전과 오류율·응답 시간을 비교한 뒤 트래픽을 복귀시키고 다음 서버로 넘어갑니다.

패키지 설치와 재시작

Debian·Ubuntu의 기본 패키지 예시입니다. 먼저 저장소 정보를 갱신하고 Candidate에 표시된 버전을 공급사 공지와 대조합니다. 실행 파일을 nginx-core나 nginx-full이 제공하는 환경에서는 해당 패키지와 설치된 동적 모듈의 후보 버전도 확인해 설치 대상에 포함하세요.

sudo apt-get update
apt-cache policy nginx

수정본을 확인하고 대상 서버의 트래픽을 정리한 뒤, 해당 배포판의 명령만 실행합니다.

# Debian · Ubuntu에서 nginx가 실행 파일을 제공하는 경우
sudo apt-get install --only-upgrade nginx
# RHEL 계열에서 현재 스트림의 수정 RPM을 확인한 경우
sudo dnf --refresh upgrade 'nginx*'

설치 직후 패키지 조회 명령을 다시 실행해 실제 실행 파일과 동적 모듈을 제공하는 패키지들의 전체 버전을 기록하세요. 업데이트 명령이 성공해도 설치 버전이 그대로일 수 있습니다. 공급사 수정본이 설치됐는지 확인한 뒤 새 바이너리로 설정을 검사합니다. 실패한 서버는 트래픽에서 제외한 채 원인을 해결합니다.

nginx -s reload는 기존 마스터가 설정을 다시 읽고 워커를 교체하는 동작입니다. 새 실행 파일을 적용하려면 아래처럼 재시작하거나 공식 무중단 바이너리 교체 절차를 따릅니다. 패키지 설치 중 자동 재시작됐다면 아래의 실행 파일 대조와 이전 워커의 종료 확인으로 교체 여부를 판단합니다. NGINX의 설정 재적용과 실행 파일 교체 ↗

sudo /usr/sbin/nginx -t && sudo systemctl restart nginx
systemctl status nginx --no-pager

지금 실행 중인 파일 대조

아래는 일반적인 Linux·systemd 서비스에서 디스크의 수정 파일과 실행 중인 마스터가 같은 파일을 가리키는지 확인하는 예입니다. 서비스를 여러 개 운영한다면 단위 이름과 파일 경로를 바꿉니다. 먼저 서비스가 active이고 MainPID가 0보다 큰 실제 NGINX 마스터인지 확인하세요.

systemctl show nginx -p ActiveState -p MainPID -p ExecMainStartTimestamp
ps -C nginx -o pid,ppid,lstart,args

nginx_pid=$(systemctl show nginx -p MainPID --value)
sudo readlink "/proc/$nginx_pid/exe"
sudo stat -Lc '%d:%i %n' "/proc/$nginx_pid/exe" /usr/sbin/nginx

stat의 두 줄에서 장치 번호와 파일 번호(inode)가 같은지 봅니다. readlink에 (deleted)가 붙거나 파일 번호가 다르면 실행 파일의 경로와 교체 내역을 다시 확인합니다. 이전 PID·시작 시각을 재시작 후 목록과 대조해 예전 마스터와 워커가 종료됐는지도 봅니다. 패키지 전체 버전과 공급사 공지, 새 프로세스의 증거를 함께 남겨야 백포트 적용도 판정할 수 있습니다.

컨테이너·Kubernetes

수정된 최종 이미지로 배포 원본을 갱신합니다. 자체 이미지라면 다시 빌드하고, Ingress Controller 등 완제품이라면 공급사가 수정한 제품 릴리스를 선택합니다. 컨테이너·Pod를 순차 교체해 모든 복제본의 실제 이미지 식별값(digest 또는 런타임 imageID), 이미지에 포함된 패키지, 준비 상태를 대조합니다. 이전 Pod가 요청을 받지 않고 종료됐는지 확인한 뒤 정상 요청을 보냅니다. 호스트에 설치된 NGINX와 이미지 안의 NGINX는 각각 기록합니다.

HTTP/2 연결 중단

gRPC를 받는 서비스부터 찾아 두세요. gRPC 클라이언트는 HTTP/2에 의존합니다. 수정된 프록시로 해당 트래픽을 옮길 때는 기존 취약 리스너를 경유하거나 원본으로 직접 접속할 수 있는지도 확인합니다. gRPC를 계속 제공해야 해서 필요한 네트워크로만 접근을 제한했다면 허용 범위의 위험과 패치 일정을 기록하고, 정상 gRPC 호출을 확인합니다. NGINX gRPC 모듈 문서 ↗

http2 지시어는 HTTP/2 모듈을 포함한 NGINX 1.25.1부터 지원됩니다. 해당 설정 범위에 http2 off;를 적용하고, 같은 주소·포트를 쓰는 모든 listen 줄에서 기존 http2 인수도 제거하세요. 아래는 HTTPS 리스너의 관련 부분만 발췌한 예입니다. 운영 설정의 다른 인수와 인증서 설정은 유지합니다. HTTP/2 지시어와 지원 버전 ↗

# 1.25.1 이상, 해당 server 블록의 예
listen 443 ssl;
http2 off;

구형 버전에서는 listen 443 ssl http2;에서 http2만 제거해 listen 443 ssl;로 바꿉니다. IPv4·IPv6 리스너, 같은 주소와 포트를 공유하는 모든 가상 호스트, 내부 평문 포트도 확인합니다.

기본 systemd 서비스에서 설정만 변경했다면 아래처럼 검사 후 재적용합니다. 이전 워커는 기존 연결을 계속 처리할 수 있으므로 적용 전 PID·시작 시각과 대조해 이전 워커와 그 HTTP/2 연결이 모두 종료됐는지 확인합니다. 기존 연결이 남으면 해당 인스턴스의 트래픽을 빼고 연결을 정리한 뒤 재시작합니다. 설정 재적용 시 기존 워커의 동작 ↗

sudo /usr/sbin/nginx -t && sudo systemctl reload nginx

HTTPS 원본이 HTTP/2를 받던 환경이라면, HTTP/2를 지원하는 curl로 변경 전후에 같은 요청을 보냅니다. 아래 도메인·원본 IP·경로는 관리 중인 가상 호스트, 해당 인스턴스 주소, 평소 응답을 아는 읽기 전용 경로로 바꾸세요. --resolve는 TLS 이름과 인증서 검증을 유지하면서 연결할 원본을 지정합니다. curl 연결 주소 지정 ↗

curl --http2 --noproxy shop.example.com \
  --resolve shop.example.com:443:192.0.2.10 \
  -sS -o /dev/null -w 'HTTP/%{http_version} %{http_code}\n' \
  https://shop.example.com/

curl -V의 Features에 HTTP2가 있는 도구를 사용하세요. 변경 전에 HTTP/2였던 원본이 변경 후 HTTP/1.1과 예상 상태 코드를 반환하는지 봅니다. 인증서 오류, 시간 초과, 연결 실패는 차단 성공으로 집계하지 않습니다. 이 확인은 해당 HTTPS 주소·이름의 새 연결에만 적용됩니다. 다른 가상 호스트와 h2c 리스너는 각각 확인하세요.

HTTP/3·동적 DNS·메일 프록시

  • HTTP/3. 대상 주소의 listen … quic 리스너를 중단합니다. HTTP/3를 광고하는 Alt-Svc도 정리하고 UDP 리스너 상태를 확인합니다. 광고를 지운 뒤에도 리스너가 열려 있으면 기존 클라이언트가 직접 접속할 수 있습니다. TCP HTTPS 리스너의 정상 응답을 확인하세요. NGINX QUIC 설정 예시 ↗
  • 동적 DNS. 변수로 정하는 프록시 대상과 SSI·mirror 등 하위 요청의 관계를 확인해 같은 이름을 동시에 조회하는 경로를 제거하거나 해당 기능을 중단합니다. 고정된 백엔드 주소로 바꾼다면 서비스 탐색이나 장애 전환 때 주소가 어떻게 갱신되는지도 확인합니다.
  • 메일 프록시. 해당 리스너를 중단하거나 방화벽·보안 그룹에서 필요한 접속만 허용합니다. 메일 클라이언트의 연결과 인증을 확인하고, 접근을 허용한 범위와 패치 예정 시각을 기록합니다.

임시 조치마다 적용한 서버와 제한한 기능을 남기세요. 수정본과 새 워커를 확인한 뒤 단계적으로 기능을 복구하고, 원래 프로토콜로 정상 요청을 한 번 더 확인합니다.

Linux 호스트에서 SCTP를 따로 점검하기

SCTP는 Linux 커널이 지원하는 전송 프로토콜입니다. Xint는 11월 19일 기준 배포판 커널 업데이트가 아직 제공되지 않았다고 설명했습니다. 실제 작업 시에는 호스트 공급사의 최신 공지에서 수정 커널을 확인하세요. 컨테이너 환경이면 해당 Pod가 올라간 노드마다 실행 커널과 SCTP 상태를 기록합니다. Xint의 커널 대응 현황 ↗

uname -r
lsmod | grep '^sctp[[:space:]]'
grep -E '^(CONFIG_IP_SCTP=|# CONFIG_IP_SCTP is not set)' \
  "/boot/config-$(uname -r)"

CONFIG_IP_SCTP=m이면 필요할 때 로드할 수 있는 모듈이고, =y이면 실행 커널에 내장돼 있습니다. # CONFIG_IP_SCTP is not set은 해당 커널에서 기능을 빼고 빌드했다는 뜻입니다. lsmod에 항목이 없거나 설정 파일을 읽지 못했다면 그 결과만으로 미사용 판정을 내릴 수 없습니다. 실행 커널에 대응하는 설정을 공급사 방식으로 확인합니다.

모듈 방식이고 업무에서 SCTP를 쓰지 않는다고 확인한 경우에는 호스트의 /etc/modprobe.d/disable-sctp.conf에 다음 설정을 넣어 자동 로드를 막을 수 있습니다. install 줄은 다른 모듈이 의존성으로 SCTP를 불러오는 경우에도 적용됩니다. Red Hat의 커널 모듈 자동 로드 차단 절차 ↗

blacklist sctp
install sctp /bin/false

이미 로드된 모듈은 계속 동작합니다. 의존 서비스와 사용 중인 연결을 확인한 뒤 해제 또는 재부팅을 계획하세요. 초기 부팅 이미지(initramfs)에 포함된 환경은 배포판 절차에 따라 이미지를 갱신합니다. 조치 후에는 호스트에서 lsmod로 SCTP가 내려갔는지 확인하고, modprobe --show-depends sctp 출력에 차단용 install /bin/false가 반영됐는지도 봅니다. 이 조회는 모듈을 로드하지 않습니다. 커널 내장형은 공급사 완화책이나 수정 커널을 추적하고, 수정 커널을 설치한 뒤에는 실제 부팅한 커널까지 대조합니다. modprobe 조회 옵션 ↗

침해 흔적은 접속 로그 밖에서도 찾기

일반 access log는 웹 요청을 중심으로 남깁니다. HTTP/2 연결을 제어하는 프레임까지 충분히 기록하지 않기 때문에 평소와 같은 접속 로그만 남을 수 있습니다. 의심 징후가 있으면 재시작으로 휘발성 증거가 사라지기 전에 사고 대응 담당자와 격리·보존 순서를 조율하세요. NGINX2Root 연구팀 안내 ↗

오류 로그에서 반복되는 워커 종료 시각을 찾고, 같은 시간대에 NGINX가 실행한 예상 밖의 자식 프로세스와 외부 통신이 있었는지 대조합니다. 웹 파일·설정·예약 작업·서비스 등록 정보의 변경 이력도 살펴봅니다. 아래 예시에서 저널과 코어 덤프는 최근 하루, 파일 검색은 현재 오류 로그 전체가 대상입니다. 실제 노출 기간에 맞춰 회전된 로그와 보관본까지 확인하세요.

sudo journalctl -u nginx --since "24 hours ago" --no-pager
sudo grep -Ei 'worker process.*exited|signal 11|segfault' /var/log/nginx/error.log
sudo coredumpctl --since "24 hours ago" list nginx

정상 종료도 검색될 수 있으므로 신호·종료 코드와 배포 시각을 함께 봅니다. 코어 덤프나 감사 로그가 수집되지 않았다면 그 기간은 ‘자료 없음’으로 남깁니다. 뒤늦게 수집을 켜도 이전 실행 이력까지 복원되지는 않습니다.

침해가 확인되면 영향을 받은 시스템을 격리하고 증거를 보존합니다. 노출 가능성이 있는 자격증명을 신뢰할 수 있는 환경에서 교체하세요. 호스트 권한까지 침해됐다면 같은 호스트의 워크로드도 확인하고 신뢰할 수 있는 이미지로 복구합니다. 업데이트는 이후의 취약한 경로를 막는 조치이므로 이미 변경된 파일과 계정은 별도로 조사합니다.

어떤 증거가 있어야 대응을 마칠 수 있을까?

  • 대상과 기능. 서비스별 원본 서버, 프록시, 포함 제품과 모든 복제본을 목록화하고, 다섯 CVE마다 사용 기능과 외부·내부 노출 여부를 기록했습니다.
  • 설치와 실행. 패키지 전체 버전 또는 이미지 digest를 공급사 공지와 대조했습니다. 새 마스터와 워커의 기동 시각, 이전 프로세스·Pod의 종료를 확인했습니다.
  • 서비스 정상 동작. 로그인, 상품 조회, 업로드, 주문·결제 연동 등 해당 서비스의 정상 흐름을 승인된 테스트 거래나 상태 조회로 확인했습니다. 패치 전후 오류율도 대조했습니다.
  • 남은 노출. 임시 완화한 서버마다 제한한 기능, 담당자, 정식 패치 일정을 남겼습니다. SCTP는 호스트별 커널 수정 또는 완화 상태로 따로 기록했습니다.
  • 침해 조사. 조사한 기간과 로그 종류, 발견한 징후, 수집 공백과 필요한 후속 조치를 기록했습니다.

여러 서버의 결과를 AI로 취합할 때

사내에서 승인한 AI 환경에 서버별 점검 결과의 필요한 부분만 넣습니다. 전체 설정 덤프 대신 인증정보·고객 정보·내부 주소를 제거한 발췌본과 익명화한 자산 식별자를 사용하세요. 아래처럼 요청하면 미확인 서버를 다시 찾기 쉽습니다.

서버·Pod별 결과를 다음 열로 묶어줘.
대상 | 패키지 전체 버전·이미지 digest | 노출 기능·CVE | 공급사 수정 근거 |
실행 프로세스 교체 증거 | NGINX 상태 | 호스트 SCTP 상태 | 남은 조치·담당·기한

NGINX 상태는 ‘패치 완료’, ‘임시 완화’, ‘미조치’, ‘미확인’으로 구분해줘.
각 CVE에 공급사가 ‘영향 없음’으로 판정했다면 제품·버전과 근거를 적어줘.
공급사 자료끼리 판정이 엇갈리면 해당 CVE를 ‘미확인’으로 표시해줘.
‘패치 완료’는 해당 CVE 전체의 수정 근거, 실제 설치 버전, 실행 교체가 확인된 경우에만 써줘.
일부 경로만 제한했다면 다른 노출 경로를 남은 조치에 적어줘.
자료가 없는 칸은 ‘미확인’으로 남기고, 같은 호스트를 쓰는 Pod는 표시해줘.

마지막에는 운영자가 원래의 자산 목록과 표의 행을 대조합니다. 표에 아예 빠진 서버는 ‘미확인’ 표시조차 없기 때문입니다. 이 가이드의 명령과 표는 운영자가 사용할 예시이며, 개별 시스템의 패치 판정에는 그 시스템에서 확보한 증거가 필요합니다.
