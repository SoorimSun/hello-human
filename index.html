잘 만들어도 좋고, 실패해도 좋습니다. “해봤는데 이건 사람이 하는 게 낫더라”도 함께 나눌 만한 결과입니다.

WORKLESS ENGINEERING

Workless Engineering

Workless Engineering의 목표는 단순한 자동화가 아닙니다.

내가 반복해서 하는 일을 들여다보고,

  1. 01Human Driven
  2. 02AI Assisted
  3. 03AI Delegated
  4. 04Human on Exception

방향으로 다시 설계해봅니다. 모든 실험이 마지막 단계까지 가야 하는 것은 아닙니다. 작은 스크립트 하나로 귀찮은 일이 줄어도 충분합니다.

AI에게 모든 판단을 넘기자는 것도 아닙니다.

  • RuleRule로 해결할 일은 Rule로,
  • SoftwareSoftware로 해결할 일은 Software로,
  • AIAI가 필요한 곳에는 AI를 사용하고,
  • Human사람이 꼭 필요한 지점만 남기는 것이 목표입니다.

THINGS TO TRY

이런 거, 한번 붙여볼까요?

정해진 진도 없이, 끌리는 것부터.

아래는 함께 해볼 수 있는 아이디어입니다. 하나를 골라도 되고, 전혀 다른 것을 가져와도 됩니다.

EVERYDAY HACKS

“그래서 내가 할 게 뭔데?”

  • 회의 녹취에서 TODO와 결정사항을 정리하는 봇
  • 긴 메일 스레드에서 내가 할 일만 추려주는 Agent
  • 매번 만드는 SQL, curl, 테스트 데이터를 명령 한 줄로 생성하기
  • 반복해서 입력하는 명령어나 작업을 CLI 하나로 합치기

CODE DETECTIVE

“이 오류, 전에 본 것 같은데?”

  • 로그 몇 만 줄에서 이상한 패턴만 찾아오기
  • Git, 문서, 이슈 기록에서 비슷한 오류를 대신 뒤지기
  • PR의 변경 범위와 테스트 누락 후보를 먼저 훑기
  • Legacy Code의 구조와 의존성을 정리하기

PLUG IT IN

“이것도 연결되나?”

  • API 명세로 Mock Server나 테스트 케이스 생성하기
  • MCP 서버를 만들어 내가 쓰는 도구를 AI에 연결하기
  • 브라우저, 터미널, API를 함께 쓰는 개인용 Agent 만들기

JUST FOR FUN

“굳이? 그래도 궁금하니까.”

  • 작은 로컬 모델로도 충분한지 직접 비교해보기
  • 여러 Agent에게 역할을 나눠주고 정말 협업하는지 구경하기
  • 반복하는 루틴 중 “그냥 없애도 되겠는데?” 싶은 것 지워보기

조금 더 파고들고 싶다면

반복하는 일을 Workflow로 쪼개볼 수도 있습니다.

  1. Trigger
  2. Context
  3. Decision
  4. Action
  5. Validation
  6. Exception

그리고 각 단계에서 질문합니다.

  • 자동화할 수 있는가?
  • 기존 코드나 API로 해결할 수 있는가?
  • LLM의 판단이 필요한가?
  • Agent가 Tool을 호출하게 할 수 있는가?
  • 사람이 승인해야 하는 지점은 어디인가?
  • 실패하면 어떻게 복구할 것인가?

도구나 프레임워크는 그때그때 골라 씁니다. 직접 연결하고 실행해보면서 어디까지 맡길 수 있는지 확인합니다.

AT YOUR OWN PACE

2주 단위로, 각자의 속도로

기본 활동 주기는 2주 단위로 생각하고 있습니다. 매번 정해진 장소에 모이는 방식은 아니며, 상황에 따라 온라인으로 이야기하거나 오프라인으로 만납니다.

2주 동안 각자 관심 있는 것을 조금씩 만져보고, 공유할 만한 것이 생기면 올리고, 같이 이야기할 것이 있으면 편하게 모입니다.

TINKER

혼자 해도, 같이 해도

  • 각자 궁금한 기술을 조금씩 만져보기
  • 마음이 맞으면 함께 작은 PoC 만들기
  • 막힌 부분이나 웃긴 실패 기록하기
  • 시간이 나는 만큼만 참여하기

HANG OUT

보여줘도, 구경만 해도

  • 공유할 것이 생기면 편하게 올리기
  • 이야깃거리가 있으면 온·오프라인으로 만나기
  • 혼자 만든 것, 만들다 만 것 보여주기
  • 다른 사람의 삽질을 구경하기

↻ 2주는 느슨한 활동 리듬입니다. 제출 마감이나 발표 일정이 아닙니다.

모든 일정에 참석하거나 매번 결과물을 가져올 필요는 없습니다. 완성된 제품이 없어도, 이번에는 구경만 해도 괜찮습니다.

숙제나 진도보다는 각자의 관심과 상황에 맞게 참여합니다.

ONE LESS THING

Workless Challenge

무엇부터 해볼지 고민된다면 “다시는 직접 하고 싶지 않은 일” 하나를 골라보세요. 해보고 싶은 사람끼리 시도하는 작은 실험입니다.

예를 들어, 공개된 샘플 로그와 예제 코드로 이런 흐름을 만들어볼 수 있습니다.

30분이 걸리던 일을 사람이 5분만 확인하도록 만들 수 있을지 실험합니다. 위 시간은 실험을 설명하기 위한 가정입니다.

SHOW YOUR EXPERIMENT

그래서, 뭐가 덜 귀찮아졌나요?

멋진 발표 자료보다 직접 해본 이야기가 궁금합니다. 공유할 때 이런 질문을 곁들여볼 수 있습니다.

관점함께 나눌 이야기
Human Time내가 쓰던 시간이 얼마나 줄었나요?
Human Touch매번 손대던 단계가 없어졌나요?
Cycle Time기다리는 시간까지 줄었나요?
Success Rate다시 돌려도 잘 되던가요?
Exception어디서는 사람이 하는 게 더 낫던가요?
Cost들인 시간과 비용에 비해 쓸 만했나요?

모든 항목을 측정하거나 성과를 증명할 필요는 없습니다. 실패한 이유, 예상 밖의 동작, “그냥 재미있었다”는 이야기도 환영합니다.

COME HANG OUT

이런 생각, 해보셨나요?

  • “이거 굳이 내가 계속 해야 하나?”
  • “이거 Agent한테 시키면 안 되나?”
  • “이거 자동으로 돌아가게 만들면 재밌겠는데?”
  • “일단 붙여보면 되지 않을까?”

AI 경험 수준은 중요하지 않습니다. 위 생각을 한 번이라도 해봤다면 잘 맞을 것 같습니다. 능숙하게 만드는 사람도, 처음 설치해보는 사람도, 다른 사람의 실험이 궁금한 사람도 함께할 수 있습니다.

첫 모집은 소규모, 선착순으로

초기에는 운영 방식을 함께 잡아가는 단계인 만큼 원활한 운영을 위해 소규모로 시작하며, 첫 모집은 선착순으로 진행합니다.

인원이 너무 많아지면 이야기보다 관리가 먼저 생길 수 있습니다. 서로의 실험을 충분히 보고 이야기할 수 있는 규모로 시작하고, 운영이 안정되면 참여 범위를 점차 넓히려고 합니다.

처음부터 완성된 운영 방식을 갖추기보다는, 함께 참여하는 사람들의 관심과 상황에 맞춰 조금씩 만들어갑니다.

START SMALL, STAY CURIOUS

회사에서 시작하지만,
회사에만 머물 필요는 없으니까요.

처음에는 사내에서 작게 시작합니다. 운영 방식이 자리 잡고 함께 실험할 주제가 쌓이면, 향후에는 회사 밖의 엔지니어들도 참여할 수 있는 기술 커뮤니티로 조금씩 열어보려고 합니다.

외부와 함께할 때는 회사 내부 정보나 고객 정보가 아닌, 공개 가능한 기술, 코드, 사례와 개인 프로젝트 중심으로 운영할 생각입니다.

같은 회사라는 접점에서 시작해, 같은 호기심으로 이어지는 작은 Engineering Community.
