01 / OPENAI · CHATGPT WALLET

상품과 금액을 승인하면,
에이전트가 결제를 이어갑니다

OpenAI는 11월 13일 ChatGPT Wallet을 발표했습니다. American Express·Mastercard·Visa와 협력한 결제 기능으로, 초기에는 미국의 만 18세 이상 ChatGPT Pro 사용자 중 적격 미국 발행 카드를 가진 사람에게 dots를 통해 순차 제공됩니다. OpenAI 발표 ↗

현재 도움말은 dot과의 대화에서만 사용할 수 있다고 설명합니다. 일반 Chat·Work·독립된 Codex 대화에는 제공되지 않습니다. 미국 거주·카드의 미국 청구지 주소가 필요하며, 적격 사용자도 아직 기능이 열리지 않았을 수 있습니다. 제공 조건 ↗

승인 후에는 카드번호·보안코드·만료일 형태의 결제 토큰이 발급됩니다. 에이전트와 판매자에게 실제 카드정보를 전달하지 않으면서 선택한 카드로 청구하는 방식입니다. 적격 거래에는 기존 리워드와 분쟁 보호도 유지된다는 설명입니다. 금액·상품 종류·기간을 정해 구매를 미리 위임하는 방식은 향후 구상입니다.

승인 화면을 통과했다고 주문까지 확정된 것은 아닙니다. OpenAI 도움말도 승인 완료와 판매자의 주문 확정을 구분합니다. 결과가 불명확하면 다시 시도하기 전에 판매자 확인을 살펴보도록 안내합니다. 정기결제에 동의한 경우에는 그 조건에 따라 판매자가 후속 청구를 할 수 있으므로, 매 구매 승인이라는 설명을 모든 후속 청구에 대한 재승인 보장으로 읽어서는 안 됩니다. 구매 승인과 주문 결과 ↗

쇼핑몰은 기존 주문·결제 시스템을 연결합니다

함께 공개한 Commerce Partner Playbook은 상품 피드, 브라우저 접근, 결제, 플러그인을 나눠 설명합니다. 기존 웹 결제창에는 Wallet 전용 통합이 필수는 아닙니다. 다만 CDN·방화벽이 Web Bot Auth로 서명된 요청을 인식하는지, 위험관리 업체가 정상적인 에이전트 구매를 차단하지 않는지 확인할 수 있습니다. 플러그인이나 WebMCP로 재고·장바구니 같은 구조화된 기능을 제공하는 경로도 안내했습니다. 결제 지원 문서 ↗

우리 업무에 대입하면, 자연어 구매 요청을 주문 준비로 연결할 입구가 하나 늘어난 셈입니다. 최종 가격·재고 확인, 주문 상태, 취소·환불은 여전히 업무 서비스가 관리해야 합니다. 특히 응답이 끊겼을 때 성공 여부를 추측하지 않고 확인하는 절차가 필요합니다. 뒤의 작은 실험은 이 지점을 다룹니다.

02 / GOOGLE · ANTIGRAVITY /TEAMWORK

작업자의 설명을 따라 읽기보다,
별도 맥락에서 결과를 검증합니다

Google Research는 11월 13일 Gemini 4 계열과 Antigravity /teamwork를 활용한 수학·과학·시스템 개발 성과를 소개했습니다. 이번 소식은 /teamwork의 첫 출시가 아니라 추가 연구 결과입니다. 이미 8월 27일에도 다중 에이전트 구조를 설명했습니다. 새 연구 발표 ↗

핵심은 작업과 검증에 들어가는 맥락을 나누는 것입니다. 작업 에이전트에는 필요한 파일·도구를 주고, 비평·감사 에이전트는 작업자의 추론을 그대로 넘겨받지 않은 상태에서 결과를 확인합니다. 반례를 찾는 검증 수단으로 Lean 4, 변경하지 않은 테스트, 시뮬레이터와 하드웨어 측정 등을 사용합니다.

정확성을 맞춘 뒤, 느린 코드를 다시 고쳤습니다

대표 사례는 AV1 영상 디코더 libgav1의 C++ 코드를 Rust로 옮긴 작업입니다. Google은 약 17만 줄을 작성해 적합성 테스트에서 비트 단위 결과 일치를 확인했다고 밝혔습니다. 처음에는 원본보다 약 4배 느렸지만, 프로파일링과 반복 최적화 뒤 성능이 개선됐다는 설명입니다.

Google의 샘플 영상·x86-64 및 ARM 환경 측정입니다. 다른 코드의 Rust 전환에서도 같은 개선이 난다는 뜻은 아닙니다. 측정 맥락 ↗

외부 개발자는 Antigravity에서 /teamwork와 /boost를 사용할 수 있다고 밝혔습니다. 다만 이번 글에 나온 재작성 패턴과 정형 증명 등 일부 특화 워크플로는 추가 제공 예정입니다. 연구에 등장한 모든 절차가 현재 제품에 그대로 들어 있다고 보기는 어렵습니다.

개발팀이 가져올 만한 아이디어는 테스트를 고정한 채 구현만 바꾸고, 정확성 통과 뒤 성능을 재는 순서입니다. 검증 에이전트를 추가하더라도 무엇을 통과해야 완료인지 정해 두어야, 서로 동의하는 답변과 실제로 동작하는 결과를 구분할 수 있습니다.

03 / GGML-ORG · LLAMA.CPP 1.0

실행 엔진을 올릴 때,
호환성 변화를 버전으로 읽습니다

ggml-org는 11월 13일 libllama와 libggml v1.0.0을 공개했습니다. llama.cpp에서 모델을 실행하는 라이브러리와 그 아래 텐서 연산 라이브러리의 릴리스입니다. 앞으로 API·ABI가 호환되지 않는 변경은 주 버전에 반영하겠다고 밝혔습니다. 개발팀 발표 ↗

공개 C API를 중심으로 정한 버전 변경 규칙 · ggml-org 발표를 정리
바뀌는 번호어떤 변경인가요
MAJOR
주 버전		include/의 공개 C API와 호환되지 않는 변경. API·ABI 비호환을 주 버전으로 알린다고 설명합니다.
MINOR
부 버전		하위 호환을 유지하는 기능·API 추가, 백엔드 업데이트, 모델 지원
PATCH
패치 버전		API 변경이 없는 버그 수정

API가 호출 코드의 약속이라면, ABI는 이미 컴파일한 프로그램과 라이브러리가 맞물리는 약속입니다. 개발자는 버전 번호로 변경의 크기를 가늠하고, 재빌드와 회귀 검사 범위를 정할 수 있습니다.

이번 1.0에는 실제 호환성 변경도 있습니다. llama.cpp 릴리스는 폐기 예정이던 공개 API 제거를, ggml 릴리스는 기존 API·연산 제거와 RPC 프로토콜 변경을 안내합니다. 번호만 올려 배포하기 전에 사용하는 바인딩·함수·원격 실행 구성이 영향을 받는지 살펴볼 필요가 있습니다.

로컬 모델을 업무 도구에 붙여 쓰는 팀이라면 모델 파일과 실행 엔진 버전을 함께 고정해 두는 편이 좋겠습니다. 같은 입력에서 응답 구조, 도구 호출 결과, 메모리 사용량과 지연이 어떻게 바뀌는지 비교하고 이전 버전으로 돌아갈 경로도 준비할 수 있습니다.

개발팀의 하드웨어·모델 지원 소개 영상 ↗공식 발표의 두 영상은 지원 범위를 소개합니다. 이번 호에서는 호환성 판단에 필요한 버전 규칙을 표로 정리했습니다.

04 / GOOGLE · GEMINI & WALLET

금융정보를 연결해 분석하되,
돈을 움직이는 권한은 주지 않습니다

Google은 11월 13일 미국의 Gemini 앱 사용자에게 Google Wallet 연결을 순차 제공한다고 발표했습니다. 웹·Android·iOS가 대상이며 연결은 선택 사항입니다. Plaid로 은행·카드 계좌를 Wallet에 연결하면 분석에 활용할 정보를 넓힐 수 있습니다. Google 발표 ↗

사용자는 지출 흐름을 차트로 보거나, 계속 내고 있는 구독료와 가격 인상을 찾아달라고 요청할 수 있습니다. 연결은 읽기 전용입니다. Gemini가 계좌 정보를 읽을 수 있어도 자금을 이동·관리·투자할 수는 없으며, 사용자는 연결을 끌 수 있습니다.

ChatGPT Wallet

사용자가 구매를 승인하고, dot이 결제 토큰으로 구매를 진행합니다.

Gemini의 Google Wallet 연결

연결된 금융정보를 읽고 지출·예산을 분석합니다. 이번 연결로 자금을 움직이지 않습니다.

Google은 개인화에 쓰는 선호·관심사·목표를 확인하고 수정하는 Memory Summary 확대도 함께 소개했습니다. 금융 분석을 업무에 응용한다면, 결과에 거래 근거를 붙이는 일이 유용하겠습니다. 가령 계좌 간 이체를 소비로 중복 집계하거나 일회성 결제를 구독으로 분류했다면 원장과 대조해 바로잡을 수 있어야 합니다.

정산 자료를 읽어 차이를 찾아주는 도구도 같은 방식으로 시작할 수 있습니다. 분석에는 조회 권한을 주고, 정산금액을 실제로 바꾸는 기능은 별도로 승인·검증하도록 설계하는 것입니다.

OUR VIEW / 헬로우 휴먼의 해석

맡길 수 있는 일 옆에,
완료를 확인할 기준을 둡니다

네 소식은 서로 다른 문제를 다룹니다. ChatGPT Wallet은 구매 결제, Gemini 연결은 금융정보 분석이고, Antigravity는 연구·개발 결과의 검증, llama.cpp는 실행 라이브러리의 변경 관리입니다.

업무 설계에 가져올 공통 질문은 있습니다. 무엇을 허용했고, 어떤 근거로 끝났다고 판단할 것인가입니다. 구매에는 승인 내역과 거래 상태가, 코드 변경에는 고정된 테스트와 성능 측정이, 금융 분석에는 원본 거래가 필요합니다. 모델이 바뀌어도 이 기준은 남겨 두고 다시 확인할 수 있어야 합니다.

Workless Engineering에서 줄이고 싶은 것은 사람이 같은 결과를 여러 번 확인하고 복구하는 시간입니다. 실행 횟수보다, 확인 가능한 결과를 남긴 업무가 얼마나 늘었는지를 살펴보면 좋겠습니다.

OUR LAB / 아직 실행하지 않은 실험 제안

결제는 됐는데 응답이 끊겼다면,
다시 결제하지 않고 복구합니다

가상 주문 O-042의 총액 42,000원을 사용자가 승인했습니다. 모의 결제사는 청구에 성공했지만, 성공 응답이 오기 직전에 연결이 끊깁니다. 이때 고객이 “다시 해줘”라고 요청합니다. 기대 결과는 주문 한 건·청구 한 건을 유지하고, 기존 거래를 확인해 완료를 알리는 것입니다. 42,000원은 상태 검증을 위한 가상 금액입니다.

11월 3일의 견적 변경·재승인 실험, 11월 7일의 채널 간 장바구니 실험에 이어, 이번에는 외부 결제 상태와 내부 주문 상태가 잠시 어긋난 경우를 확인합니다. 실제 Wallet·카드·결제망에 연결하지 않고 주문 서비스와 모의 결제사만 만듭니다.

모델의 재시도 판단과 서비스의 상태 확인을 나눠 비교합니다

A는 모의 결제 시간 초과를 일반 실패로 처리하고, 재요청 때 새 결제를 생성하는 기준선입니다. B는 같은 모델·지침·주문을 사용하되, 서비스가 최초 시도와 키를 저장하고 상태 조회·동일 키 재전송·중복 알림 제거를 담당합니다. 모델에는 카드정보 대신 주문 ID와 확인된 상태만 전달합니다. 두 방식의 차이는 이 연결 코드로 한정합니다.

모의 결제사는 같은 키와 같은 요청이면 저장한 결과를 반환하고, 같은 키에 금액·통화·주문 내용이 달라지면 거절하도록 만듭니다. 키의 보관 기간은 평가 기간보다 길게 둡니다. 기록이 없다고 답한 경우에도 곧바로 새 키를 만들지 않고, 조회 지연을 반영한 재확인 또는 동일 키 재전송만 허용합니다.

접수 전 연결 실패동일 키로 재전송해 청구 1건을 만듭니다. 새 시도를 중복 생성하지 않습니다.
성공 응답만 유실기존 성공 거래를 조회해 완료합니다. 청구는 1건입니다.
조회 실패·알림 지연확인 중을 유지합니다. 확인 기한을 넘기면 사람의 대조 대상으로 남기고 추가 청구하지 않습니다.
성공 알림 중복 도착거래 ID로 중복을 제거해 주문 완료·후속 출고 이벤트를 각각 한 번만 기록합니다.

별도의 조정용 4건으로 구현을 맞춘 뒤 평가용 12건을 고정합니다. 같은 오류 발생 위치·알림 순서로 A와 B를 실행하고, 모델이 답한 문장이 아닌 모의 결제 원장과 주문·출고 이벤트 기록을 정답과 대조합니다. 고정 모델 응답으로 상태 전이를 먼저 확인한 다음 실제 모델 요청을 평가하면 두 오류 원인을 나누기 쉽습니다.

12건 중 기대 상태와 일치한 건수, 주문별 중복 청구·출고 건수, 확인 중을 잘못 완료로 안내한 건수, 복구 시간과 사람이 대조한 시간을 기록합니다. 중복 처리나 잘못된 완료 안내가 한 건이라도 있으면 채택을 보류합니다. 입력·오류 재생 파일, 모델·지침 버전, 원장 대조기와 상태 변경 로그를 남겨 다음 변경에서도 반복 확인할 수 있게 합니다.
