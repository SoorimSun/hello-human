01 / OPENAI · 레거시 코드 전환

새 언어로 옮겨도
같은 결과가 나와야 합니다

OpenAI는 10월 19일 COBOL·Fortran 등 학습에 활용할 공개 코드와 문서가 상대적으로 적은 언어에서 코딩 성능이 얼마나 나아졌는지 발표했습니다. 오래전부터 써온 업무 시스템을 레거시 시스템이라고 하는데요. 이런 시스템을 유지하거나 새 언어로 옮기는 데 모델이 얼마나 도움이 되는지 살펴본 연구입니다. OpenAI 발표 ↗

평가는 두 가지입니다. 첫 번째인 MultiLangBench에서는 20개 언어로 SQLite라는 데이터베이스와 호환되는 프로그램을 만들게 합니다. 모델에 설명 문서와 테스트를 제공한 뒤, 만든 프로그램이 데이터를 처리한 결과를 실제 SQLite의 결과와 비교합니다. MultiLangBench 평가 방식 ↗

두 번째인 COBOL 전환 평가에서는 기존 프로그램을 C++·Java·Kotlin·Python·Rust로 옮깁니다. 바뀐 프로그램의 출력이 기존과 바이트 단위까지 같고, 모든 테스트를 통과해야 성공으로 인정합니다. 즉, 실행되는 코드를 만드는 데서 그치지 않고 같은 입력에 같은 결과가 나오는지 확인하는 평가입니다. COBOL 전환 평가 기준 ↗

아래 그래프의 ‘추론 노력’은 모델이 답을 도출하는 과정에 얼마나 많은 계산을 쓰도록 할지 정하는 설정입니다. 같은 평가 안에서는 이 설정을 맞춰 모델 간 점수를 비교했습니다.

비용도 달라졌습니다. OpenAI에 따르면, 추론 노력을 낮게 설정한 평가에서 GPT-6.1 Sol의 작업당 API 사용 비용은 GPT-5.6 Sol보다 39% 적었습니다. 이는 평가를 수행하며 모델을 호출하는 데 든 비용의 차이입니다. API 요금 자체나 전체 전환 프로젝트의 비용이 그만큼 줄었다는 뜻은 아닙니다. 실제 업무에 적용하려면 전문가 검토와 업무 규칙, 다른 프로그램과의 연결 관계를 반영한 테스트가 필요합니다.

계산이 끝났다는 것만으로 충분할까요?

가상의 주문 계산기를 떠올려보겠습니다. 할인액이 10.9원일 때 기존 정책이 소수점을 버려 10원을 적용했다면, 새 코드가 11원으로 반올림하는 순간 결과가 달라집니다. 오류 없이 실행돼도 같은 업무를 수행했다고 볼 수 없습니다.

이런 차이를 찾으려면 어떤 입력에 어떤 결과가 나와야 하는지부터 정리해야 합니다. 기존 동작을 그대로 옮기는 일과 업무 규칙을 고치는 일을 따로 진행하면, 결과가 달라졌을 때 원인을 찾기가 쉽습니다.

02 / AWS · TORCHNEURON & DEEPGRAM

다른 칩으로 옮긴 뒤에도
실행 효율을 다듬어야 합니다

코드의 언어를 바꾸는 일과 함께, 코드를 실행할 칩을 바꾸는 시도도 이어지고 있습니다. AWS는 10월 19일 PyTorch 블로그에서 TorchNeuron을 소개했습니다. AI 모델 개발 도구인 PyTorch로 작성한 코드를 AWS의 AI 연산용 칩 Trainium2·Trainium3에서 실행하도록 연결해 주는 소프트웨어입니다. TorchNeuron 공식 소개 ↗

AWS는 실행 장치 설정을 바꿔 기존 PyTorch 작업을 옮길 수 있다는 점을 강조했습니다. 10월 20일 공개 베타 출시를 예고했으며, 자료 확인 시점에는 베타 버전과 Apache 2.0 오픈소스 라이선스가 공개 저장소에 표시돼 있었습니다. TorchNeuron 저장소 ↗

다만 지원하지 않는 연산은 일반 계산을 담당하는 CPU로 넘어갈 수 있습니다. 입력 데이터의 크기가 달라지면 코드를 실행 가능한 형태로 다시 변환하는 ‘재컴파일’이 필요할 수도 있습니다. 따라서 NVIDIA 전용 코드를 포함해 모든 코드가 그대로 옮겨진다고 보기는 어렵습니다. 현재 지원 범위와 제약 ↗

Deepgram 사례가 보여주는 추가 작업

AWS와 음성인식 기업 Deepgram은 같은 날 음성인식 모델 Nova-3를 Trainium2로 옮긴 과정도 공개했습니다. 녹음된 음성을 모아서 처리하는 ‘오프라인 배치’ 작업이 대상입니다. 두 팀은 수개월에 걸쳐 코드가 실행되는지 확인하고, 인식 정확도를 비교하고, 느린 연산을 개선한 뒤 기존 서비스에 연결했습니다. AWS·Deepgram 적용 사례 ↗

이 사례를 보면 다른 칩에서 코드를 실행하는 데 성공한 뒤에도 개선할 부분이 남습니다. 실행 환경을 고를 때는 같은 정확도를 유지하면서 같은 비용으로 얼마나 처리할 수 있는지 살펴야 합니다. 처음 옮기는 작업과 이후 유지보수에 드는 노력도 함께 고려할 필요가 있습니다.

03 / MODAL · NVIDIA VERA CPU

에이전트가 도구를 쓸 때는
실행 환경도 중요합니다

에이전트가 일을 마치려면 모델의 답을 받는 것 외에도 파일을 찾고, 코드를 실행 가능한 프로그램으로 만들고, 테스트를 돌리는 과정이 필요합니다. 이런 작업을 다른 환경과 분리해 실행하는 공간을 샌드박스라고 합니다. 여러 샌드박스가 한 서버에서 동시에 돌아가면 CPU와 메모리를 쓰기 위해 기다리는 시간이 생길 수 있습니다.

클라우드 실행 환경을 제공하는 Modal은 이 문제와 관련해 10월 19일 NVIDIA Vera CPU의 초기 시험 결과와 도입 계획을 공개했습니다. Vera는 Arm 방식으로 명령을 처리하는 CPU입니다. Modal은 이를 지원하려면 기존 시스템과 실행 환경을 미리 묶어 두는 이미지의 제작 방식도 바꿔야 한다고 설명했습니다. Modal 기술 발표 ↗

핵심은 여러 작업이 몰릴 때 같은 시간에 처리할 수 있는 양이 늘었다는 점입니다. 특정 장비와 시험 조건에서 나온 결과이므로, 모든 CPU나 에이전트 작업에 ‘두 배’라는 수치를 적용할 수는 없습니다.

우리 업무에서도 모델의 응답을 기다리는 시간, 도구가 실행되는 시간, 외부 서비스나 사람의 검토를 기다리는 시간을 나눠 볼 수 있습니다. 오래 걸리는 단계가 어디인지 알면 모델을 바꿀지, 실행 환경을 개선할지 판단하기가 쉬워집니다.

04 / 미국 DHS · 모델 사용 범위

내가 쓰는 서비스 안에는
어떤 모델이 들어 있을까요?

실행 성능뿐 아니라 어떤 모델을 쓸 수 있는지도 점검해야 할 때가 있습니다. 미국 국토안보부(DHS)는 연방 민간기관의 구매 대상에서 DeepSeek 관련 제품·서비스를 제외하고, 사용 중인 정보기술 시스템에서도 제거하도록 한 기존 명령을 공고했습니다. 서명된 부록에 따르면 원 명령은 2026년 7월 24일 발행된 제2026-01호입니다. 이 명령을 담은 공고는 10월 19일 사전 공개됐고, 10월 20일 연방관보에 정식으로 실렸습니다. 서명된 명령 부록 ↗

다른 회사의 제품도 포함됩니다

구매 대상에서 제외하고 시스템에서 제거해야 하는 범위에는 DeepSeek와 관계사의 제품뿐 아니라, DeepSeek를 적용해 다른 회사가 개발한 제품·서비스도 들어갑니다. 겉으로 보이는 서비스 이름만으로는 적용 여부를 판단하기 어려운 이유입니다.

대상 기관은 미국 연방 민간기관입니다. 미국의 모든 민간기업이나 개인에게 적용되는 금지는 아닙니다. 국가안보 시스템과 보안 구획 정보시스템도 이번 DHS 명령의 범위에서 제외되며, 부록은 국방·정보당국의 별도 권한을 설명합니다.

즉시 조치가 원칙입니다

부록은 명령 발행 직후 구매·조달 대상에서 제외하고, 사용 중인 시스템에서는 제거하거나 예외를 신청하도록 규정합니다. 기관이 승인한 제품 목록, 서비스 제공업체의 장비 목록, 전자상거래 장터 등에서도 제외해야 합니다.

기관은 적용을 면제받거나 이행을 늦춰 달라고 요청할 수 있습니다. 이때는 명령 발행일부터 60일 이내에 서면으로 신청해야 합니다. 어떤 제품에 어떤 예외가 필요한지, 기관의 업무에 어떤 영향이 있는지, 위험을 줄이기 위해 대신 무엇을 할 것인지 등을 제시하고 심사를 받는 절차입니다.

따라서 60일은 예외 신청 기한입니다. 모든 기관에 60일 동안 제품을 계속 써도 된다는 유예를 준 것은 아니며, 10월 공고일부터 새로 계산하는 기간도 아닙니다. 요구 조치와 예외 신청 절차 ↗

완전히 제거하기 전까지는 네트워크 통신을 살피고, 활동 기록을 더 자세히 남기며, 데이터 유출을 막는 임시 보안 조치도 권고합니다.

DHS는 중국 내 서버와 정부의 정보 접근 가능성, 민감한 입력 정보의 전송, 보안 취약점 등을 명령의 근거로 들었습니다. 이는 DHS의 위험 판단을 담은 것이며, 모든 DeepSeek 모델에서 악성코드가 확인됐다는 의미는 아닙니다.

우리 업무에 연결해 보면 서비스 안에서 어떤 모델을 쓰는지 기록해 두는 일이 중요합니다. 모델 이름과 버전, 사용하는 업무, 실행 위치를 알아야 사용 조건이 바뀌었을 때 영향을 파악하고 교체 여부를 검토할 수 있습니다.

HELLO, HUMAN! · 우리의 해석

바꿀 수 있는 것과
지켜야 할 것을 함께 기록하기

새로운 기술을 도입할 때는 성능 수치와 함께 기존 업무에 미칠 영향도 살펴야 합니다. 이번 소식에서 다룬 코드 전환, 실행 환경, 모델 사용 조건을 우리 업무의 질문으로 바꾸면 다음과 같습니다.

각 소식을 우리 업무의 질문으로 바꾸면
바꾸는 대상함께 확인할 것
프로그램 언어계산·오류·빈 데이터 처리 결과가 유지되는가?
실행 칩정확도와 비용 효율, 이전·유지보수 부담은 어떤가?
동시 실행 환경작업이 몰릴 때 처리량과 개별 대기시간은 어떤가?
사용 모델어느 업무에서 쓰며, 사용 조건이 바뀌면 교체할 수 있는가?

Workless Engineering 관점에서는 코드와 함께 검증 기준을 남기는 일도 중요합니다. 업무 규칙, 입력과 출력의 예시, 검증 결과를 기록해 두면 다음에 시스템을 바꿀 때도 활용할 수 있습니다. 같은 내용을 처음부터 다시 확인하는 수고를 줄이는 방법입니다.

CLUB EXPERIMENT · 모임에서 해볼 실험

가상 주문 계산기의
바뀌면 안 되는 결과를 찾아보세요

아직 진행하지 않은 실험이지만, 모임에서 작은 계산 프로그램 하나로 시작해 보면 어떨까요? 실제 사내 코드나 고객 데이터 대신, 주문금액·할인 한도·배송비를 계산하는 가상의 프로그램과 입력값을 준비합니다. 개발자가 아닌 멤버도 “이 조건이면 얼마가 나와야 하는가”를 정리하는 역할로 참여할 수 있습니다.

  1. 기준 결과를 남깁니다. 최소 주문금액보다 조금 적거나 많은 금액, 할인 한도에 걸리는 금액, 소수점이 있는 값, 아무 값도 넣지 않은 경우를 시험합니다. 각각의 결과를 저장해 비교 기준으로 삼습니다. 이런 방식을 ‘골든 마스터 테스트’라고 부릅니다.
  2. 계산 부분을 옮깁니다. AI에게 해당 부분을 다른 언어로 바꾸도록 요청한 뒤, 같은 입력값을 넣어 기존 프로그램과 결과를 비교합니다.
  3. 차이의 원인을 기록합니다. 코드를 옮기다 생긴 오류인지, 기존 업무 규칙 자체의 문제인지 구분합니다. 기존 규칙을 고칠 필요가 있더라도 코드 전환과는 별도 작업으로 남겨둡니다.

사람이 직접 옮긴 경우와도 비교해 보세요. 결과가 얼마나 일치하는지, 사람이 어떤 부분을 다시 확인했는지, 완료까지 얼마나 걸렸는지 기록하면 됩니다. 목표는 OpenAI의 평가 점수를 재현하는 것이 아니라, 코드가 바뀌어도 지켜야 할 결과를 정하고 검증하는 연습입니다.
