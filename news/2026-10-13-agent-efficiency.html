토큰은 AI가 글을 나누어 처리하는 단위입니다. 위 세 소식은 서로 다른 기술을 다루며, 하나의 제품에 함께 적용된 사례는 아닙니다.

이번 호30초 요약오래 일하는 모델같은 전력으로 더 많이계산 기록의 저장헬로우 휴먼의 관점모임에서 해볼 실험읽은 자료

원문에 2026년 10월 12일로 표기된 세 발표와 관련 자료를 10월 13일 한국시간 기준으로 확인했습니다. 기업이 설명한 기능과 전망, 외부 기관의 평가, 연구팀의 실험 결과를 나누어 소개합니다.

AI에게 여러 단계의 일을 맡기면, 답변 하나의 정확도 못지않게 작업을 끝까지 마무리하는 능력이 중요해집니다. 처음 정한 조건을 기억하고, 중간에 오류가 나면 다시 시도해야 하니까요. 이번 세 소식도 일을 끝내는 능력과 그 과정에 드는 시간·비용을 중심으로 살펴보겠습니다.

01 / MUSE WONDER

앞서 정한 조건을 기억하고
막혀도 작업을 이어가는 모델

Meta는 10월 12일 Muse Wonder와 Muse Wonder Full을 공개했습니다. 복잡한 업무와 코딩처럼 여러 단계를 거쳐야 하는 작업을 위한 AI 모델입니다. Wonder는 다른 프로그램에서 모델을 불러 쓰는 Meta Model API와 코딩 도구 Muse Code에서 제공합니다. 일반 사용자용 Muse에는 구독자부터 순차적으로 적용할 예정이라고 밝혔습니다. Meta 공식 발표 ↗

기억을 이어가고, 막히면 다른 방법을 찾습니다

Meta가 강조한 능력은 두 가지입니다. Active Memory는 여러 대화에서 나눈 중요한 내용을 기억하고, 지금 하는 일에 필요한 정보를 다시 찾는 능력입니다.

Active Focus는 어려운 작업에서도 목표를 향해 계속 시도하는 능력입니다. 한 방법이 막히면 다른 방법을 찾고, 새 정보나 오류가 생기면 이에 맞춰 작업을 이어갑니다. Meta는 모델이 필요할 때 질문하고, 중요한 행동 전에는 사용자에게 확인하도록 훈련했다고 설명합니다. Meta 연구 블로그 ↗

상품 등록을 예로 들어 보겠습니다. 처음 전달한 확인 기준을 AI가 기억하고, 실패한 단계를 다시 시도한다면 사람이 같은 설명을 반복할 일이 줄어들 수 있습니다. 다만 기억해 둔 조건이 지금도 유효한지는 별개의 문제입니다. 재고나 쿠폰 정책처럼 바뀌는 정보는 업무 시스템에서 확인해야 합니다.

이런 기능 설명과 함께 외부 평가 결과도 살펴보겠습니다. 다음은 평가기관 Artificial Analysis가 공개한 세 모델의 점수입니다.

평가 이름과 모델 설정 살펴보기

평가 이름은 Artificial Analysis Intelligence Index v4.3.2입니다. 전체 모델 순위가 아니라 이 기사에서 다루는 세 모델의 결과를 골라 비교했습니다.

원문에 적힌 실행 설정 이름은 Claude Opus 5.5가 max with fallback, Muse Wonder Full과 Muse Wonder가 각각 max입니다. 그래프의 점수는 각 모델을 이 설정으로 평가한 결과입니다.

긴 코딩 작업을 다룬 Meta의 SWE-Marathon은 위 그래프와 별도의 평가입니다. 여기에는 다른 회사의 코딩 에이전트 제품으로 실행한 결과도 포함돼, 모든 모델을 같은 도구로 비교한 것은 아닙니다. 이런 조건의 차이도 살펴본 뒤, 도입 전에 우리가 쓸 언어와 도구, 확인 기준으로 시험해 봐야 합니다. Muse Wonder 모델 카드 ↗

이용 경로와 API 가격 살펴보기

공식 개발자 페이지에 안내된 Wonder의 API 가격은 100만 토큰당 입력 4달러, 캐시 입력 0.20달러, 출력 20달러입니다. 입력은 모델에 보내는 내용, 출력은 모델이 생성한 내용입니다. 캐시 입력은 저장해 둔 입력을 재사용하는 경우를 말합니다. 토큰 수는 글자 수와 정확히 일치하지 않습니다.

Full은 위 API 가격표에 포함되지 않습니다. Muse Code의 Power Usage 또는 Maximum Usage 구독에서 제공합니다. 공식 이용 경로·가격 ↗ Artificial Analysis는 두 모델을 가중치가 공개되지 않은 독점 모델로 분류합니다. 가중치는 모델이 학습한 내부 값을 말합니다.

이 단가만으로 업무 한 건의 총비용을 알 수는 없습니다. 에이전트가 모델에 여러 번 요청하거나 외부 도구를 사용하면 비용이 더 들 수 있습니다.

Meta가 공개한 게임 제작·일정 계획 데모 보기 ↗Meta가 골라 공개한 시연입니다. 모임에서 같은 결과를 직접 확인한 것은 아닙니다.

02 / AZURE MAIA 300

같은 전력으로
더 많은 AI 요청을 처리하려면

Microsoft도 10월 12일 자체 AI 추론 시스템 Azure Maia 300을 발표했습니다. 추론은 학습을 마친 AI가 사용자의 요청을 받아 답을 만드는 과정입니다. Maia 300은 긴 문맥을 다루거나 여러 단계를 거치는 에이전트 작업을 고려해 설계됐습니다. 실제 도입은 2027년부터 시작할 계획입니다. 현재 운영 실적으로 소개된 내용은 이전 세대인 Maia 200의 이야기입니다. Microsoft 공식 발표 ↗

Microsoft는 계산 장치와 메모리, 통신, 실행 소프트웨어를 함께 설계해 데이터를 주고받는 부담을 줄이겠다고 설명합니다. 이를 통해 기대하는 처리량 증가를 아래 두 수치로 제시했습니다.

더 많이 처리한다고, 내 일이 그만큼 빨라질까요?

위 수치는 시스템 전체의 처리량에 관한 것입니다. 요청 하나의 결과를 받기까지 기다리는 시간은 지연시간이라고 부릅니다. 전체 처리량이 늘어나더라도, 내 요청의 대기 시간이 같은 비율로 줄어들지는 않습니다.

상품 100건을 분석하는 에이전트를 떠올려 보면 쉽습니다. AI가 답을 빨리 만들어도 상품 정보를 불러오거나 외부 시스템의 응답을 기다리는 데 오래 걸리면, 전체 작업은 여전히 느릴 수 있습니다. 따라서 위 수치를 그대로 업무 시간 절감률이나 API 요금 인하율로 받아들이기는 어렵습니다.

03 / REPLAYSSM

계산용 기록을
매번 통째로 저장하지 않는 방법

NVIDIA와 프린스턴대 Dao AI Lab 연구진은 ReplaySSM이라는 방법으로 모델이 답변을 만드는 과정을 개선했습니다. 논문은 10월 9일 arXiv에 처음 등록됐고, NVIDIA의 기술 해설은 10월 12일 공개됐습니다. 논문과 등록 이력 ↗

AI가 답변을 이어 만들 때는 앞서 처리한 정보를 참고해야 합니다. 상태 공간 모델(SSM)은 그 정보를 고정된 크기의 계산값으로 압축해 둡니다. 아래에서는 이 내부 상태를 ‘계산용 기록’이라고 부르겠습니다. 대화 내용을 기억하는 Muse Wonder의 기능과는 다른 개념입니다.

기술 용어와 그림의 조건 살펴보기

ReplaySSM이 주기적으로 저장하는 내부 상태를 체크포인트, 그 사이의 입력값을 모아 두는 공간을 버퍼라고 합니다. 그림의 ‘작은 메모’는 이 입력값 기록을 가리킵니다.

그림은 입력을 16토큰씩 모으는 설정(L=16)에서, 저장된 체크포인트와 빈 버퍼로 시작하는 예시입니다. 전체 기록의 저장 횟수가 줄어도, 읽고 쓰는 데이터 전체가 16분의 1로 줄어드는 것은 아닙니다.

이전 토큰을 참고하는 Attention 방식과 SSM을 함께 쓰는 모델을 하이브리드 모델이라고 부릅니다. 아래 성능 실험은 이런 모델을 대상으로 했습니다.

연구팀은 저장 방식을 바꾼 뒤, 계산 일부와 답변 생성 과정 전체가 각각 얼마나 빨라지는지 측정했습니다.

실험에 쓴 모델과 장비 살펴보기

그림의 ‘내부 계산 일부’는 SSM 계산 커널, ‘답변을 이어 만드는 과정 전체’는 일반 디코딩 단계 전체를 가리킵니다.

40억 매개변수(4B) 모델 두 개는 H100, 1,200억 매개변수(120B)급 모델 두 개는 B300에서 측정했습니다. 매개변수는 모델이 학습한 내부 값이며, H100과 B300은 AI 계산에 쓰는 장치 이름입니다.

계산용 기록은 32비트 정밀도(FP32)로 저장하고, 최근 입력은 16토큰씩(L=16) 모았습니다. 배치 크기는 토큰이 이어진 묶음(시퀀스)을 동시에 몇 개 처리하는지 나타내며, 위 그림에서는 이해하기 쉽게 ‘동시에 만드는 답변 수’로 풀어 썼습니다.

연구팀은 다음에 나올 토큰을 미리 제안하고 한꺼번에 검증하는 추측 디코딩도 별도로 시험했습니다. 위 그림과는 실행 조건이 다릅니다.

B300에서 120B급 모델 두 개를 배치 512로 실행했을 때, 처리량은 기존 vLLM의 추측 디코딩 대비 각각 1.85배와 2.10배였습니다. 수학 문제 모음인 GSM8K를 사용하고 한 번에 토큰 4개를 제안한 조건에서 나온 결과입니다. 실험 조건, 그림 4 ↗

이 결과는 AI가 답변을 만드는 과정에서 얻은 것입니다. 문서를 불러오고 도구를 실행하는 시간까지 포함한 업무 전체의 속도는 따로 확인해야 합니다.

NVIDIA는 TensorRT-LLM·vLLM·FlashInfer 같은 실행 소프트웨어와의 통합, 일부 모델의 실제 서비스 적용도 소개했습니다. 도입할 때는 우리가 쓸 모델과 실행 소프트웨어가 이를 지원하는지 확인해야 합니다.

OUR VIEW

AI가 오래 일하는 만큼
우리의 반복 업무도 줄어들려면

헬로우 휴먼은 이런 발전이 우리의 반복 업무를 얼마나 줄여 줄지에 주목합니다. AI가 한 시간 동안 작업한다고 사람의 일이 한 시간 줄어드는 것은 아닙니다. 잘못된 판단을 반복하거나 이미 확인한 정보를 다시 찾는 데 시간을 쓸 수도 있으니까요.

그래서 먼저 “어디까지 해야 이 일이 끝난 것인가”를 정해 두면 좋겠습니다. 정확도와 걸린 시간, 사용한 자원을 이 기준에 맞춰 살펴봐야 기술의 발전이 우리 업무에도 도움이 됐는지 판단할 수 있습니다.

AI에게 반복 확인을 맡기고 사람은 예외와 최종 결과를 살피도록 역할을 나눌 수 있습니다. 이때 이미 확인한 정보를 AI가 매번 다시 살피고 있지는 않은지도 돌아볼 만합니다. 다음 실험에서는 이전 결과를 다시 활용해 반복 작업을 줄일 수 있는지 알아봅니다.

TRY TOGETHER

100개 중 10개만 바뀌었다면,
어디까지 다시 확인할까요?

가상 상품 100개의 판매 기간에 오류가 없는지 AI로 확인한 뒤, 그중 10개의 판매 기간만 바뀐 상황을 가정해 봅시다. 나머지 90개 상품과 확인 기준, 판단에 참고하는 정보는 그대로입니다. 이 상황에서 아래 두 방식을 비교합니다.

이 순서로 해보면 됩니다

  1. 100개를 한 번 확인하고 결과를 저장합니다. 상품마다 번호를 붙이고, 판매 시작일과 종료일을 확인하도록 AI에 요청합니다. 첫 결과는 정답과 맞는지 확인한 뒤 저장합니다. 이 준비에 든 시간과 비용은 따로 적어 둡니다.
  2. 10개의 판매 기간만 바꿉니다. 바꾼 상품 번호를 기록하고, 일부에는 시작일이 종료일보다 늦은 오류를 넣습니다. 다른 상품의 정보가 없어도 판단할 수 있는 기준을 씁니다.
  3. 바뀐 내용을 반영해 A와 B를 실행합니다. AI 모델과 요청문을 같게 맞추고, 상품은 한 건씩 처리합니다. A에는 100개를, B에는 기록해 둔 10개만 보냅니다. B의 새 결과 10개는 이전 결과 90개와 합칩니다.

마지막에는 두 방식이 만든 100개 결과를 같은 정답표와 비교합니다. 오류를 놓치거나 정상 상품을 잘못 지적한 경우가 없는지 봅니다. 시간과 비용은 다시 확인하기 시작한 때부터 최종 결과를 완성할 때까지 측정합니다. B는 바뀐 상품을 고르고, 이전 결과를 불러와 합치는 과정까지 포함합니다.

확인 기준도 그대로여야 합니다. 기준이나 공통으로 참고하는 정보가 바뀌면, 수정하지 않은 상품도 영향을 받을 수 있습니다. 그때는 영향을 받는 상품 전체를 다시 확인해야 합니다.

이 실험은 ReplaySSM의 기술 성능 실험과는 별개입니다. 평소 쓰는 AI로 시작해도 됩니다.
