30초 요약

  • Beam 적은 연산으로 높은 성능을 내는 데 초점을 맞춘 모델입니다. 모델 실행에 필요한 가중치는 10월 중 공개할 예정입니다.

  • Together Link 쓰던 코딩 도구에 다른 모델을 연결합니다. 실제 비용이 얼마나 줄어드는지는 업무별로 비교해야 합니다.

10월 2~5일의 공식 발표와 개발 문서를 2026년 10월 6일 한국시간 기준으로 확인했습니다. 날짜는 원문 표기를 따릅니다. 성능·비용 수치는 각 회사의 발표이며, 제품을 직접 실행해 측정하지는 않았습니다.

AI에게 자료 조사를 맡겼는데 같은 검색을 반복한다면 언제 멈춰야 할까요? 작업 도중 오류가 나면 처음부터 다시 해야 할까요? AI가 여러 단계를 거쳐 일을 처리할수록, 어떤 모델을 쓸지와 함께 얼마나 맡기고 어떻게 관리할지도 정해야 합니다.

이번에 살펴볼 네 소식은 이 문제를 서로 다른 방향에서 다룹니다. 연산을 줄이는 모델부터 사용량과 권한을 관리하는 플랫폼, 모델을 바꿔 연결하는 도구, 작업 기록을 남기는 기능까지 나왔습니다. 이 글에서 말하는 ‘운영 계층’은 AI를 업무에 연결하고 비용·권한·진행 상황을 관리하는 장치들을 뜻합니다.

01 / REFLECTION BEAM

Beam, 적은 연산으로
높은 성능을 내는 데 초점을 맞춥니다

Reflection은 10월 5일 코딩과 추론, 에이전트 작업을 위한 모델 Beam을 발표했습니다. 모델을 실행하는 데 필요한 학습된 수치, 즉 가중치를 공개하는 오픈웨이트 방식으로 제공할 예정입니다. 공식 발표 ↗

Beam은 입력에 따라 모델의 일부만 골라 계산하는 MoE 구조를 사용합니다. 아래 수치에서 파라미터는 모델이 학습한 수치를, 토큰은 글을 나누어 처리하는 단위를 뜻합니다.

전체 파라미터
5,010억 개모델 전체에 저장된 수치
토큰당 활성 파라미터
230억 개토큰 하나를 처리할 때 쓰는 수치

회사는 일부 추론 평가에서 GLM 5.2와 비슷한 성능을 더 적은 연산으로 냈다고 설명합니다. 코딩·터미널 평가 중에는 Kimi K3와 DeepSeek V4.1 Flash 등이 앞선 항목도 있습니다. 이번 발표에서 눈여겨볼 점은 필요한 성능을 내면서 연산을 얼마나 줄일 수 있느냐입니다.

연산에 참여하는 파라미터가 적으면 계산량을 줄이는 데 도움이 됩니다. 다만 전체 모델을 저장할 메모리는 여전히 필요합니다. 회사가 제시한 연산량도 입력 처리와 서비스 운영에 드는 연산 일부를 뺀 추정치여서, 실제 이용 요금이 같은 비율로 줄어든다고 볼 수는 없습니다.

Beam은 어떤 규모로 학습했을까요?

Reflection은 NVIDIA GB300 GPU 1만500개를 4주간 사용해 1억 회 넘는 강화학습 실행 기록을 생성했다고 밝혔습니다. 코딩·도구 사용·과학 및 수학 문제 등을 위한 환경도 약 100만 개 마련했다고 설명합니다. 모두 회사 발표값입니다.

이런 실행 기록을 rollout이라고 합니다. 모델이 문제를 풀기 위해 행동하고 결과를 받는 과정을 담습니다. 자료로 학습하는 사전학습에 더해, 직접 시도하고 피드백을 받는 훈련에도 큰 규모의 자원을 투입한 것입니다.

가중치는 10월 중 공개 예정입니다

발표 당시 Beam은 최종 안전성 시험과 평가를 진행 중이었으며, 사전 이용 신청을 받고 있었습니다. 가중치와 기술 보고서, 모델 설명서, 개발 도구는 10월 중 공개할 예정이라고 밝혔습니다. 직접 운영하는 데 필요한 장비와 이용 조건은 배포 자료가 나온 뒤 확인해야 합니다.

일반뉴스 07에서 소개한 Reflection의 공개 계획에 이어, 이번에는 모델의 이름과 사양이 나왔습니다. 게임·지도·개발 작업 예시는 Reflection이 선정한 데모에서 볼 수 있습니다.

02 / COHERE NORTH 2

North 2, 에이전트의 사용량과
권한을 관리합니다

Cohere가 10월 5일 소개한 North 2는 기업이 AI 에이전트를 업무에 활용하고 관리하는 플랫폼입니다. 여러 단계로 이루어진 일을 자동화하고, 반복 업무에 필요한 기능과 지식을 다시 쓸 수 있도록 돕습니다. 공식 한국어 발표 ↗

반복해서 쓰는 업무 기능은 Skills로, 함께 참고할 지식은 Libraries로 관리합니다. Memory는 새 대화에서도 이전 업무의 배경을 기억하게 해주는 기능입니다.

관리자용 North Admin에서는 누가 얼마나 사용했는지 살피고, 사용자와 에이전트의 권한을 정할 수 있습니다.

USAGE / 얼마나 쓰는가사용량 확인과 한도 설정

사용자·에이전트별 사용량을 확인합니다. 일정 시간에 허용할 요청·토큰 수와 사용자·조직별 한도를 관리합니다.

ACCESS / 무엇을 할 수 있나모델 사용과 실행 권한

사용할 모델과 역할별 권한을 정합니다. 중요한 결정이나 행동에는 사람이 관여하도록 설정할 수 있습니다.

이런 관리가 필요한 이유는 한 번의 지시가 여러 번의 검색과 도구 실행으로 이어질 수 있기 때문입니다. 오류가 나서 재시도하면 사용량도 늘어납니다. 따라서 업무 한 건에 어느 정도의 사용량을 허용하고, 언제 멈출지를 정해야 합니다.

업무를 이어갈 때는 기억 기능과 처리 기록도 구분해야 합니다. 예를 들어 고객 문의의 배경을 기억하더라도, 답변을 이미 발송했는지는 별도의 기록으로 확인해야 중복 처리를 막을 수 있습니다.

Cohere는 자체 설비나 가상 사설 클라우드, 외부망과 분리된 환경에서 운영하는 선택지도 안내합니다. 도입할 때는 선택한 환경에서 필요한 모델과 연결 도구를 쓸 수 있는지, 사용량 한도가 어떻게 적용되는지 확인해야 합니다.

헬로우 휴먼의 해석

사용량을 확인하는 화면은 관리의 시작입니다. 한도에 가까워지면 알릴지, 요청을 늦출지, 실행을 멈출지도 정해야 합니다. 중단된 일을 누가 이어받을지까지 정해두어야 실제 업무에서 쓸 수 있습니다.

03 / TOGETHER LINK

익숙한 코딩 도구에
다른 모델을 연결하는 방법

Together AI는 10월 5일 Together Link를 소개했습니다. 쓰던 코딩 도구를 유지하면서 Together가 제공하는 다른 모델을 연결할 수 있게 해주는 도구입니다. 공식 발표 ↗

코딩 에이전트에서는 모델이 코드나 다음 행동을 제안하고, 이를 둘러싼 작업 환경이 파일을 읽거나 명령을 실행합니다. 실행 승인과 대화 기록도 이 환경에서 관리합니다. 이처럼 모델을 실제 작업에 연결하는 환경을 하네스(harness)라고 부릅니다. Together Link는 이 환경에 연결할 모델을 바꾸는 역할을 합니다.

10월 6일 확인한 공식 문서에서는 베타로 안내하고 있습니다. 지원 앱은 Claude Code·Claude Desktop·Codex·ChatGPT Desktop·OpenCode·Pi이며, 설치하려면 macOS 또는 Linux와 Together API 키가 필요합니다. 설치·지원 조건 ↗

사용 기록에서는 한 작업 세션에서 쓴 토큰과 비용을 볼 수 있습니다. Together는 비용을 “50% 이상 절감”할 수 있다고 주장합니다. 다만 비교 화면에는 같은 토큰 사용량에 모델별 가격을 대입한 계산이 포함돼 있습니다. 같은 일을 같은 품질로 끝내는 데 든 비용을 비교한 결과로 보기는 어렵습니다. 사용 기록·지원 앱 안내 ↗

실제 비용을 비교하려면 실패한 작업의 재시도와 사람이 수정한 시간까지 살펴야 합니다. Together API 사용료와 기존 도구의 구독료도 각각 계산해야 합니다.

모델이 바뀌는 시점은 공식 자료마다 설명이 다릅니다

요청을 처리할 모델을 고르는 과정을 라우팅이라고 합니다. 10월 5일 발표 글과 제품 페이지는 첫 요청에서 모델을 고른 뒤 같은 작업 세션 동안 유지한다고 설명합니다. 반면 10월 6일 확인한 개발 문서는 요청마다 모델을 고른다고 안내합니다. 어느 설명이 현재 동작과 일치하는지는 확인하지 못했습니다.

따라서 실제 비교에서는 요청마다 어떤 모델을 썼는지, 이전 계산을 재사용하는 캐시가 얼마나 적용됐는지 기록해야 합니다. 모델을 한 번만 고르거나 캐시가 계속 유지된다고 가정하기는 어렵습니다.

개발 문서에 따르면 Anthropic API 키를 사용하는 Claude 계열 세션에서는 Opus도 선택할 수 있습니다. Codex·OpenCode·Pi·ChatGPT Desktop은 Together 모델을 사용합니다. 라우팅 문서 ↗

04 / GITHUB AGENTIC WORKFLOWS

GitHub, 할 일과 처리 기록을
대화 밖에 남깁니다

GitHub Agentic Workflows는 코드 저장소에서 할 일을 글로 적으면 에이전트가 실행하도록 연결하는 도구입니다. 실행에는 GitHub의 자동화 서비스인 GitHub Actions를 사용합니다. 10월 5일 주간 업데이트에서는 10월 3일에 사전 공개한 v0.90.3을 중심으로 최근 변경 사항을 소개했습니다. v0.90.3 릴리스 ↗

눈에 띄는 기능은 작업 대기열인 work queue와 기록 저장소인 ledger입니다. 대기열은 앞으로 처리할 일과 순서를 관리합니다. 장부에 해당하는 ledger는 실행 중 생긴 정보를 모델과의 대화 밖에 저장합니다. 대화가 끝나도 다음 실행에서 참고할 기록을 남길 수 있는 것입니다.

v0.90.3에는 Git을 이용해 대기열을 관리하는 명령이 추가됐습니다. 장부에는 로그, 집합, 이름과 값을 짝지은 데이터, 표, 횟수를 세는 카운터 등 여러 형태로 정보를 저장할 수 있습니다.

도구 호출 한도와 권한 설정은 어디에 적용될까요?

v0.90.3에는 한 번의 실행에서 도구를 호출할 수 있는 횟수를 제한하는 기능도 포함됐습니다. 릴리스에 명시된 적용 대상은 Copilot SDK(개발 도구 모음)를 기반으로 한 에이전트입니다. 호출 횟수 제한만으로 토큰 사용량이나 시간, 금액까지 모두 제한할 수는 없습니다.

GitHub App의 접근 범위를 워크플로 파일 변환 단계에서 명시하도록 하고, Claude의 외부 도구 연결 설정을 더 엄격하게 적용하는 변경도 있습니다. 주간 업데이트에 함께 소개된 감사 자료와 위협 탐지 결과 기록은 v0.90.1에서 개선된 기능입니다. 공식 주간 업데이트 ↗

헬로우 휴먼의 해석

하던 일을 이어가려면 무엇을 끝냈고, 실제로 무엇을 변경했으며, 다음에 어디서 시작해야 하는지 알 수 있어야 합니다. 이런 정보를 대화와 별도로 기록해두면 다음 실행의 기준으로 삼을 수 있습니다.

05 / OS PERMISSIONS

AI 앱이 읽을 수 있는 파일,
운영체제의 권한도 확인해야 합니다

권한 관리는 앱 설정에서 끝나지 않습니다. Apple은 10월 2일 macOS의 전체 디스크 접근 권한(Full Disk Access)에 추가 통제를 도입하겠다고 발표했습니다. 백업 앱 등에 필요했던 이 권한은 파일뿐 아니라 메일·메시지·브라우징 기록에도 폭넓게 접근할 수 있게 합니다. Apple은 AI 에이전트가 스스로 더 많은 행동을 할수록 이 권한의 위험도 커진다고 설명합니다. Apple Developer 원문 ↗

Apple은 사용자가 이 권한을 줄 때 명확하게 동의하도록 절차를 바꿀 계획입니다. 앞으로 도입할 변경이며, 해당 공지에서는 적용 버전과 일정, 구체적인 승인 화면까지 확인할 수는 없습니다.

에이전트의 행동 규칙＋플랫폼의 계정·도구 권한＋OS의 파일 접근 권한

AI에게 어떤 일을 허용할지 정할 때는 앱 안의 규칙과 계정 권한, 운영체제의 파일 접근 권한을 함께 살펴야 합니다. 앱 내부의 설정만으로는 그 앱이 실제로 어디까지 읽을 수 있는지 알기 어렵기 때문입니다.

모델을 바꿔도
업무 규칙과 기록은 유지되어야 합니다

Reflection은 모델이 쓰는 연산을 줄이고, Cohere는 기업의 사용량과 권한을 관리합니다. Together는 쓰던 도구에 다른 모델을 연결하고, GitHub는 할 일과 처리 기록을 남깁니다. 이 소식들을 함께 보면 AI를 업무에 쓰려면 모델 성능과 운영 방식을 함께 살펴야 한다는 점이 드러납니다.

어떤 모델을 쓰든 업무의 완료 기준과 승인 절차, 처리 기록은 유지할 수 있어야 합니다. 이런 규칙을 모델과 분리해두면 모델을 바꿀 때마다 업무 절차 전체를 다시 만들 필요가 줄어듭니다. 다만 새 모델이 도구를 제대로 사용하고, 정해진 형식으로 답하며, 실패에 적절히 대응하는지는 다시 확인해야 합니다.

Workless Engineering이 줄이려는 것은 사람이 되풀이하는 일입니다. AI가 한 번 좋은 답을 냈는지에 더해, 오류를 고치고 다시 지시하는 시간까지 줄었는지 살펴야 합니다. 비용과 처리 기록을 남기는 이유도 실제로 일이 줄었는지 판단하기 위해서입니다.

SMALL EXPERIMENT

같은 작업 20개로
일을 끝내는 데 드는 비용 비교하기

이 차이를 확인하기 위해 모임에서 작은 비교 실험을 해볼 수 있습니다. 아직 실행하지 않은 제안입니다. 가상의 Java/Spring 프로젝트에 작업 20개를 준비합니다. 데이터 전달용 객체를 추가하거나 테스트를 작성하는 작은 작업 10개, 여러 기능에 걸친 오류를 찾거나 변경의 영향을 분석하는 복잡한 작업 10개로 나눕니다.

  1. 작업 분류와 완료 기준을 먼저 정합니다. 각 작업의 기대 결과, 확인할 테스트, 재시도 횟수와 시간 한도를 미리 적습니다. 작업 난이도도 결과를 보기 전에 분류합니다.
  2. 같은 20개를 두 방식으로 실행합니다. 한쪽은 모든 작업에 고성능 모델을 씁니다. 다른 쪽은 미리 정한 규칙에 따라 모델을 고릅니다. 두 방식 모두 같은 코드와 도구 권한으로 시작하고, 캐시 사용 조건도 기록합니다.
  3. 실패한 시도와 사람이 도운 시간도 기록합니다. 자동 테스트 결과와 사람의 최종 검토 결과를 각각 남깁니다. 더 강한 모델로 재시도한 비용과 사람이 고친 시간도 해당 작업에 포함합니다.
성공률
미리 정한 완료 기준을 충족한 작업 수 ÷ 전체 20개
작업당 모델 비용
실패·재시도를 포함한 총 API 비용 ÷ 전체 20개
완료 시간
대기와 재시도를 포함해 끝날 때까지 걸린 시간. 미완료 작업은 별도 표기
사람이 쓴 시간
검토·수정·재지시에 실제로 든 시간
모델 선택이 적절했는지
저비용 모델의 실패·모델 변경 비율과 두 방식의 결과 품질 비교

성공 한 건당 모델 비용도 함께 계산합니다. 실패와 재시도를 포함한 총 API 비용을 완료 기준을 통과한 작업 수로 나누는 값입니다. 이렇게 해야 실패한 시도의 비용까지 반영할 수 있습니다. 성공이 한 건도 없으면 이 값은 계산하지 않고, 전부 실패했다고 기록합니다.

사람이 검토하고 수정한 시간은 별도로 비교합니다. 시간까지 금액으로 환산하려면 두 방식에 같은 시간당 비용을 적용하고, 계산 기준을 밝혀야 합니다.

결과를 볼 때는 비용과 함께 실패에 대응하는 방식도 살펴봅니다. 저비용 모델의 실패를 빨리 발견했는지, 더 강한 모델도 풀지 못한 일을 사람에게 넘겼는지, 정한 예산 안에서 멈췄는지가 그 기준입니다.

AI에게 일을 맡길 때는
끝내는 데 드는 비용과 멈춰야 할 조건도 함께 정해봅시다.
