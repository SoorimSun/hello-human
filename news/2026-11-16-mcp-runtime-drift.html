Corelight가 짚은 MCP, 버전은 같아도 실행 환경은 바뀐다

MCP 서버의 버전을 고정했는데 하위 라이브러리는 달라졌습니다. Corelight의 관찰과 Claude Fable 5.2의 코드 그림 시연을 통해, 실행 환경과 작업 과정을 어떻게 확인할지 살펴봅니다.

2026년 11월 16일 월요일헬로우 휴먼 AI뉴스한국시간 기준
이번 호30초 요약MCP의 숨은 변경코드로 그리는 Fable헬로우 휴먼의 관점실행 환경 비교 실험읽은 자료

AT A GLANCE

30초 요약

  • MCP의 설치 경로 서버 버전을 고정해도 새 환경을 만들 때 하위 패키지를 다시 고르면 실행 코드가 달라질 수 있습니다.
  • Claude Fable 5.2 개발자들이 코드를 써서 가상 붓질을 쌓는 그림 시연을 공개했습니다. 사람의 지시와 중간 결과를 보며 고치는 과정도 담겼습니다.
  • 우리의 확인 과제 같은 요청에 같은 결과가 나왔는지와, 같은 실행 환경을 썼는지를 따로 기록하고 비교합니다.

자료 확인 2026년 11월 16일 기준. Corelight의 11월 10일 조사와 이를 인용한 CSA의 11월 15일 연구 노트, Fable 개발자들의 공개 게시물·대화를 확인했습니다. 아래 발표일은 원문 기준이며 X 게시물 날짜는 한국시간입니다.

01 / CORELIGHT · MCP

설정 파일은 그대로인데
함께 실행되는 코드는 바뀝니다

Corelight는 관리자 작업 환경의 MCP 서버를 살펴보다가, 같은 릴리스·커밋에서 5주 동안 15종의 종속성 구성이 쓰인 사례를 보고했습니다. 여기서 종속성은 서버와 함께 설치되는 라이브러리입니다. 새 침해사고 보고가 아니라, 설치 구성이 달라지는 현상을 관찰한 조사입니다. Corelight 원문 ↗

CSA는 이 조사를 바탕으로 상위 버전 고정과 전체 실행 환경 고정의 차이를 짚었습니다. Corelight가 고른 서버 35개 중 23개는 권장 설치 경로에서 시작·설치·이미지 빌드 시 공개 저장소의 종속성을 다시 결정할 수 있었습니다. 선정 표본의 설치 방식이며 전체 MCP 서버의 피해 비율은 아닙니다. CSA 연구 노트 ↗

매번 내려받는 것은 아닙니다

uvx 같은 실행 도구는 캐시에 저장한 환경을 다시 사용합니다. uv 공식 문서도 캐시를 지우거나 갱신하면 환경을 새로 만든다고 설명합니다. 그때 허용된 버전 범위 안에서 하위 패키지를 다시 고를 수 있습니다. uv의 캐시·도구 환경 설명 ↗

저장소에 잠금 파일이 있어도 실제 설치 명령이 그 파일을 읽어야 합니다. npm에서도 배포 패키지에는 일반적인 package-lock.json이 포함되지 않으며, 배포용 잠금 파일인 npm-shrinkwrap.json은 별도입니다. 설치 경로를 확인해야 하는 이유입니다. npm 잠금 파일 문서 ↗

고정한 뒤에도 업데이트할 사람이 필요합니다

Corelight는 서버 5개의 전체 종속성을 고정하고 설치한 프로그램을 직접 실행했습니다. 이후 2주간 총 457회 시작한 뒤 비교한 패키지 목록은 최초 설치 때와 같았다고 보고했습니다. 패키지 목록의 일치를 확인한 결과이며 모든 업무 결과가 같았다는 뜻은 아닙니다.

CSA는 고정한 버전도 취약해질 수 있으므로 업데이트 절차를 함께 두라고 권고합니다. 변경 내용을 검토해 다시 설치하고, 도구에는 필요한 권한만 주는 방식입니다. 에이전트가 자동으로 시작하는 프로그램에도 같은 관리가 필요합니다.

02 / CLAUDE FABLE 5.2

그림을 그리는 코드를 쓰고
붓질을 쌓아 갑니다

11월 15일 The Decoder는 Anthropic 개발자들의 코드 그림 시연을 소개했습니다. Fable 5.2의 모델 발표는 11월 9일이었고, 아래 두 시연은 한국시간 11월 10일에 게시됐습니다. 새 이미지 생성 제품의 출시 소식과는 구분해서 볼 만합니다.

Jake Eaton은 Fable이 Python 프로그램으로 붓의 질감과 물감의 움직임을 다루며, 외부 이미지 모델이나 미리 렌더링·트레이싱한 이미지를 쓰지 않았다고 설명했습니다. 사람이 의견과 방향을 주면 Claude가 붓·물감 엔진을 수정한 과정도 밝혔습니다. 제작자의 설명 ↗

되돌리기 없이 고치는 과정을 공개했습니다

Michael Graczyk은 ‘해 뜰 무렵 나뭇가지에 앉은 새’를 그리게 했습니다. 공개 대화에는 잘못 그린 흔적을 남기고 다음 붓질로 이어 가라는 지시가 있습니다. Claude는 중간 캔버스를 확인했고, 가늘게 나온 새의 등을 더 굵은 붓질로 덮었다고 설명합니다.

공개 대화에서는 한 붓질을 색상·폭·좌표 경로로 표현하고, 결과를 본 뒤 다음 선을 정하는 흐름을 읽을 수 있습니다. 코드를 실행하고 화면을 확인하는 과정이 결과물의 일부인 셈입니다. 다만 여기서는 제작자의 대화와 시연을 확인했으며, 실행 코드를 재현하거나 전용 이미지 모델과 성능을 비교하지는 않았습니다.

OUR VIEW

다시 맡길 수 있으려면
무엇이 달라졌는지 알아야 합니다

MCP 사례는 같은 설정 뒤에서 실행 코드가 바뀌는 문제이고, Fable 시연은 코드를 만들고 결과를 보며 다음 행동을 정하는 사례입니다. 그림 시연이 MCP의 위험을 해결해 주는 것은 아닙니다. 두 소식에서 가져올 공통 질문은 실행 과정을 나중에 얼마나 설명할 수 있는가입니다.

도구의 환경을 고정해도 입력 데이터나 모델의 판단은 달라질 수 있습니다. 반대로 결과가 우연히 같아도 내부 라이브러리는 바뀌었을 수 있습니다. 실행 환경의 목록과 작업 결과의 검증 기록을 나눠 두면, 문제가 생겼을 때 어디부터 살필지 정하기 쉬워집니다.

OUR LAB · 아직 실행하지 않은 실험 제안

같은 상품 무게를 읽게 하고
도구의 구성이 바뀌는지 봅니다

가상 상품의 무게 0.5 kg을 읽어 500 g으로 돌려주는 작은 MCP 도구를 준비합니다. 서버 코드는 그대로 두고, 단위를 읽는 하위 라이브러리만 새 버전으로 바꿔 봅니다. 지난 호의 실행·비용 기록 대조에 이어, 이번에는 캐시가 사라진 뒤에도 검토한 구성이 유지되는지 확인합니다.

A는 서버 버전만 고정하고 하위 라이브러리는 1.x 범위에서 선택하게 합니다. B는 전체 버전과 파일 해시를 잠근 뒤 한 번 설치하고 그 프로그램을 직접 실행합니다. 운영체제·런타임·패키지 관리자 버전은 같게 두고, 캐시 상태를 기록합니다.

1.1 추가 뒤 확인할 기대 상태. 측정 결과가 아닌 실험 설계입니다.
실행 조건구성 확인결과·실패 확인
A · 캐시 재사용기존 구성이 유지되는지 확인같은 결과만 보고 새 설치도 같을 것이라 판단하지 않습니다.
A · 새 환경 설치1.1이 선택되는지 확인구성 변경과 함께 0 g이라는 결과가 기대값 500 g과 다르다는 오류를 찾습니다.
B · 직접 재시작1.0과 승인한 파일 해시 유지정상 입력과 오류 입력이 모두 기존 기대 상태와 같아야 합니다.
B · 해시가 다른 설치 파일잠금 정보와 불일치격리된 재설치 검사에서 중단합니다. 다른 버전으로 몰래 대체하지 않습니다.

최종 평가에는 kg 입력 4건, g 입력 4건, 잘못된 단위 2건, 값 누락 2건을 고정합니다. 위 네 조건을 각각 3회 반복하되, 설치가 거부된 회차에서는 업무 요청을 보내지 않습니다. 조정용 입력은 따로 둡니다.

통과 기준은 B의 정상 재시작 3회에서 구성 차이 0건, 회차마다 기대 상태 12/12건 일치입니다. 해시 불일치는 3회 모두 실행 전에 막아야 합니다. A의 새 환경에서 의도한 변경이 선택되지 않으면 ‘차이 없음’으로 끝내지 않고 캐시·버전 선택 조건부터 확인합니다.

구현 범위와 남길 기록

테스트용 MCP 서버, 단위 변환 라이브러리 2개 버전, 로컬 패키지 저장소, 설치·재시작 실행기와 결과 대조기를 만듭니다. 먼저 모델 없이 고정된 도구 호출로 비교해 설치 방식의 효과를 봅니다.

각 회차에 서버 커밋, 전체 패키지 버전, 잠금 파일·배포 파일의 해시, OS·런타임·설치 도구, 캐시 상태를 남깁니다. 설치 파일의 해시 확인과 설치 뒤 파일 비교는 구분하며, 패키지 목록만으로 동일 파일임을 단정하지 않습니다.

구성 차이, 기대 상태 일치 건수/12건, 시작 시간과 오류 조사 시간을 기록합니다. 시간 초과·패키지 누락·해시 불일치는 별도 실패로 남기고 자동 대체 설치는 끕니다. 최종 산출물은 입력·정답 파일, 두 설치 설정, 실행별 구성 명세와 차이 보고서입니다.

Workless Engineering에서 줄이고 싶은 것은 사람이 같은 문제를 다시 조사하는 시간입니다. 검토한 도구 환경과 결과를 대조할 기록이 남아 있으면, 다음 변경 때도 그 기준을 이어 쓸 수 있습니다.
