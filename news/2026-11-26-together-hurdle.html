TOGETHER AI · HURDLE

에이전트가 상품 등록에 실패하면 무엇을 고쳐야 할까요?

상품 등록 기능을 연동해 달라고 했는데 에이전트가 같은 오류를 세 번 만났다고 가정해 보겠습니다. 문서에는 ‘옵션별 가격이 필요하다’는 설명이 빠져 있고, API는 ‘입력값 오류’라고만 답합니다. 개발자라면 문서에 필수값을 적고, 오류 메시지에도 어느 옵션의 가격이 비었는지 알려 줄 겁니다. 에이전트에게도 그 설명이 필요합니다.

명확한 개발 문서와 일관된 인터페이스, 이해하기 쉬운 오류 메시지는 좋은 개발자 경험(DX)을 만드는 요소입니다. 에이전트 사용 경험(AX, Agent Experience)은 이 관점을 에이전트로 확장합니다. 에이전트가 필요한 기능을 발견하고, 사용 조건을 이해하며, 오류가 났을 때 다음 행동을 찾을 수 있는지를 살펴봅니다.

Together AI가 11월 25일 MIT 라이선스로 공개한 Hurdle은 Claude Code와 Codex에 같은 과제를 반복해서 맡길 수 있는 평가 도구입니다. 모델의 성능을 높이는 것과 에이전트가 업무를 잘 수행할 수 있는 소프트웨어를 만드는 것은 서로 다른 문제입니다. Hurdle에서는 모델을 그대로 두고 문서나 업무 지침을 바꿔 그 차이를 확인할 수 있습니다. 공개 발표 ↗ · 코드와 라이선스 ↗

정산 금액이 맞는지는 일반 코드로 검사할 수 있습니다. 반면 에이전트가 오류 메시지를 이해하고 적절한 해결 방법을 찾았는지는 마지막 숫자만 보고 알기 어렵습니다. 이때는 심사 모델에 실행 기록과 평가 기준을 함께 주는 방법이 있습니다.

Microsoft Threat Intelligence는 11월 25일, 보안 점검을 자동화하는 도구 ARTEX를 국가 지원 조직과 금전 목적의 공격 조직이 실제로 사용했다고 밝혔습니다. 여러 단계에서 사람이 하던 일을 에이전트가 빠르게 이어 갔다는 게 Microsoft의 관찰입니다. Microsoft의 관찰과 방어 권고 ↗

로그인 실패 한 건만 보면 비밀번호를 잘못 입력한 고객일 수 있습니다. 그런데 같은 계정에서 평소와 다른 접근 요청과 권한 변경까지 이어졌다면 살펴볼 이유가 생깁니다. 이렇게 여러 행동 사이의 관계와 순서를 보고 이상 징후를 찾는 방식을 행위 기반 탐지(behavioral detection)라고 합니다.

Microsoft는 인터넷에 노출된 서비스의 범위를 줄이고, 인증정보를 보호하고, 계정에 꼭 필요한 권한만 부여하라고 권고했습니다. 이런 기본 통제를 갖추고 여러 기록을 연결하면 어떤 계정과 서비스를 먼저 보호해야 할지 판단하기 쉬워집니다.

BLACK FRIDAY · RETAIL

행사 트래픽을 견딘 뒤, 주문도 정확히 복구할 수 있을까요?

커머스 플랫폼에서는 대규모 할인 행사를 준비할 때 동시 접속자와 주문 처리량, 데이터베이스 부하를 확인합니다. 로이터가 11월 25일 블랙프라이데이를 앞두고 살펴본 것은 유통기업이 보안 사고를 얼마나 견디고 복구할 수 있는지였습니다. 아래 두 그래프는 보험사에 들어온 청구 기록과 기업의 보험 가입 응답을 각각 보여 줍니다. 로이터 보도 전문 ↗

사고가 나도 핵심 업무를 유지하고 정상 상태로 되돌리는 능력을 사이버 복원력(cyber resilience)이라고 합니다. 결제 승인은 끝났는데 주문 완료 응답을 보내기 전에 서비스가 멈췄다고 해 보겠습니다. 결제 기록과 주문 상태를 맞춰 기존 주문을 되살릴 수 있어야 고객이 두 번 결제하지 않습니다. AI가 관련 로그를 모으더라도 거래 복구에는 주문·결제 규칙과 검증 절차가 필요합니다.

커머스 시스템의 경쟁력은 평상시 처리량뿐 아니라 비정상적인 상황에서 거래의 정확성을 유지하고 복구하는 능력에서도 결정됩니다.

헬로우 휴먼의 관점

사람과 에이전트가 같은 상품을 찾는다면

개발자가 API를 사용하다 실패하면 문서와 인터페이스, 오류 메시지를 개선합니다. 그런데 AI 에이전트가 같은 API를 쓰다 실패하면 모델을 교체하거나 프롬프트를 고치기 쉽습니다. 에이전트의 실패 원인이 소프트웨어에 있다면 더 강력한 모델을 사용해도 문제는 남습니다.

모임에서 해볼 실험

모델을 바꾸지 않고 우리 API의 사용 경험 측정하기

같은 모델과 추론 설정에서 API 문서와 오류 메시지, 업무 지침만 개선해도 작업 성공률이 올라갈까요? Hurdle의 아이디어를 빌려 현재 쓰는 코딩 에이전트와 테스트 도구로 시도해 볼 수 있습니다. 개발자가 같은 업무를 다시 설명하거나 실패 원인을 찾는 시간도 함께 재 봅니다.

가상 상품 30개, 쿠폰 10개, 주문 20건으로 시작합니다

읽기 전용 모의 API와 예상 금액을 계산하는 함수만 준비합니다. 예를 들어 ‘2만 원 이상이면 3천 원 할인, 배송비 2천 원’인 주문에서 상품 합계가 정확히 2만 원이라면 기대 결제액은 1만 9천 원입니다. 1만 9,900원이라면 쿠폰이 빠져 2만 1,900원이 됩니다. 이처럼 한 조건만 달리한 입력과 정답을 먼저 고정합니다.

    업무 조건이 포함된 문서A에 선행 조건, 필수값, 상태별 처리 기준을 추가합니다.
  3. C
    구조화된 오류 메시지B에 실패 원인과 가능한 후속 조치를 담은 오류 응답을 추가합니다.
  4. D
    Agent Skill 추가C에 업무 수행 순서와 결과 검증 절차를 담은 지침을 연결합니다.

각 실행은 이전 결과를 기억하지 않는 새 세션에서 시작합니다. 같은 입력을 A부터 D까지 각각 주고, API 호출과 응답, 재시도, 최종 결과를 기록합니다. 독립 검증 프로그램으로 정답을 판정하고 시간 초과와 오답도 전체 시도에 포함합니다. 판매 상태나 테스트 데이터가 실행 사이에 바뀌면 문서 변경의 효과를 비교하기 어렵습니다.

실험을 시작하기 전에 A와 D를 어떤 기준으로 비교할지 정합니다. 모임에서 써 볼 목표는 네 가지입니다.

  • 금지된 실제 거래 0건. 모의 환경에서 금지 요청을 시도하면 그 실행은 실패로 기록합니다.
  • 업무 완료율 15%포인트 향상. 기본 문서만 준 A와 업무 지침까지 준 D의 정답률을 비교합니다.
  • 불필요한 API 호출 30% 감소. 같은 사례에서 되풀이한 호출을 셉니다.
  • 사람의 개입 시간 30% 감소. 업무를 다시 설명하고 오류 원인을 조사하는 데 쓴 시간을 합산합니다.

네 수치는 실험의 목표입니다. 실제 결과를 낼 때는 비율 옆에 시도 수와 성공 수를 함께 적고, 분모가 0이면 계산할 수 없다고 표시합니다.

실험이 끝나면 무엇이 남을까요?

실험이 끝나면 모델별 점수와 함께 개선된 API 명세와 업무 설명, 구조화된 오류 규격, Agent Skill, 검증 시나리오를 남깁니다. 이 자산은 새로운 모델이나 에이전트에서도 재사용할 수 있습니다. 실패가 반복되는 API는 인터페이스 자체를 개선할 수 있습니다. 복잡한 절차가 매번 같은 순서로 성공한다면 일반 소프트웨어 기능으로 옮길 수도 있습니다.

AI가 일하기 좋은 환경을 만드는 엔지니어링

Together AI의 Hurdle은 에이전트가 소프트웨어를 쓰다가 어디서 막히는지 확인할 방법을 제시합니다. Baidu의 가중치 공개는 모델을 어디서 운영할지 선택할 여지를 넓힙니다. Microsoft의 분석과 로이터의 보도에서 모임이 함께 생각해 볼 질문도 있습니다. 실행을 에이전트에 맡긴 뒤 누가 이상을 알아차리고, 어느 기록을 보고 거래를 복구할까요?

에이전트가 일하는 환경에서 각 구성요소가 맡는 일
구성요소담당하는 일
Software정확한 업무 기능과 데이터 제공
AI 모델요청의 의미를 이해하고 해결 방법 제안
Agent필요한 업무 기능을 찾아 실행
Workflow실행 순서, 권한, 검증, 복구 관리
Evals같은 입력과 기준으로 전체 업무 수행 능력 평가

지금까지 개발자는 사람이 사용하기 좋은 소프트웨어를 만들기 위해 노력했습니다. 앞으로는 에이전트가 사용하기 좋은 소프트웨어도 설계해야 합니다.

AI가 API를 이해하지 못할 때마다 사람이 설명하고, 실행에 실패할 때마다 개발자가 원인을 조사한다면 반복 업무는 사라지지 않습니다. 반복 업무의 형태만 바뀝니다.

Workless Engineering은 AI에게 일을 잘 시키는 기술을 넘어, AI가 별도의 반복적인 설명 없이도 정확하게 일할 수 있는 소프트웨어 환경을 만드는 엔지니어링입니다.
