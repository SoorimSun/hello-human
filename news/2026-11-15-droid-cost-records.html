01 / FACTORY DROID

어떤 도구를 썼는지,
어떤 기록이 남는지

Factory는 11월 14일자 변경 기록에서 Droid CLI·Desktop v1.12.0을 공개했습니다. 이번에는 도구 호출을 알아보기 쉽게 표시하고, 감사 기록과 세션 처리 오류를 고친 내용을 중심으로 살펴봅니다. 공식 변경 기록 ↗

도구 호출에 소속과 기능을 함께 표시합니다

Droid 명령, 커넥터, MCP 호출의 도구 행에 namespace와 capability를 표시합니다. 여러 외부 도구를 연결해 쓸 때 어떤 도구 영역에서 어떤 기능을 호출했는지 구분하기 쉬워집니다.

개발자가 실행 기록을 읽으며 실패한 호출을 찾는 데 도움이 될 변화입니다. 이 표시는 호출을 식별하는 정보이므로, 성공 여부는 도구 응답과 실제 변경 결과를 함께 확인해야 합니다.

Git 위험도는 승인 설정과 함께 봐야 합니다

일반 push와 Pull Request 작업은 중간 위험도, 강제 push는 높은 위험도로 분류합니다. 서비스 계정 키를 폐기할 때 조직 감사 기록에 이벤트를 남기는 변경도 포함됐습니다.

위험도는 화면의 안내에만 쓰이지 않습니다. Factory 문서에 따르면 명령 정책이 먼저 적용되고, 해당 정책과 일치하지 않는 작업은 위험도와 Autonomy Level을 비교해 자동 실행 여부를 정합니다. 조직 정책과 샌드박스도 영향을 줍니다. 따라서 업데이트 후 push에 승인을 요구할지는 현재 정책과 자율 실행 설정을 함께 확인해야 합니다. 공식 승인 설정 설명 ↗

실패한 명령에서 결과물이 남던 문제를 고쳤습니다

저장한 세션 ID로 다시 실행할 때 이전 대화를 첫 요청에 전달하도록 수정했습니다. 또 파이프 처리로 오류가 가려진 gh·glab 명령이 실패했는데도 artifact를 기록하던 문제를 고쳤습니다.

여기서 확인된 범위는 실패한 GitHub·GitLab CLI 명령의 결과물 기록입니다. 전체 작업의 성공 판정을 보장하는 기능으로 확대해서 읽을 수는 없습니다. 다만 자동화가 잘못 남은 기록을 다음 단계의 근거로 삼지 않도록 하는 수정이라는 점에서 중요합니다.

02 / OPENAI STATUS

서비스는 실행돼도
비용 데이터는 늦게 올 수 있습니다

OpenAI는 한국시간 11월 14일 01:10 조직 비용 데이터 제공 지연을 공지했습니다. 공지 제목은 ‘Delayed Costs Data in the Compliance API’이고, 본문은 Costs API를 통한 비용 데이터 제공이 늦어진다고 설명합니다. 해당 상태 공지 ↗

완화 조치를 적용한 뒤에도 지연이 예상돼 모니터링을 이어가고 있습니다. 최초 공지에는 API와 ChatGPT 사용 자체에는 영향이 없다고 명시했습니다. 11월 15일 14:35 확인 시점에도 상태는 Monitoring입니다.

이 공지로 모든 고객의 지연 시간이 같았다거나 실제 청구 금액이 잘못 계산됐다고 판단할 수는 없습니다. 확인된 문제는 비용 데이터가 제때 제공되지 않는다는 것입니다.

조회 시각과 데이터 반영 범위를 나눠 봅니다

작업이 끝났는데 비용 조회 결과에 아직 나타나지 않으면, 비용이 발생하지 않았다고 해석하기 쉽습니다. 운영 화면에는 언제 조회했는지와 어느 기간의 데이터인지를 함께 두고, 완전한 집계인지 확인되지 않으면 그 상태도 남기는 편이 좋습니다. 방금 조회했다는 사실만으로 최신 사용량까지 모두 반영됐다고 보장되지는 않습니다.

OpenAI의 공개 Costs API는 현재 일 단위 버킷과 프로젝트·비용 항목 등의 묶음을 제공합니다. 이 집계만으로 애플리케이션의 개별 작업 ID에 비용이 자동 연결되는 것은 아닙니다. 작업별 모델 호출·사용량 기록을 따로 모으고, 같은 기간과 범위의 공급자 집계와 대조할 연결이 필요합니다. Costs API 문서 ↗

에이전트가 재시도하거나 하위 에이전트를 실행하면 추가 모델 호출이 생길 수 있습니다. 도구 이용료가 별도로 발생하는 경우에는 해당 공급자의 과금 기준도 반영해야 합니다. 운영 대시보드에서는 호출 기록으로 계산한 추정 비용, 공급자가 집계한 비용, 최종 청구 내역을 구분해 보는 것이 적절합니다.

OUR VIEW

완료 보고에
대조할 근거가 있어야 합니다

Factory의 업데이트는 도구 호출을 읽고 실패한 실행의 기록을 다루는 문제입니다. OpenAI의 사례는 서비스가 동작하는 동안에도 비용 데이터는 늦어질 수 있음을 보여줍니다. 둘을 함께 보면 에이전트를 운영할 때 확인해야 할 정보가 조금 더 선명해집니다.

에이전트가 “완료했습니다”라고 답했을 때, 실제 업무 시스템의 상태가 기대한 결과와 일치하는지 확인할 수 있어야 합니다. 비용 데이터가 비어 있을 때도 미집계인지, 확인된 0원인지 구분할 수 있어야 합니다.

업무 목표와 실행 결과, 검증 증거를 연결한 기록이 있어야 사람이 문제를 처음부터 재구성하는 시간을 줄일 수 있습니다. 모델과 프롬프트를 고르는 일에 더해, 어떤 근거로 완료를 인정할지 설계하는 일이 필요합니다.

OUR LAB · 아직 실행하지 않은 실험 제안

실행 완료와 비용 집계를
따로 기록하고 대조해 봅니다

가상 상품 P-021의 설명을 “세척 후 완전히 말려 보관”으로 바꾸는 요청을 보냅니다. 업무 API에 변경이 반영되고 다시 읽은 값도 같지만, 비용 집계는 아직 도착하지 않았습니다. 이때 기대 상태는 작업 검증 완료 / 비용 집계 대기입니다. 비용을 0원으로 확정하거나, 비용을 확인하려고 업무를 재실행해서는 안 됩니다.

지난 호의 결제 응답 유실 실험이 중복 결제 없이 복구하는 흐름을 다뤘다면, 이번에는 서로 다른 시점에 도착하는 실행·검증·비용 기록을 대조하는 작은 도구를 만들어 봅니다. 실제 고객 코드와 데이터는 사용하지 않습니다.

상품 설명 수정 20건을 준비해 정상 처리, API 실패, 성공 응답 뒤 값 불일치, 중복 요청의 네 묶음에 5건씩 배치합니다. 각 묶음에서 비용 기록을 즉시 제공하는 경우와 늦게 제공하는 경우를 섞습니다. 구현을 조정할 예시는 이 20건과 따로 만듭니다.

실패 상황별 기대 처리. 아래 상태는 실측값이 아닌 실험의 정답 기준입니다.
주어진 상황실행·검증 상태비용·재실행 처리
값 일치, 비용 지연검증 완료집계 대기. 금액은 미확인으로 두고 변경 요청을 반복하지 않습니다.
API 오류를 모델이 완료로 보고실패와 잘못된 완료 보고를 함께 기록실패 전 모델 호출의 사용량도 남깁니다.
성공 응답, 실제 값 불일치검증 실패비용이 집계돼도 업무 완료로 바꾸지 않습니다.
같은 요청이 두 번 도착작업 ID로 묶고 중복 실행 여부 확인비용 스냅샷은 같은 기간의 새 값으로 교체하며 이중 합산하지 않습니다.

같은 입력과 오류 순서를 두 방식으로 비교합니다. A에서는 사람이 실행 로그·상품 상태·비용 자료를 직접 대조합니다. B에서는 별도 대조기가 불일치와 집계 대기를 먼저 표시하고 사람이 최종 확인합니다. 모델·지침·실행 기록은 동일하게 두어, 대조 방식의 차이를 봅니다.

실행 상태 일치율은 20건 중 최종 분류가 미리 정한 기대 상태와 일치한 건수로 계산합니다. 잘못된 성공 보고를 놓친 건수, 중복 쓰기 횟수, 미집계를 0원으로 표시한 건수, 비용 반영 지연, 사람이 조사한 시간과 전체 처리 시간도 기록합니다. A/B를 보는 순서를 바꿔 앞서 본 정답이 조사 시간을 과도하게 줄이지 않도록 합니다.

초기 통과 기준은 B에서 기대 상태 20/20건 일치, 잘못된 성공 보고 누락 0건, 미집계의 0원 처리 0건입니다. 중복 쓰기가 발생하면 모두 찾아야 하며, 사람의 조사 시간도 A보다 줄어야 합니다. 통과하더라도 실제 운영에 적용하기 전에는 더 다양한 실패와 데이터 규모로 확인합니다.

구현 범위와 남길 결과물

모의 상품 API, 호출 기록 저장소, 상품 상태 대조기, 비용 집계 입력기를 만듭니다. 작업 ID·시도 ID·도구 이름·가상 입력의 식별자·호출 시각·결과·검증 상태를 남깁니다. 인증정보와 민감한 원문 입력은 저장하지 않습니다.

비용 입력기는 미리 정한 집계 기간과 금액을 즉시 또는 지연 제공하고, 같은 기간의 수정된 스냅샷도 내보냅니다. 실험용 값이며 실제 요금 추정치가 아닙니다. 실서비스에 연결할 때는 호출별 사용량으로 작업 비용을 추정하고, 공급자 집계와는 프로젝트·기간·비용 항목이 같은 합계끼리 대조합니다. 집계 시각과 완전성 확인 상태를 기록하고, 공급자가 완전성을 보장하지 않으면 ‘확정’으로 표시하지 않습니다.

중복 쓰기는 API의 변경 이벤트 수로 확인합니다. 값이 같다는 이유로 두 번 쓴 사실을 놓치지 않도록 합니다. 비용 재조회는 업무 재시도와 분리하고, 시간 초과·집계 누락은 미확인 사유를 남깁니다. 입력·오류 재생 파일, 모델·지침 버전, 기대 상태 표, 대조 코드와 결과 보고서를 보관합니다. 먼저 고정 응답으로 대조기를 확인한 뒤 실제 모델의 완료 보고를 평가합니다.

실행 결과를 검증하는 반복 작업까지 줄입니다

AI가 요청을 이해하고 Agent가 도구를 호출하면, 업무 소프트웨어는 규칙과 실제 상태를 책임집니다. Workflow는 검증·재시도·복구를 이어 주고, 관측 기록은 그 과정에서 무엇이 일어났는지 확인할 근거가 됩니다.

Workless Engineering의 다음 과제는 실행된 작업의 결과와 비용을 사람이 매번 처음부터 조사하는 시간까지 줄이는 것입니다. 이번 실험에서는 더 많은 작업을 시키기 전에, 이미 실행한 작업을 어떤 근거로 믿을 수 있는지 확인해 봅니다.
