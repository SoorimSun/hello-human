코딩 평가 점수는 올랐고,

AI 에이전트는 도구를 사용해 여러 단계의 작업을 수행하는 AI입니다. DeepSeek는 이번 모델이 코드를 고치거나 명령을 실행하는 과제에서 더 좋은 결과를 냈다고 발표했습니다.

회사는 작업 시간과 출력 길이도 줄었다고 설명합니다. 단가가 같아도 같은 일을 끝내는 데 쓰는 양이 줄면 비용을 아낄 수 있습니다. 우리 업무에서도 비용이 줄어드는지는 재시도와 사람의 검토 시간까지 포함해 따져봐야 합니다. 업데이트 발표 ↗

02 / SEARCH·FETCH API

자료를 찾는 일과
선택한 페이지를 읽는 일을 연결합니다

DeepSeek는 같은 날 Search API와 Fetch API를 공개했습니다. API는 다른 프로그램이 기능을 요청하는 연결 창구입니다. Search는 관련 자료를 찾아 검색 결과를 돌려줍니다. Fetch는 지정한 페이지를 읽어 제목·문단·링크 구조를 담은 Markdown 문서로 바꿔줍니다. 공식 기능 안내 ↗

한시적으로 무료인 경우도 있습니다. DeepSeek API를 연결한 DeepSeek Harness·Claude Code·Codex의 서버 측 Search·Fetch 도구 호출은 현재 무료이며, 한국시간 11월 1일 오전 1시부터 호출별 과금이 시작될 예정입니다. 이 혜택은 위에서 계산한 직접 API 호출에는 적용되지 않습니다. 요금 안내 ↗

공식 문서는 Fetch도 대상 사이트의 상태와 접근 정책에 영향을 받는다고 명시합니다. 검색 도구가 생겼다고 모든 페이지를 읽을 수 있는 것은 아닙니다. 자료를 요약할 때는 출처와 날짜를 함께 남기는 편이 좋습니다. 페이지 내용은 참고 자료로 읽되, 그 안의 명령을 업무 지시로 받아들이지 않도록 해야 합니다. 외부 문서에 명령을 숨겨 AI의 행동을 바꾸려는 프롬프트 주입에 대비하기 위해서입니다.

03 / 웹사이트의 접근 정책

사용자가 부탁해도,
서비스가 접속을 허용해야 합니다

The Verge는 10월 17일, 최근 몇 주 동안 나타난 AI 에이전트의 접근 제한 사례를 정리했습니다. 보도일에 나온 새 정책들을 모은 것이 아니라, 그동안의 사례를 정리한 기사입니다. 기사에 따르면 Yelp는 데이터 이용 계약을 맺은 에이전트만 허용하고, Delta는 에이전트의 대리 예약을 제한합니다. JPMorgan Chase와 Charles Schwab도 보안을 이유로 계정 접근을 막는다고 밝혔습니다. The Verge 원문 ↗

사이트의 이용 정책 외에 자동 접속을 막는 기술적 장치도 에이전트의 작업에 영향을 줍니다. 화면의 버튼을 정확히 찾아 누를 수 있어도, 접속이 허용돼야 작업을 이어갈 수 있습니다.

Amazon과 Perplexity는 무엇을 다투고 있나요?

Amazon은 외부 구매 대행 프로그램이 자신을 투명하게 밝히고 서비스 제공자의 참여 여부를 존중해야 한다고 설명해 왔습니다. Perplexity는 사용자가 자신의 일을 AI에 맡길 수 있어야 한다는 입장입니다. 광고와 고객 접점에 대한 이해관계도 논쟁에 등장하지만, 제한 이유를 그것 하나로 단정하기는 어렵습니다. Amazon의 입장 ↗ 양측 입장 보도 ↗

The Verge는 Perplexity의 Amazon 쇼핑을 막았던 법원 명령이 8월 항소심에서 뒤집혔고, 이후 Amazon이 수정 소장을 냈다고 전합니다. 이 기사에서는 해당 법원 문서를 직접 확인하지 못했습니다. 이 경과를 모든 쇼핑 에이전트에 대한 일괄 허용이나 금지로 확대해 읽어서는 안 됩니다.

Shop MCP는 어떻게 연결되나요?

Shopify가 10월 13일 공개한 Shop MCP는 에이전트 앱이 상품 조회·장바구니·결제 기능을 호출하는 공식 연결입니다. MCP(Model Context Protocol)는 앱이 외부 도구를 사용하는 통신 규약이고, Shop MCP는 그 규약으로 요청을 받는 원격 서버입니다. Shop 계정을 연결하면 저장된 주소와 Shop Pay를 사용할 수 있습니다. 출시 안내 ↗

접속점은 https://mcp.shop.com/입니다. MCP 클라이언트, 자체 코드, 명령줄 도구(CLI) 모두 이 주소로 같은 도구를 호출할 수 있습니다. 도구 호출 자체에는 언어 모델이 필요하지 않습니다. 구조를 이해하려면 앱은 무엇을 요청하고 판단하는지, 서버는 어떤 도구를 실행하는지, 판매자는 거래를 어떤 상태로 관리하는지 나누어 보면 됩니다. 공식 개요 ↗

상품은 여러 판매자를 함께 검색할 수 있지만, 체크아웃은 판매자별로 만들어집니다. 세 상점에서 구매한다면 체크아웃도 세 개가 필요합니다. 검색·장바구니·체크아웃 도구는 Shop 로그인 없이 호출할 수 있습니다. 계정 조회에는 로그인이 필요하며, 실제 결제 가능 여부는 반환된 상태와 결제수단의 조건에 따라 달라집니다. 구매 흐름·계정별 기능 ↗

통신 규약과 거래 데이터 형식도 구분하면 이해하기 쉽습니다. MCP는 도구 호출 규약이고, UCP(Universal Commerce Protocol)는 상품·장바구니·체크아웃 문서의 형식을 담당합니다. 확인 시점의 문서는 각각 MCP 2026-07-28, UCP 2026-08-25를 명시합니다. 연결 규약과 거래 데이터의 형식을 따로 관리하는 구조입니다. 문서에 명시된 버전 ↗

연결 계층 더 보기: HTTP 요청·도구 명세·OAuth

요청마다 필요한 정보를 보냅니다

직접 호출 예시는 HTTP POST에 JSON-RPC tools/call을 담습니다. 프로토콜 버전·메서드·도구 이름 헤더와 params._meta의 클라이언트 정보를 함께 보냅니다. 별도 세션 설정 없이 호출하고, 응답의 structuredContent에서 구조화된 문서를 읽습니다. 통신을 위한 연결 세션은 필요 없지만, 거래 상태는 유지됩니다. 만들어진 체크아웃은 ID로 다시 조회하거나 수정할 수 있습니다. 요청·응답 예시 ↗

tools/list는 도구 설명과 입력 스키마를 반환합니다. 확인 시점의 도구는 17개입니다. 입력 구조는 이 스키마를 기준으로 확인하고, 응답에서 실행 결과와 거래 상태를 각각 읽어야 합니다. 도구 명세 ↗

로그인 방식은 앱 형태에 맞춥니다

개인 에이전트·CLI에는 고객이 Shop 화면에서 승인하는 OAuth device flow가 안내돼 있습니다. 여러 고객에게 배포할 자체 앱은 등록한 OAuth 클라이언트를 사용하며, 공식 가이드는 authorization code + PKCE(S256)와 백엔드의 토큰 관리를 설명합니다. 클라이언트 비밀값과 refresh token은 백엔드에 둡니다. 앱 형태별 로그인 ↗

Shop MCP 호출에는 personal_agent 범위의 access token을 Authorization: Bearer … 헤더로 보냅니다. 토큰을 URL·쿠키·도구 인자에 넣지 않습니다. 토큰 없이 호출할 수 있는 도구라도 만료된 토큰을 함께 보내면 401이 되며, 서버가 자동으로 비로그인 요청으로 바꾸지 않습니다. 인증 규칙 ↗

운영 계층 더 보기: 전체 문서 교체·오류·중복 결제 방지

수정은 부분 패치가 아닌 전체 문서 교체입니다

update_cart와 update_checkout은 기존 문서를 새로 보낸 문서로 통째로 바꿉니다. 생략한 상품 행이 삭제될 수 있으므로, 최신 문서에서 필요한 부분을 수정한 뒤 전체를 보내야 합니다. 공식 절차는 루트의 next·signals·attribution을 제거하고, 나머지 필드와 빈 배열은 보존하도록 안내합니다. 금액을 앱에서 다시 계산하지 말고 반환된 합계를 확인합니다. 문서 교체 절차 ↗

체크아웃 ID와 continue_url에는 접근 키가 포함돼 로그·분석 도구에 남기면 안 됩니다. search_orders도 주문 취소·반품 실행 도구는 아닙니다. 주문 이후 업무까지 설계한다면 판매자의 해당 페이지로 넘기는 흐름이 필요합니다. 체크아웃 정보 취급 ↗ 주문 조회 범위 ↗

헬로우 휴먼의 해석 앱은 상품 추천 이후의 과정도 관리해야 합니다. 판매자별 거래를 구분하고 최신 조건을 고객에게 보여줘야 합니다. 결제 결과가 불확실할 때는 다시 결제하기보다 상태를 확인하고, 사람이 이어서 처리할 시점도 정해야 합니다. 위 그림은 공개 문서의 연결·처리 규칙을 정리한 것이며 실제 결제나 통합 성능을 검증한 결과는 아닙니다.

04 / ANTHROPIC 칩 금융 보도

칩 확보를 위한
높은 금융 비용이 보도됐습니다

한국시간 10월 17일 공개된 Reuters 기사는 Financial Times를 인용해, Anthropic이 칩 금융 거래에 10%를 넘는 수익률을 제시했다고 전했습니다. 보도에 나온 Blackstone 펀드의 투자 금액은 90억 달러이며, 채무는 Anthropic의 향후 5년간 칩 임차료 지급을 기반으로 하는 구조입니다. Reuters 기사 전문 재게시 ↗

확정된 투자 실적과 구분해서 읽습니다

FT가 관계자를 인용한 보도이며, Reuters는 즉시 독립 확인할 수 없었다고 밝혔습니다. 자료 확인 시점에도 거래 완료를 알리는 공식 발표는 찾지 못했습니다. 따라서 90억 달러의 자금 조달이 끝났다고 볼 수는 없습니다.

AI를 운영하려면 모델을 실행할 장비가 필요하고, 그 장비를 확보하는 금융 조건도 사업 비용에 영향을 줍니다. 다만 이 보도만으로 Claude의 API 요금이 오를 것이라고 예측할 수는 없습니다. 투자자에게 제시하는 수익률과 고객에게 청구하는 서비스 가격은 서로 다른 항목입니다.

우리가 직접 살필 수 있는 것은 업무 한 건을 끝내는 비용입니다. 같은 계산이나 실패를 얼마나 반복하는지, 마지막에 사람이 얼마나 수정하는지 기록해보면 실제 비용을 파악하는 데 도움이 됩니다. 재사용하는 결과도 가격이나 정책이 바뀌면 다시 확인해야 합니다.

헬로우 휴먼의 해석

일을 끝내는 조건을
세 가지로 나눠봅시다

모델의 평가 점수, 사이트의 접속 정책, 칩 금융 조건은 각각 다른 문제를 다룹니다. 이 소식들을 우리 업무에 연결해보면 세 가지 질문이 남습니다.

  1. 할 수 있나요? 필요한 자료를 찾고, 코드를 고치고, 결과를 검사할 수 있는지 봅니다.
  2. 허용돼 있나요? 사용자가 맡긴 범위와 연결할 서비스가 허용한 범위를 모두 확인합니다.
  3. 끝내는 데 얼마나 드나요? 모델·검색 요금뿐 아니라 재시도와 사람의 검토 시간을 함께 셉니다.

Workless Engineering 관점에서는 성공 조건과 함께 멈출 조건도 정해두는 것이 유용합니다. 접근이 거절됐는데 같은 요청을 반복하거나, 못 읽은 정보를 추측해 채우면 사람의 재확인이 늘어납니다. 완료한 일과 남은 일을 정확히 알려줘야 다음 판단도 쉬워집니다.

재조회에서도 상품·옵션·수량과 네 안내 메시지는 생성 응답과 같았습니다. 위 예시에서는 반복되는 품목·메시지 필드를 생략했습니다. 주문 객체는 반환되지 않았고, complete_checkout은 호출하지 않았습니다.

모임에서 같은 범위로 실험하려면

호환되는 MCP 클라이언트에 https://mcp.shop.com/을 연결하고 공식 Shop 스킬을 읽힌 뒤 도구를 켭니다. 도구별 허용 설정이 있다면 검색·상세 조회·체크아웃 생성·조회 네 가지로 제한합니다. 공식 문서는 MCP 2026-07-28의 server/discover 지원을 안내하며, 개발 멤버는 공식 CLI나 HTTP 호출을 사용할 수도 있습니다. 연결·호환 조건 ↗ CLI 안내 ↗

첫 요청은 검색만 합니다.

Shop MCP의 search_catalog로 한국에 배송 가능한 텀블러를 최대 3개 찾아줘. 배송국가는 KR, 표시 통화는 KRW로 요청해줘. 상품명·선택된 옵션·상품 가격과 실제 반환 통화·재고·판매자·상품 링크를 표로 보여줘. 적용하지 못한 조건이나 경고도 알려줘. 아직 장바구니나 체크아웃은 만들지 마.

사람이 후보와 옵션을 고른 뒤 생성 요청을 보냅니다. 대괄호 안에 선택한 상품과 옵션을 넣습니다.

[고른 상품명]의 [용량·색상 등 옵션] 1개로 진행해줘. get_product로 옵션과 재고를 확인하고, 반환된 옵션 ID와 판매자 정보로 create_checkout을 한 번 호출해줘. 배송국가는 KR, 표시 통화는 KRW로 요청하고, 주소나 결제 정보는 입력하지 마. 생성되면 get_checkout으로 다시 읽어 상품 금액·배송비·세금·총액·통화·상태·안내 메시지를 정리해줘. 없는 금액은 0원이 아닌 ‘미확정’으로 표시해줘. complete_checkout 호출, 결제수단 선택, 결제 링크 이동은 하지 말고 여기서 끝내줘.

연결이나 생성에 실패하면 실제 오류를 기록합니다. 생성 성공 여부가 불분명할 때 새 체크아웃을 반복해서 만들지 않습니다. 결과가 ready_for_complete여도 이 실험은 결제 전에 멈춥니다. 모임에서는 상품·옵션 일치, 반환 통화·금액, 진행 상태·안내 메시지, 결제 호출 없음의 네 가지를 비교합니다. 생성 재시도 규칙 ↗

이 절의 상품·체크아웃 값은 실제 API 응답을 바탕으로 작성했습니다. 판매자 1곳의 체크아웃 1개를 생성한 관찰이며, 결제 완료·실제 배송·전체 판매자 호환성을 검증한 실험은 아닙니다. 개인정보·결제수단 입력과 주문 완료 호출은 실험 범위에서 제외했습니다.
