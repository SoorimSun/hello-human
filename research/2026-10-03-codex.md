# Codex 입문 가이드 공식 근거 메모

- 확인일: 2026-10-03 (한국 시간).
- 목적: 헬로우 휴먼 초보자를 위한 요리 실습 가이드. 기본은 레시피 정적 HTML과 GitHub Pages, 심화는 2인분 기준 재료를 1~6인분 정수로 환산하는 계산기와 테스트다.
- 조사 범위: OpenAI 공식 개발자·학습 문서. 공식 도메인 검색 후 원문을 열어 확인했다. 이 메모에서 설치·로그인·모델 호출·커밋·푸시는 실행하지 않았다.
- 구분: 아래 기능 설명은 확인한 사실, 학습 순서와 예제 프롬프트는 가이드 편집 제안이다. 계정·조직 정책·클라이언트 버전에 따라 메뉴와 모델 목록이 달라질 수 있다.

## 1. 앱과 CLI: 같은 Codex를 여는 두 입구

공식 최신 문서는 데스크톱 제품을 **ChatGPT desktop app**으로 안내한다. macOS·Windows·Linux용 앱을 제공하며, 앱에서 ChatGPT 또는 Codex를 선택한다. Codex는 New chat에서 시작한다. 따라서 기존의 “Codex 앱” 표현을 쓰더라도 “현재는 ChatGPT 데스크톱 앱에서 Codex 선택”을 함께 설명하는 편이 정확하다. [데스크톱 앱](https://learn.chatgpt.com/docs/app)

Codex CLI는 터미널에서 프로젝트 파일을 읽고 수정하고 명령을 실행하는 별도 진입점이다. 폴더를 연 뒤 `codex`로 시작한다. 초보 가이드는 앱을 주 경로로 두고, 같은 실습을 CLI에서도 수행할 수 있는 대안을 제시하면 된다. 앱 설치가 CLI 설치까지 보장한다는 설명은 피한다. [Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

로컬 앱·CLI·IDE 확장은 ChatGPT 로그인과 API 키 로그인을 모두 지원한다. ChatGPT 로그인은 구독 접근, API 키는 사용량 기반 접근이다. API 키 사용료는 ChatGPT의 포함 사용량과 별도이며, Codex Cloud에는 ChatGPT 로그인이 필요하다. 초보 기본 경로는 ChatGPT 로그인으로 충분하다. [인증](https://learn.chatgpt.com/docs/auth)

## 2. 설치 명령과 로그인

다음은 **가이드에 수록할 명령**이며 이번 조사에서 실행하지 않았다.

macOS / Linux 독립 설치:

```sh
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

공식 CLI 문서의 설치·업데이트 예시와 일치한다. [CLI 설치](https://learn.chatgpt.com/docs/codex/cli)

Windows PowerShell 독립 설치:

```powershell
irm https://chatgpt.com/codex/install.ps1 | iex
```

**근거와 한계:** CLI 페이지의 Windows 탭 본문은 웹 텍스트 추출에 나타나지 않았다. 다만 공식 환경변수 문서가 위 Windows 설치 스크립트 URL을 명시하고, 동일 명령 앞에 `CODEX_NON_INTERACTIVE=1`을 설정한 무인 설치 예시를 제공한다. 위 일반 설치 명령은 그 자동응답 설정을 제외한 조합이다. 해당 설정의 기본값은 false이며 첫 설치에는 무인 모드를 쓰지 말라고 설명한다. [설치 환경변수](https://learn.chatgpt.com/docs/config-file/environment-variables)

Node.js/npm을 이미 쓰는 사람의 대안:

```sh
npm install -g @openai/codex@latest
codex --version
```

이 예시는 공식 Cookbook에 실려 있다. `npm i -g @openai/codex`도 같은 패키지를 설치하지만 가이드에는 확인한 전체 표기를 권장한다. 독립 설치와 npm 설치를 모두 수행할 필요는 없다. [공식 Cookbook](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

프로젝트 폴더에서 `codex`를 실행하면 첫 인증 흐름으로 이어진다. 명시적으로 로그인하려면 `codex login`, 인증 방식 확인에는 `codex login status`를 쓴다. 브라우저 로그인은 사용자가 직접 완료한다. [CLI 시작](https://learn.chatgpt.com/docs/codex/cli), [인증 절차](https://learn.chatgpt.com/docs/auth)

## 3. 모델·reasoning: 공식 추천과 수업 기본값 구분

현재 공식 모델 문서는 GPT-6.1 Sol을 사용 가능한 계정·클라이언트에서 추천하며 모델 ID는 `gpt-6.1-sol`이다. 모델 선택기에 표시되는 목록은 계정과 조직 정책에 따라 달라진다. 모든 사용자에게 보인다고 쓰면 안 된다. 공식 문서는 GPT-6.1 Sol의 reasoning을 클라이언트 기본값에서 시작해 조정하라고 설명한다. **Medium을 수업 예시로 선택하는 것은 편집 결정**이며, 공식 문서상 Medium은 속도와 깊이의 균형을 위한 설정이다. 최고 설정이 항상 필요한 것은 아니다. [모델과 reasoning](https://learn.chatgpt.com/docs/models)

- 앱: 입력창의 모델 선택기 또는 `/model`, reasoning은 `/reasoning`으로 선택할 수 있다. `/`를 입력해 현재 가능한 명령을 확인한다. [앱 명령](https://learn.chatgpt.com/docs/reference/slash-commands)
- CLI: `/model`에서 모델과 reasoning을 선택하고 `/status`로 적용 상태를 확인한다. 한 번의 실행에는 다음처럼 설정한다. [개발자 설정](https://learn.chatgpt.com/docs/developer-settings)

```sh
codex --model gpt-6.1-sol --config model_reasoning_effort='"medium"'
```

`--config`의 공식 예시를 그대로 썼다. 모델이 목록에 없으면 `--model`을 생략하거나 `/model`에 실제 표시되는 모델을 선택한다. 영구 설정 예시는 개인 `~/.codex/config.toml`의 `model = "gpt-6.1-sol"`, `model_reasoning_effort = "medium"`이며, 앱·CLI·IDE가 설정을 공유하므로 초보 가이드에서는 대화별 선택이 이해하기 쉽다. [설정](https://learn.chatgpt.com/docs/developer-settings), [모델 기본값](https://learn.chatgpt.com/docs/models)

## 4. Plan과 권한은 서로 다른 설정

`/plan`은 구현 전에 계획을 다루는 대화 모드다. 앱과 CLI 모두 지원한다. CLI에서는 `/plan 레시피 페이지의 구현 계획을 제안해줘`처럼 요청을 함께 적을 수 있고, 이미 작업 중일 때는 일시적으로 사용할 수 없다. [앱 Plan](https://learn.chatgpt.com/docs/reference/slash-commands), [CLI Plan](https://learn.chatgpt.com/docs/developer-commands)

파일·네트워크 접근 범위는 sandbox, 추가 행동을 누가 검토하는지는 approvals가 정한다. 따라서 Plan을 파일 시스템의 읽기 전용 잠금과 같은 기능으로 설명하면 안 된다. 읽기 전용 탐색을 명확히 제한할 때는 CLI의 `read-only` sandbox를 별도로 설정할 수 있다. [권한](https://learn.chatgpt.com/docs/permission-modes), [CLI 플래그](https://learn.chatgpt.com/docs/developer-commands)

```sh
# 먼저 읽고 설명받기
codex --sandbox read-only --ask-for-approval on-request

# 검토한 범위의 파일 수정과 로컬 실행
codex --sandbox workspace-write --ask-for-approval on-request
```

앱 권한은 **입력창 아래 permissions control → Ask for approval**을 기본으로 안내한다. 이는 `workspace-write`, `on-request`, reviewer `user`에 해당한다. 현재 작업 폴더의 수정과 일상적인 로컬 명령은 가능하며, 인터넷 접근이나 폴더 밖 행동에는 승인을 요청한다. CLI는 `/permissions`로 변경한다. **앱 `/permissions`는 공식 앱 명령 목록에서 확인하지 못했으므로 동일 명령으로 안내하지 않는다.** 조직 설정에 따라 선택지가 제한될 수 있다. [권한 메뉴](https://learn.chatgpt.com/docs/permission-modes)

교육상 권장 문장: “먼저 계획과 완료 조건을 확인하고, 구현을 맡긴 뒤 변경 파일과 테스트 결과를 직접 검토하세요.” `on-request`가 파일 하나를 수정할 때마다 사용자에게 묻는 모드라고 설명하면 안 된다.

## 5. AGENTS.md, skill, plugin의 역할

| 구성 | 입문 설명 | 실습 연결 |
| --- | --- | --- |
| AGENTS.md | 프로젝트에서 반복 적용할 작업 규칙 | 파일 구성, 한국어 설명, 검증 방법, 사용자가 요청하기 전 푸시 금지 |
| Skill | 특정 작업의 재사용 가능한 절차와 자료 | 새 레시피를 동일한 형식으로 정리하는 절차 |
| Plugin | skill과 도구 등을 설치·배포하는 묶음 | 필요한 워크플로를 앱이나 CLI에서 추가 |

Codex는 시작 시 전역 `~/.codex`와 프로젝트 루트부터 현재 폴더까지의 지침을 읽는다. 각 위치에서 `AGENTS.override.md`를 `AGENTS.md`보다 먼저 확인하며, 하위 폴더 지침이 상위 지침을 구체화할 수 있다. `/init`은 프로젝트용 `AGENTS.md` 초안을 만든다. 초안에 실제로 존재하지 않는 테스트 명령을 넣지 않았는지 사람이 확인한다. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [앱 /init](https://learn.chatgpt.com/docs/reference/slash-commands)

Skill은 `SKILL.md`를 포함하는 폴더이며 이름과 description이 필요하다. 지침 외에 참고 자료와 스크립트를 포함할 수 있다. Codex는 작업에 맞는 skill을 자동 선택하거나, 사용자가 `$`로 명시 선택할 수 있다. [Skill과 plugin](https://learn.chatgpt.com/docs/skills-and-plugins)

현재 공식 repo skill 위치는 `.agents/skills/<skill-name>/SKILL.md`다. 개인 skill 위치로는 `~/.agents/skills`를 안내한다. 시스템 내장 `$skill-creator`로 instruction-only skill을 만들 수 있으며, 생성 후 실제 요청으로 시험하고 수정한다. 스킬 변경은 자동 감지되지만 보이지 않으면 재시작한다. [Skill 만들기와 경로](https://learn.chatgpt.com/docs/build-skills)

선택 실습 프롬프트(교육용 창작):

```text
$skill-creator
이 프로젝트에서 새 레시피를 추가할 때 쓰는 recipe-editor 스킬을 만들어줘.
입력은 요리 이름, 기준 인분, 재료와 단위, 조리 순서야.
출력은 기존 레시피와 같은 구조의 HTML이고 모바일 화면도 확인해야 해.
모르는 조리 정보와 수량은 만들어내지 말고 나에게 물어봐.
인분 계산 기능이 있으면 2인 기준 수량이 그대로 유지되는지도 확인해.
프로젝트의 .agents/skills/recipe-editor에 지침 중심으로 만들고,
커밋이나 푸시 없이 생성한 내용을 보여줘.
```

## 6. Plugin 설치와 Superpowers를 설명할 때의 경계

공식 설치 경로:

1. 앱의 **Plugins** 탭에서 검색하고 상세를 연다.
2. **+** 버튼으로 설치한다. 연결 서비스가 필요한 경우 해당 인증을 완료한다.
3. 새 대화를 시작해 설치한 plugin이나 skill을 사용한다.
4. CLI는 `/plugins`에서 marketplace와 plugin을 선택해 설치하고 **새 세션**을 시작한다.

CLI plugin browser는 설치한 항목에서 Space로 활성 상태를 바꿀 수 있다. 공식 문서는 IDE 확장의 plugin 지원은 없다고 명시한다. standalone skill 지원과 혼동하면 안 된다. [Plugin 설치](https://learn.chatgpt.com/docs/plugins)

**Superpowers 관련 확인 범위:** OpenAI 공식 문서로 확인한 것은 plugin 설치 구조, skill의 `$` 호출, 활성화와 재시작 동작이다. Superpowers 자체의 현재 배포 이름·마켓플레이스 항목·정확한 설치 명령·각 skill의 동작은 이 조사 범위의 공식 OpenAI 문서만으로 검증하지 않았다. 이를 “OpenAI 내장 기능”이나 “OpenAI 공식 필수 절차”라고 쓰지 않는다. 제3자 배포처를 별도로 검증한 뒤 선택 확장으로 소개해야 한다. 설치된 이름은 `$` 선택기에서 확인하는 안내가 안전하다.

## 7. 이어하기, diff, review, 작업 위치

| 목적 | CLI에서 확인한 기능 |
| --- | --- |
| 이전 대화 선택 | `codex resume` 또는 세션 안의 `/resume` |
| 현재 폴더의 최근 대화 | `codex resume --last` |
| 다른 폴더의 대화까지 선택 | `codex resume --all` |
| 변경 내용 보기 | `/diff` (staged·unstaged·untracked 포함) |
| Codex의 변경 검토 요청 | `/review` |

위 명령은 CLI용이다. 앱에서는 사이드바의 해당 대화를 다시 열며, 앱의 `/review`로 로컬 변경을 검토할 수 있다. [CLI 명령](https://learn.chatgpt.com/docs/developer-commands), [앱 리뷰](https://learn.chatgpt.com/docs/code-review)

`/review`는 Git checkout의 변경을 읽고 우선순위가 있는 문제를 보고하며 작업 파일을 수정하지 않는다. 앱에서는 변경 창으로 diff를 열고 직접 검토할 수 있고, Unstaged·Staged·Branch·Last turn 등의 범위를 고를 수 있다. 리뷰 창의 변경에는 사용자와 다른 도구가 만든 변경도 포함된다. AI 리뷰를 실제 실행 테스트의 대체로 설명하지 않는다. [코드 리뷰](https://learn.chatgpt.com/docs/code-review)

앱의 **Local**은 현재 프로젝트 폴더, **Worktree**는 Git으로 분리한 작업 사본, **Cloud**는 별도로 준비된 원격 환경이다. Local과 Worktree는 모두 사용자 컴퓨터에서 실행된다. 입문 실습은 This computer/Local이 단순하다. [실행 위치](https://learn.chatgpt.com/docs/environments/modes)

Worktree에는 Git 저장소가 필요하다. 새 대화에서 입력창 아래 Worktree를 선택하고 시작 브랜치를 고른 뒤 요청하면 생성된다. 기본은 detached HEAD이며, 결과를 유지할 브랜치를 만들거나 Handoff로 Local에 옮길 수 있다. “새 대화마다 무조건 Worktree”로 가르칠 필요는 없다. [Worktree](https://learn.chatgpt.com/docs/environments/git-worktrees)

## 8. 요리 예제에 연결할 교육 흐름

아래는 기능 사실을 바탕으로 편집한 수업 구성이다. OpenAI의 공식 요리 튜토리얼은 아니다.

| 단계 | 학습자가 맡길 일 | 직접 확인할 결과 |
| --- | --- | --- |
| 계획 | `/plan`으로 한 페이지 레시피의 범위·완료 조건 정하기 | 제목, 기준 인분, 재료, 순서, 모바일 확인을 포함한 짧은 목록 |
| 설계 | 2인 기준 재료 데이터와 화면 배치를 먼저 설명받기 | 데이터와 표현의 구분, 표시 단위, 파일 구성 |
| 구현 | 검토한 계획에 따라 정적 HTML 만들기 | 브라우저에서 열리는 실제 파일 |
| 검증 | 넓은 화면·좁은 화면, 재료 누락, 링크와 읽기 순서 확인 | 실행한 확인과 남은 문제를 구분한 보고 |
| 공개 | 검토한 파일만 GitHub Pages에 게시하는 절차 학습 | 공개 URL의 파일·경로·표시 상태; 사용자 검토 후 별도 실행 |
| 심화 | 기준 수량 × 요청 인분 ÷ 2 계산 기능 추가 | 1·2·6인 정상값, 0·7·1.5·빈 입력 처리, 화면 갱신 |
| 재사용 | `$skill-creator`로 레시피 편집 절차 저장 | 실제 새 레시피 요청으로 형식과 검증 절차 재현 |

심화는 “테스트가 실패함을 확인 → 최소 구현 → 통과 확인 → 구조 정리 → 다시 검증”을 작은 수량 계산 함수로 보여주기 적합하다. 이는 수업의 개발 방식 제안이며 Codex가 테스트를 항상 자동 보장한다는 뜻은 아니다. 요청에는 예상 결과와 사용할 검증 명령을 포함하고, 테스트 도구가 없으면 먼저 현재 프로젝트에 맞는 방법을 정한다. GitHub Pages의 정확한 메뉴·요금·저장소 제약은 별도 GitHub 공식 문서 조사 대상이며 본 메모에서 검증하지 않았다.

## 9. 가이드 반영 시 사실 확인 체크

- 앱의 ChatGPT/Codex 선택과 Chat/Work 선택을 섞지 않는다.
- 모델은 확인일을 표시하고 계정에 나타나는 목록을 우선한다. Medium은 수업의 선택으로 설명한다.
- Plan·읽기 전용 sandbox·승인 정책을 같은 기능으로 표현하지 않는다.
- 앱과 CLI 명령 목록을 분리한다. 앱에는 `/reasoning`, CLI에는 `/permissions`, `/diff`, `/resume`, `/plugins`가 각각 확인됐다.
- 현재 공식 로컬 skill 경로는 `.agents/skills`다. 설치 plugin의 내부 cache 경로를 학습자의 직접 편집 위치로 안내하지 않는다.
- 새 plugin 설치 후 새 대화/세션을 시작한다.
- 학습자의 GitHub 게시 실습과 이 가이드 제작 저장소의 실제 푸시는 구분한다.

## 10. 최종 실습 구성과 추가 공식 근거

- 입문은 `recipe.md`를 바탕으로 CSS를 포함한 `index.html` 한 장을 만든다. 기본 자료는 2인분 갈비찜이며 사진·영양 수치·조리 시간을 추가로 생성하지 않는다. 사용자의 요리 변경 요청을 반영해 소갈비·무·당근·간장·설탕·다진 마늘·참기름의 일곱 재료로 구성했다. 요리 예시는 학습용 편집 자료이며 조리 실측 자료가 아니다.
- 심화는 1~6의 정수 인분을 받아 `기준량 × 인분 ÷ 2`로 계산한다. 빈 값·범위 밖 값·소수·문자를 거부하고 마지막 유효 결과를 유지한다. 초기화·반복 변경·새로고침·키보드·모바일 확인을 완료 기준에 포함했다.
- 심화의 실제 계산 코드 `servings.mjs`를 페이지와 `tests/servings.test.mjs`가 함께 사용한다. 테스트 안에 계산식을 복제해 자기 자신만 검증하는 구성을 피한다. Node.js 내장 `node:test`와 `node --test`를 사용하며 외부 npm 패키지는 필수로 만들지 않았다. [Node.js 테스트 러너](https://nodejs.org/api/test.html)
- Node.js는 확인 당시 LTS 다운로드가 제공된다. 독자에게 버전을 고정하지 않고 공식 페이지의 현재 LTS를 선택하도록 안내한다. [공식 다운로드](https://nodejs.org/en/download)
- 브라우저 ES 모듈의 로컬 확인은 `file://` 대신 HTTP 서버를 사용한다. 한국어 MDN 원문에서 로컬 서버와 CORS 설명을 확인했고 영문 원문도 대조했다. `.mjs`를 GitHub Pages에서 제공할 수 있다는 영문 안내도 확인했다. [한국어 모듈 안내](https://developer.mozilla.org/ko/docs/Web/JavaScript/Guide/Modules), [영문 원문](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)
- 배포는 앞서 Claude Code 가이드 작성 중 같은 확인일에 검증한 GitHub 공식 절차를 재사용했다. 개인 Public 저장소, README로 기본 브랜치 생성, 파일을 루트에 업로드, Settings → Pages → Deploy from a branch → main → /(root) → Save, Actions와 Visit site를 확인한다. 기본 `github.io` 주소를 사용하고 HTTPS를 확인한다. [사이트 생성](https://docs.github.com/ko/pages/getting-started-with-github-pages/creating-a-github-pages-site), [게시 위치](https://docs.github.com/ko/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [HTTPS](https://docs.github.com/ko/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)
- 공개 파일은 입문 `index.html`·`.nojekyll`, 심화에서는 여기에 `servings.mjs`를 추가한다. 요구사항·지침·스킬·테스트·로컬 서버·확인 기록은 이번 학습의 로컬 자료로 둔다.
- 선택 스킬 실습은 `$skill-creator`로 `recipe-check`를 만든 뒤 실제 정상 자료와 복사본의 수량 오류를 검사하는 과정으로 정했다. 스킬의 검사와 자동 수정·배포를 구분한다.
- 가이드 자체는 13개 장, 10개 도식, 다운로드 3종으로 구성했다. 실제 학습자 계정에서의 설치·모델 실행·계산기 완성·배포를 모두 수행한 결과라고 주장하지 않는다.

## 11. Wayfinder + Superpowers로 개발 과정을 경험하는 심화

추가 확인일: 2026-10-03. 이 절은 앞선 6절의 조사 범위를 넓혀 **각 프로젝트의 공식 저장소**, 설치 도구 제작자의 저장소, Git 공식 문서까지 확인한 추가 메모다. 앞선 본문은 보존했다. 아래 명령은 가이드용으로 검증한 문법이며 실제 설치·clone·브랜치 생성·커밋·푸시는 실행하지 않았다.

### 11.1. 확인한 역할과 수업에서 조정할 부분

**사실:** Wayfinder는 `mattpocock/skills`의 `skills/engineering/wayfinder/SKILL.md`에 있다. 기본 목적은 여러 세션에 걸친 불확실한 일을 의사결정 지도와 질문 티켓으로 나누는 것이다. 티켓은 구현 작업 조각이 아니라 결정할 질문이다. 지도의 기본 종료 조건도 구현 완료가 아니라 결정할 것이 없어져 진행 방향이 명확해지는 시점이다. 초기 호출은 지도와 티켓을 만들고 멈추며, 후속 세션은 원칙적으로 티켓 하나를 해결한다. 연구 티켓은 예외다. 작고 경로가 명확하면 지도가 불필요하다고 알리고 진행 방향을 묻는다. [Wayfinder 원문](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)

**사실:** 최신 Superpowers `brainstorming`은 Spike·Bounded·Architectural로 과정을 나눈다. 기존 코드의 작은 변경은 짧은 채팅 설계만으로 진행할 수 있고, 새 구조를 만드는 작업은 설계 문서와 구현 계획을 검토한다. `writing-plans`는 작업 파일, 인터페이스, 테스트, 실행 명령과 예상 결과를 정리한다. [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

**수업 권장:** 인분 계산기에서는 큰 프로젝트용 과정을 짧게 축소해 체험한다. 이미 확정한 2인 기준·1~6 정수·잘못된 입력 처리 등을 다시 미정으로 만들지 않는다. 실제로 남은 화면 선택·표시 방식 등을 지도에서 결정한 뒤, 짧은 설계서와 실행 계획을 남기는 데 학습 목적을 둔다. 모든 작은 기능에 전체 문서 절차가 필수라고 설명하지 않는다. 두 프로젝트를 연결한 이 수업 흐름은 가이드의 편집 구성이다.

| 경험할 단계 | 주로 사용할 skill | 학습자가 직접 판단할 것 |
| --- | --- | --- |
| 결정 지도 | Wayfinder | 무엇이 이미 정해졌고 어떤 질문이 남았는지 |
| 설계 | Superpowers brainstorming | 선택지의 장단점과 최종 화면·데이터 구조 |
| 구현 계획 | Superpowers writing-plans | 파일, 작업 순서, 각 단계의 성공 조건 |
| 구현과 테스트 | Superpowers executing-plans + test-driven-development | 실패한 테스트가 왜 실패했고 구현 뒤 왜 통과했는지 |
| 코드 검토 | Superpowers requesting-code-review | 요구사항 누락·오류가 있는지, 지적이 타당한지 |
| 완료 검증 | Superpowers verification-before-completion | 실제 명령 결과·화면 증거로 완료를 말할 수 있는지 |

### 11.2. 권장 준비: 공개 저장소를 로컬에 복제하고 기능 브랜치 만들기

**사실:** Git 공식 사이트는 OS별 설치 경로를 제공한다. `git clone <repository> <directory>`는 저장소를 새 폴더로 복제하며 지정 폴더가 이미 있으면 비어 있어야 한다. `git switch -c <new-branch>`는 새 브랜치를 만들고 전환한다. [Git 설치](https://git-scm.com/install/), [clone](https://git-scm.com/docs/git-clone), [switch](https://git-scm.com/docs/git-switch)

수업용 터미널 예시. `YOUR-ID`와 `YOUR-REPO`는 입문에서 공개한 본인 저장소 값으로 바꾼다. 새 폴더가 생길 상위 위치에서 시작한다.

```sh
git --version
git clone https://github.com/YOUR-ID/YOUR-REPO.git hello-kitchen-process
cd hello-kitchen-process
git switch -c codex/servings-calculator
```

`recipe.md`, `AGENTS.md`, `advanced-brief.md`는 앞 단계의 로컬 자료에서 이 새 폴더로 복사하고, 앱에서도 **hello-kitchen-process**를 연다. 공개 저장소에 올리지 않았던 로컬 파일은 clone만으로 따라오지 않는다. 이 연결 설명은 수업 구성이다.

첫 커밋에는 이름·이메일 설정이 필요하다. 이미 설정돼 있으면 유지하고, 없다면 학습자의 이름과 커밋용 이메일을 설정한다. `git config user.name ...`, `git config user.email ...`처럼 `--global`을 생략하면 현재 저장소에만 적용할 수 있다. 예시 값을 실제 신원으로 잘못 안내하지 않는다. [Git 초기 설정](https://git-scm.com/book/en/v2/Getting-Started-First-Time-Git-Setup)

### 11.3. Wayfinder 설치: Codex 앱의 채팅 명령과 터미널 명령 구분

**사실:** Matt Pocock의 현재 README는 Codex에 `npx skills@latest add mattpocock/skills`를 안내한다. native Codex plugin은 아직 보류된 것으로 설명한다. 따라서 Claude용 `/plugin install mattpocock-skills`를 Codex 설치법으로 옮기면 안 된다. [공식 README의 Codex 항목](https://github.com/mattpocock/skills#installation-30-second-setup), [Codex plugin 보류 결정](https://github.com/mattpocock/skills/blob/main/.agents/adr/0002-ship-as-a-claude-code-plugin.md)

Node.js/npm을 준비한 뒤, **hello-kitchen-process 폴더의 터미널**에서 실행할 권장 대화식 명령:

```sh
npx skills@latest add mattpocock/skills
```

설치 화면에서는 다음을 안내한다.

- 대상 agent는 Codex, 범위는 Project를 선택한다. 감지된 agent 수에 따라 선택 화면이 생략될 수 있으므로 마지막 요약의 대상을 확인한다.
- 최소한 `wayfinder`, `setup-matt-pocock-skills`, `grilling`, `domain-modeling`, `research`, `prototype`을 포함한다. 앞의 두 개는 사용자 진입점이며 나머지는 Wayfinder가 질문·조사·시제품에 호출하는 skill이다. 필요한 것을 고르기 어려우면 묶음 전체를 선택할 수 있지만, 이를 Wayfinder 단일 skill 설치라고 표현하지 않는다. [Wayfinder의 호출 관계](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)
- 설치 방식에는 Symlink와 Copy가 있다. 초보 Windows 실습은 링크 권한 문제를 줄이기 위해 Copy를 수업 선택으로 권장할 수 있다.
- `--all`은 모든 skill을 모든 agent에 확인 없이 설치하는 옵션이다. Codex 하나만 대상으로 삼는 안내에는 사용하지 않는다. [설치 도구 옵션](https://github.com/vercel-labs/skills#options), [설치 방식](https://github.com/vercel-labs/skills#installation-methods)

선택 오류를 줄이는 대안은 다음과 같다. 제작자가 안내한 저장소와 Vercel이 문서화한 옵션을 조합한 명령이며, 별도의 공식 단일 레시피는 아니다.

```sh
npx skills@latest add mattpocock/skills --agent codex --skill wayfinder setup-matt-pocock-skills grilling domain-modeling research prototype --copy
```

`--skill` 다음은 공백으로 구분한 이름이다. `--skill=...` 표기는 이 안내에서 사용하지 않는다. 설치 전 목록만 보려면 `npx skills@latest add mattpocock/skills --list`, Codex 설치 목록을 확인하려면 `npx skills@latest list --agent codex`를 쓸 수 있다. 프로젝트 범위의 Codex skill 경로는 `.agents/skills/`다. [Vercel README](https://github.com/vercel-labs/skills), [대화식 선택 구현](https://github.com/vercel-labs/skills/blob/main/src/add.ts)

설치 후 앱에서 해당 폴더의 새 Codex 대화를 열고 `$` 선택기에서 `wayfinder`와 `setup-matt-pocock-skills`가 보이는지 확인한다. 없으면 앱을 재시작하고 폴더·설치 대상·범위를 확인한다. 이는 Codex의 skill 명시 호출 및 재감지 안내를 적용한 확인 절차다. [Codex skill 호출과 재감지](https://learn.chatgpt.com/docs/build-skills)

### 11.4. Wayfinder 초기 설정과 지도 호출 문구

**사실:** setup은 issue tracker와 문서 위치를 설정하는 대화형 skill이다. GitHub remote가 있으면 GitHub를 제안할 수 있으므로, 이번 수업은 **Local Markdown**을 명시한다. 결과는 `docs/agents/issue-tracker.md`, `docs/agents/domain.md`와 기존 지침 파일의 연결 문구다. `triage`가 설치되지 않았으면 triage 설정은 생략된다. 초안을 보여준 뒤 사용자가 확인하도록 되어 있다. [setup 원문](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/SKILL.md)

Codex 앱의 새 대화에 넣을 수업용 문구:

```text
$setup-matt-pocock-skills
이 폴더는 인분 계산기 개발 과정을 배우는 프로젝트야.
issue tracker는 GitHub Issues 대신 Local Markdown을 사용해.
기존 AGENTS.md를 유지하면서 설정 초안을 보여줘.
외부 이슈를 만들거나 푸시하지 마.
```

원문의 Local Markdown tracker는 `.scratch/<effort>/map.md`를 지도, `.scratch/<effort>/issues/NN-<slug>.md`를 질문 티켓으로 사용한다. `Blocked by`로 선행 질문을 연결하고, 해결된 답은 티켓에 기록하며 지도에는 짧은 설명과 링크만 남긴다. 구현 계획 파일과 구분해야 한다. [로컬 tracker 템플릿](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/issue-tracker-local.md)

지도 작성용 문구:

```text
$wayfinder
recipe.md, AGENTS.md, advanced-brief.md와 현재 index.html을 읽어줘.
인분 계산기를 만들기 전에 확정된 요구와 아직 결정할 질문을 나눠보자.
목적은 개발 과정을 배우는 것이어서, 작은 예제에도 짧은 지도를 남기고 싶어.
확정된 요구는 다시 질문으로 만들지 말고, 실제 미정 사항만 티켓으로 만들어줘.
Local Markdown tracker를 쓰고 지도 위치는 .scratch/servings-calculator/map.md로 해줘.
이번 대화에서는 지도까지만 만들고 제품 코드는 수정하지 마.
```

이 문구에서 작은 지도까지 남기도록 하는 부분은 수업을 위한 사용자 요청이다. 원래 Wayfinder는 지도 자체가 불필요하다고 판단할 수 있다. 지도에서 질문 하나를 고른 다음에는 **새 Codex 대화**에서 같은 폴더를 열고 다음처럼 실제 파일 경로로 이어간다.

```text
$wayfinder
.scratch/servings-calculator/map.md를 읽고 다음 미해결 질문 하나를 골라줘.
선택지와 추천 이유를 쉬운 말로 설명하고, 내 답을 기다려줘.
내 답이 정해지면 해당 티켓과 지도의 상태를 갱신해줘.
제품 구현은 하지 마.
```

학습자가 지도에서 확인할 것은 질문의 이름, 선행 관계, 자신의 선택, 선택 이유다. 지도와 답이 준비되면 다음 설계 단계로 넘긴다.

### 11.5. Superpowers 설치와 호출 이름

**사실:** Superpowers 제작자의 현재 README는 Codex 앱에서 **Plugins → Superpowers → +** 설치를 안내한다. Coding 영역에 있다는 설명도 있지만, 위치가 달라지면 이름으로 검색하는 안내가 더 안정적이다. Codex CLI 대안은 세션 안의 `/plugins`에서 `superpowers`를 검색해 **Install Plugin**을 선택하는 것이다. Claude용 `/plugin install ...`을 Codex 앱에 입력하는 방식은 아니다. [Superpowers Codex 설치](https://github.com/obra/superpowers#codex-app)

OpenAI 공식 문서는 plugin을 설치한 뒤 새 대화나 CLI 세션을 시작해야 포함된 skill과 도구가 사용 가능해진다고 설명한다. [OpenAI plugin 사용](https://learn.chatgpt.com/docs/plugins)

**이름 확인:** Codex용 manifest의 plugin 이름은 `superpowers`이며, 원문 skill들은 `superpowers:brainstorming`, `superpowers:writing-plans`, `superpowers:executing-plans`처럼 서로를 참조한다. Codex는 `$`로 skill을 선택할 수 있다. 따라서 가이드에는 `$`를 입력해 **Superpowers 출처의 해당 skill**을 고르거나, 다음처럼 자연어로 이름과 출처를 명시하는 방법을 권장한다. 모든 버전에서 동일한 문자열이 자동완성된다고 보장하지 않는다. [Codex manifest](https://github.com/obra/superpowers/blob/main/.codex-plugin/plugin.json), [skill 우선순위와 이름](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md), [Codex 명시 호출](https://learn.chatgpt.com/docs/skills-and-plugins)

```text
superpowers:brainstorming 스킬을 사용해 다음 기능을 설계해줘.
```

Wayfinder는 위 `npx` 경로에서 독립 skill 파일로 설치하므로 `$wayfinder`를 사용한다. Claude plugin의 `mattpocock-skills:wayfinder` 접두사를 이 경로의 필수 이름으로 설명하지 않는다.

**버전 주의:** 확인 당시 제작자 `main`의 Codex manifest는 6.4.2, 공개 `openai/plugins` 저장소의 Superpowers manifest는 6.3.0이었다. 공개 저장소 스냅샷만으로 사용자에게 제공되는 실시간 catalog 버전을 단정할 수 없다. 설치본과 최신 원문에 차이가 있을 수 있으므로, 수업에서는 설치한 skill을 읽고 적용하도록 요청한다. [제작자 manifest](https://github.com/obra/superpowers/blob/main/.codex-plugin/plugin.json), [OpenAI 공개 배포 manifest](https://github.com/openai/plugins/blob/main/plugins/superpowers/.codex-plugin/plugin.json)

### 11.6. 같은 폴더에서 inline 실행할 수 있는가

**사실:** `using-git-worktrees`는 기존 격리 환경을 먼저 확인하고, 사용자의 기존 worktree 선택을 존중한다. 사용자가 거절하면 현재 폴더에서 작업하도록 명시한다. 따라서 “Superpowers를 쓰려면 반드시 새 worktree를 만들어야 한다”는 설명은 부정확하다. [using-git-worktrees](https://github.com/obra/superpowers/blob/main/skills/using-git-worktrees/SKILL.md)

**사실:** `executing-plans`의 inline은 같은 세션에서 직접 작업별 구현을 진행한다는 뜻이다. 새 implementer를 매 작업마다 만드는 방식과 구분되며, 완료 후 전체 변경에 대한 별도 리뷰는 유지한다. 기본 절차에는 Git 커밋·SHA·작업 기록·리뷰 패키지가 포함된다. 실제 `sdd-workspace`는 `git rev-parse --show-toplevel`, `task-start`는 `git rev-parse HEAD`를 사용한다. Git 저장소 없는 폴더에서 전체 기본 흐름이 그대로 작동한다고 말할 수 없다. [executing-plans](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md), [sdd-workspace 코드](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/scripts/sdd-workspace), [task-start 코드](https://github.com/obra/superpowers/blob/main/skills/executing-plans/scripts/task-start)

**권장:** 11.2의 clone과 기능 브랜치를 준비한 뒤 같은 폴더에서 inline으로 실행한다. 이 선택은 Git을 생략하는 것과 다르다. 새 worktree 생성은 생략하되 기능 브랜치의 로컬 커밋을 허용하면 기본 실행·검토 흐름을 유지할 수 있다. 상위 skill은 사용자의 명시 지시가 skill보다 우선한다고 밝힌다. [사용자 지시 우선순위](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md)

설계부터 공유할 수업용 작업 조건:

```text
이번에는 hello-kitchen-process의 codex/servings-calculator 브랜치에서 작업해.
새 worktree를 만들지 말고 지금 폴더에서 진행해.
설계와 구현 계획은 내가 읽고 확인한 뒤 구현해.
구현 방식은 같은 세션에서 직접 실행하는 inline으로 정할게.
이 기능 브랜치의 로컬 커밋은 허용해.
push, merge, PR 생성, 공개 배포는 하지 마.
완료 후 브랜치와 확인 기록을 보존해줘.
```

Git 없는 상태를 유지하려면 SHA·커밋·브랜치 관련 보조 절차를 파일 기반 기록과 직접 검토로 대체하라는 별도 사용자 지시가 필요하다. 이는 전체 기본 실행 흐름을 조정하는 대안이며 이번 권장 경로가 아니다.

### 11.7. 복사 가능한 단계별 호출 문구

다음 프롬프트는 공식 skill의 역할에 맞춰 만든 **수업 예시**다. 파일 경로는 앞 단계에서 실제 생성된 경로로 대체한다.

**설계:**

```text
superpowers:brainstorming 스킬을 사용해.
advanced-brief.md와 .scratch/servings-calculator/map.md의 결정 사항을 읽어줘.
이제 인분 계산기의 화면, 데이터, 계산 함수, 잘못된 입력 처리를 설계하자.
이번 수업에서는 작은 기능이어도 설계와 구현 계획을 짧은 파일로 남기고 싶어.
두 가지 접근의 차이를 설명하고 내 선택을 기다려줘.
선택한 설계를 docs/superpowers/specs에 저장한 뒤 내가 읽고 확인하게 해줘.
아직 제품 코드를 구현하지 마.
```

**구현 계획:**

```text
이 설계 문서를 검토했고 내용에 동의해.
superpowers:writing-plans 스킬로 docs/superpowers/plans에 구현 계획을 만들어줘.
화면과 테스트가 함께 사용하는 servings.mjs를 기준으로 나눠줘.
각 작업에 수정 파일, 먼저 실패할 테스트, 실행 명령, 예상 결과를 적어줘.
계산식, 입력 검증, 화면 연결을 독립적으로 확인할 수 있게 해줘.
inline 실행을 선택했지만, 구현 전에는 완성된 계획을 내가 확인하게 해줘.
```

`writing-plans`의 기본 경로는 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`이며 사용자가 지정한 위치가 우선한다. 계획 작성 후에는 사용자가 결과를 검토하고 실행 방식을 정하는 절차가 있다. [계획과 실행 인계](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

**구현과 TDD:**

```text
이 구현 계획을 검토했고 진행해도 돼.
superpowers:executing-plans와 superpowers:test-driven-development를 사용해.
지금 기능 브랜치와 폴더에서 inline으로 계획을 실행해.
먼저 테스트가 요구한 이유로 실패하는 것을 확인하고 최소 구현으로 통과시켜줘.
단순 실행 오류를 기능 실패로 착각하지 말고 원인을 구분해줘.
작업마다 테스트 명령과 결과를 기록하고, 완료 후 전체 변경을 별도로 리뷰해줘.
실행을 막는 필수 도구가 없다면 실패 이유와 필요한 도구를 알려줘.
로컬 커밋은 허용하지만 push, merge, PR 생성, 배포는 하지 마.
```

TDD 원문은 테스트를 먼저 쓰고 실패를 관찰한 뒤 최소 코드를 구현하는 Red → Green → Refactor를 요구한다. 테스트가 처음부터 통과했다면 검증 대상과 테스트를 다시 살펴야 한다. [test-driven-development](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md)

**리뷰와 완료 검증:**

```text
superpowers:requesting-code-review로 설계와 계획에 비춰 전체 변경을 검토해줘.
이미 마지막 리뷰를 했다면 그 결과와 남은 지적부터 보여줘.
중요한 오류는 재현 테스트로 확인하고 수정해줘.
이어서 superpowers:verification-before-completion으로 최종 확인해줘.
node --test 결과, 브라우저의 초기값·반복 변경·초기화·잘못된 입력·새로고침,
모바일과 키보드 확인을 요구사항별로 보고해줘.
직접 확인하지 못한 항목은 미확인으로 표시해.
최종 커밋과 남은 작업을 알려주고 브랜치를 그대로 보존해줘.
```

리뷰 skill은 계획과 변경 범위를 reviewer에게 전달하고 중요도에 따라 지적을 처리한다. 검증 skill은 실제로 실행한 명령의 전체 결과와 종료 상태를 확인한 뒤 완료를 말하도록 요구한다. 기존 테스트 결과나 다른 agent의 완료 선언만으로 통과를 단정하지 않는다. [requesting-code-review](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md), [verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)

### 11.8. 학습자가 마지막에 남길 증거

권장 산출물은 결정 지도와 답, 설계 문서, 구현 계획, 테스트 실패·통과 기록, 실제 동작하는 화면, 리뷰 지적과 처리 결과다. 파일 개수 자체가 학습 목표가 아니라 **내가 결정한 요구가 코드와 검증 결과까지 이어지는지**를 확인하는 데 목적이 있다.

이번 수업의 공개 단계는 앞선 GitHub 웹 업로드 절차를 유지한다. 학습자가 검토한 `index.html`, `servings.mjs`, `.nojekyll`만 선택하고, 지도·지침·테스트·설치 skill·로컬 서버·작업 기록 전체를 폴더째 업로드하지 않도록 구분한다. 로컬 커밋은 GitHub 게시를 자동 수행하지 않는다. 실제 배포 전 확인은 별도 단계다.
