## 구성과 원문 재확인

인사 → 추천 3편 → 사례연구 → 일반뉴스 → 단신 → 작업물 업데이트 → 작은 실습 → 맺음말 순서다. 관찰할 방법을 마련한 Beep Locator, 선택지를 평가하는 Decision, 설치 구성을 비교한 MCP 조사를 추천한다. 관련 주제를 연결한 편집이며 세 자료를 하나의 성능 증거로 합치지 않는다.

## 작은 실습의 범위

- 사용자 피드백에 따라 화면 중복에 관한 가상 문답을, 웹서버·Tomcat·모의 PG·테스트 DB를 사용하는 실험 설계로 바꿨다. 사례연구 09의 ‘관찰할 수 있는 환경을 마련하고 근거로 원인을 좁힌다’는 주제를 이어간다.
- 브라우저 → Nginx 또는 Apache → Tomcat, Tomcat ↔ PG와 Tomcat ↔ DB의 분기를 표시한다. PG가 주문 DB에 직접 쓰는 구조로 설명하지 않는다. 외부 결제·실제 고객 데이터 없이 로컬 모의 PG를 사용한다.
- 정상 처리, PG 승인 후 응답만 5초 지연, 승인 후 DB 상태 갱신 실패를 각각 비교한다. 지연 실험은 웹서버 3초·앱 HTTP 클라이언트 8초와 응답 중간 전송 없음·자동 재시도 없음 조건을 둔다. 최초 주문 저장과 승인 후 상태 변경은 별도 DB 트랜잭션이다.
- 0·3·5초 시간표는 설계한 예상 흐름이며 관측 결과가 아니다. 웹서버 연결 종료 후 Tomcat 처리가 이어지는지는 앱 구현과 실제 기록으로 확인한다. DB 롤백과 외부 PG 승인 취소를 구분한다.
- 같은 구매 시도 ID·같은 결제 내용·같은 PG 멱등키로 재요청하되 요청 ID는 달리한다. PG 호출 수와 승인 수, DB 저장 시도와 커밋된 행을 구분한다. 재시도·동시 요청에서 승인 1건/주문 1건 유지와 서로 다른 주문의 정상 처리를 검사하도록 제안했다.
- 설정·관측 항목은 접이식 설명, 구조와 예상 시간표는 정적 HTML/CSS로 구현한다. 해당 호 전용 CSS를 추가했으며 공통 스타일은 변경하지 않았다.
- 실제 주문 시스템 구현·환경 구축·재현·수정·모델 실험은 수행하지 않았다.

### 실험 설계의 기술 근거 · 11월 17일 확인

- [Nginx proxy_read_timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout): 전체 요청 시간 상한이 아닌, 응답 읽기 사이의 대기 제한. 3초는 이번 모의 실험에서 정한 값이다.
- [Nginx proxy_next_upstream](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream): `off`는 다음 upstream으로 넘기지 않게 한다. 브라우저·앱 자동 재시도도 별도로 끄도록 명시했다.
- [Apache ProxyTimeout](https://httpd.apache.org/docs/2.4/mod/mod_proxy.html#proxytimeout): 프록시 요청의 네트워크 대기 설정. Nginx와 동일한 설정 이름·재시도 동작이라고 주장하지 않는다.
- [토스페이먼츠 멱등키](https://docs.tosspayments.com/reference/using-api/authorization#멱등키-헤더): 키 적용 범위, 처리 중 응답, 오류 뒤 키 변경 위험을 확인했다. 모의 PG의 동작 규약과 실제 PG 연동 규약은 구분한다.
- [토스페이먼츠 타임아웃](https://docs.tosspayments.com/resources/glossary/timeout): 실제 결제 API의 권장 대기 값이 이번 모의 실험의 3·5·8초와 다름을 확인했다. 본문 수치를 운영 권장값으로 제시하지 않는다.

## 검증 기록

### 실험 환경 예시 개편 후 확인

- 기존 Node 테스트 71개 통과, 실패 0개. 문서 속 주문 환경을 실행한 결과가 아니라 저장소의 기존 기능 검사다.
- 본문·목록·홈의 로컬 참조 107개와 앵커, 외부 링크 속성, 중복 ID, 콘텐츠 편수를 검사했다. 새 실험은 비교표 3행·예상 시간표 3단계이며 `noindex`를 유지한다.
- 데스크톱 라이트에서 서버 분기 흐름도·예상 시간표·비교표를 확인했다. CSS viewport 390px, 실제 본문 폭 375px에서 라이트·다크 화면을 확인했으며 페이지 가로 넘침은 없었다. 비교표는 자체 영역 안에서 가로 스크롤되고, 키보드 오른쪽 화살표로도 이동했다.
- 상세 설정 설명의 펼침·접힘과 모바일에서 펼쳤을 때의 넘침 여부를 확인했다. 최종 확인 탭의 브라우저 error·warn 로그는 없었다. 임시 화면 크기와 다크 모드 설정은 복구했다.
- 기존 탭의 댓글 모드가 일부 조작을 가로채 별도 미리보기 탭에서 동작을 확인했다. 앞서 기록한 긴 목차 스크롤의 검증 한계는 유지한다.
- 실제 PG 호출·실험 환경 구축·장애 재현·결제 처리는 수행하지 않았다. 커밋·푸시·배포·메일 발송도 하지 않았다.

### 최초 작성 시 확인

- 기존 `node --test --test-reporter=dot`에서 71개 테스트가 통과했다. 저장소 기능 검사이며 기사 속 제품·연구·제안 실습의 실행 결과가 아니다.
- 일회성 HTML 검사로 분야별 목록의 기간 내 URL 집합과 뉴스레터의 새 글 10개 고유 URL이 정확히 일치함을 확인했다. 일반뉴스 7·단신 2·사례연구 1, 추천 3편의 포함 관계, 작업물 업데이트 1편과 목록의 7개 호도 확인했다.
- 홈·목록·7호의 상대 파일·자산·앵커 참조 107개, 외부 링크의 새 탭·rel 속성, 중복 ID 없음, noindex와 공통 스크립트를 확인했다. 작업물 보고서 앵커를 실제 `#measured`로 맞췄다.
- `git diff --check`를 통과했다. 새 원고·편집 기록의 줄 끝 공백·마지막 개행·엠대시·문자 대체 기호도 검사했다.
- 앱 내 브라우저에서 로컬 HTTP로 확인했다. 기본 데스크톱과 실제 CSS viewport 폭 354px·291px(스크롤바를 뺀 본문 폭 340px·277px)에서 본문 가로 넘침이 없었다. 브라우저에 요청한 390px·320px와 실제 CSS viewport가 달라 측정된 폭을 기록한다.
