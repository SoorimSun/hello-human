수량 선택 순서는 **명시한 `cancelQuantity` → 맵의 해당 값 → 품목의 남은 수량**입니다.

1. **둘 다 들어오면 `cancelQuantity`가 우선**입니다. `cancelQuantity == null`일 때만 맵을 조회하므로, 0을 명시해도 맵 값으로 대체하지 않습니다(`OrderServices.java` 2006·2012~2016행).
2. **직접 수량이 없으면** `itemQtyMap`에서 `orderItemSeqId + ":" + shipGroupSeqId` 키를 조회합니다. 예를 들어 `{"00001:00001": "2"}`이며, 해당 값이 비어 있지 않으면 `new BigDecimal(...)`로 변환합니다(2013~2016행).
3. **맵이 없거나 비어 있거나, 해당 키의 값이 없거나 비어 있으면** `cancelQuantity`는 null로 남고 `itemQuantity`를 사용합니다(2097~2102행). 이는 **품목 주문수량 − 기존 취소수량 − 입고수량(구매주문) 또는 출고수량(그 외)**입니다(2071~2094행). 배송그룹의 잔여수량을 기본값으로 쓰는 것은 아닙니다.

입력 정의상 `cancelQuantity`는 `BigDecimal`, `itemQtyMap`은 `Map`이며 요청 필드 접두사로 `iqm_`가 선언돼 있습니다(`services.xml` 284·287행). Java 내부 조회 키에는 접두사가 없습니다. 또한 맵 조회는 반복문 전에 요청의 두 ID로 한 번만 하므로, 조회된 배송그룹마다 키를 다시 만들지 않습니다(2013~2019·2051행).

선택한 수량이 배송그룹의 `quantity − cancelQuantity`보다 크면 자동 축소하지 않고 오류를 반환합니다(2065~2069·2104·2213~2215행).

추가 확인할 내용은 `iqm_00001:00001` 같은 요청 필드가 실제 맵으로 변환되는 과정과 우선순위·키 누락 테스트입니다. 제공된 테스트 발췌는 주문 생성만 다룹니다.
