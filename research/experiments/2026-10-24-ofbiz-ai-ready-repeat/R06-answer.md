선택 순서는 **null이 아닌 `cancelQuantity` → 맵의 해당 키 값 → 계산된 남은 항목 수량**입니다.

확인한 코드 근거는 다음과 같습니다.

1. **두 입력이 함께 있으면 `cancelQuantity`가 우선합니다.** `cancelQuantity == null`일 때만 `itemQtyMap`을 조회하므로, 명시한 값이 0이어도 맵 값으로 대체하지 않습니다(`OrderServices.java` 2006~2017행).

2. **맵 내부 키는 `orderItemSeqId + ":" + shipGroupSeqId`입니다.** 예를 들어 `00001:00002`이며, 값은 문자열로 읽어 `new BigDecimal(...)`로 변환합니다. 서비스 정의에서 `cancelQuantity`는 `BigDecimal`, `itemQtyMap`은 `Map`이고 문자열 입력 접두사는 `iqm_`로 선언돼 있습니다. 따라서 접두사를 붙인 입력 형태는 `iqm_00001:00002`, Java가 조회하는 맵 키는 `00001:00002`로 구분해야 합니다(`services.xml` 284~287행, Java 2012~2016행).

3. **직접 수량이 null이고 맵이 없거나 비어 있거나 해당 키 값이 비어 있으면**, `cancelQuantity`는 null로 남아 `itemQuantity`를 사용합니다. 이는 항목의 주문 수량에서 기취소 수량을 빼고, 구매 주문은 수령 수량, 그 외는 출고 수량을 추가로 뺀 값입니다(Java 2071~2102행).

배송 그룹의 `availableQuantity`는 기본값이 아니라 상한 검사에 사용됩니다. 선택한 수량이 이를 넘으면 자동 축소하지 않고 오류를 반환합니다(Java 2065~2069, 2104, 2213~2215행). 맵 조회는 반복문 전에 입력 식별자로 한 번 수행되며, 각 배송 그룹의 키를 순회해 다시 선택하지 않습니다.

추가 확인이 필요한 부분은 실제 요청에서 `iqm_` 입력을 맵으로 변환하는 경로와 실행 결과입니다. 제공된 생성 테스트와 미실행 초안은 위 우선순위·키 누락 동작을 검증한 근거가 아닙니다.
