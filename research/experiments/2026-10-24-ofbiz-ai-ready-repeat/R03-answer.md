선택 순서는 **명시적 `cancelQuantity` → `itemQtyMap`의 해당 값 → 계산된 품목 잔여 수량**입니다.

확인한 근거:

1. `cancelQuantity`가 `null`이 아니면 그대로 사용합니다. 맵 조회 조건이 `cancelQuantity == null`이므로 둘 다 들어오면 명시적 수량이 우선합니다. `0`도 이 조건에서는 명시적 수량입니다(`OrderServices.java` 2006, 2012~2016행).

2. 명시적 수량이 없고 맵이 비어 있지 않으면, 요청의 `orderItemSeqId + ":" + shipGroupSeqId`로 조회합니다. 맵 내부 키는 예를 들어 `00001:00001`이고, 값은 문자열을 `new BigDecimal(...)`로 변환합니다. 서비스 정의에는 `itemQtyMap`의 `string-map-prefix="iqm_"`가 선언돼 있습니다(`services.xml` 284~287행).

3. 해당 키가 없거나 값이 비어 있으면 `cancelQuantity`는 `null`로 남습니다. 이때 `thisCancelQty`에는 **품목 수량 − 기존 품목 취소 수량 − 입고/출하 수량**을 사용합니다. 구매 주문은 입고 수량, 그 외는 출하 수량을 뺍니다. 키 누락을 0이나 취소 생략으로 처리하지 않습니다(2071~2102행).

맵 조회는 반복문 전에 요청 ID로 한 번 수행됩니다. 각 배송 그룹의 키를 다시 조회하지 않습니다(2013~2019, 2051행). 선택 수량이 배송 그룹의 `quantity − cancelQuantity`보다 크면 자동 축소하지 않고 오류를 반환합니다(2065~2069, 2104, 2213~2215행).

추가 확인 사항: `iqm_00001:00001` 같은 요청 필드가 실제 맵으로 변환되는 과정은 발췌에 없습니다. 요청 바인딩 구현과 실제 입력 폼을 확인해야 합니다. 제공된 테스트는 주문 생성만 다뤄 이 선택 순서를 검증하지 않습니다.
