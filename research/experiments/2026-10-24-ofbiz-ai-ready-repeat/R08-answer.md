확인된 선택 순서는 **명시적 `cancelQuantity` → 해당 맵 값 → 계산된 잔여 품목 수량**입니다.

1. **둘 다 들어오면 `cancelQuantity`가 우선합니다.** `OrderServices.java` 2006~2016행은 `cancelQuantity == null`일 때만 `itemQtyMap`을 조회합니다. 따라서 명시값이 0이어도 맵 값으로 대체하지 않습니다.

2. **맵 내부 키는 `orderItemSeqId + ":" + shipGroupSeqId`입니다.** 예를 들어 `00001:00002`이며, 해당 값이 비어 있지 않으면 문자열을 `BigDecimal`로 변환합니다(2014~2016행). `services.xml` 284~287행은 `cancelQuantity`를 `BigDecimal`, `itemQtyMap`을 `Map`으로 선언하고, 맵 입력 접두사로 `iqm_`를 지정합니다. Java가 조회하는 내부 키에는 `iqm_`가 없습니다.

3. **명시값이 없고 맵·키·값도 없거나 비어 있으면 잔여 품목 수량을 씁니다.** `cancelQuantity`가 null로 남아 `thisCancelQty = itemQuantity`가 됩니다(2097~2102행). 이 수량은 품목 주문수량에서 기존 취소수량을 빼고, 구매주문이면 입고수량, 그 외에는 출고수량을 추가로 뺀 값입니다(2071~2094행).

맵 조회는 배송그룹 연결 목록을 순회하기 **전에 한 번만** 수행합니다(2013~2019, 2051행). 각 연결마다 키를 다시 만들지 않습니다. 선택된 수량이 해당 연결의 `quantity - cancelQuantity`보다 크면 자동 축소하지 않고 오류를 반환합니다(2065~2069, 2104, 2213~2215행).

추가 확인이 필요한 부분은 `iqm_00001:00002` 같은 요청 필드를 내부 맵으로 구성하는 실제 입력 처리 경로입니다. 발췌에는 접두사 선언만 있으며, 제공된 테스트도 이 우선순위와 키 누락 사례를 검증하지 않습니다.
